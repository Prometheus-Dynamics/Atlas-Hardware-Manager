# B38: a real build of one product, by hand

`scripts/build-product.sh <product>` runs Gaia at the locked commit for one product under `devices/products`: the
OS, the kernel, every component and the image. The gate never does this (it stops at the resolved configuration).
The same script is the `build-product` job of the `next` workflow, started by hand with a product name; it keeps
the image files as the run's artifact with sizes and SHA-256. Nothing is released, tagged or published.

## Run here (2026-11-14, Gaia c6a3d10, this PC, cores 6-31, nice 19)

`scripts/build-product.sh raze-base --jobs 13 --tool veritysetup=<stand-in>`: every step up to and including the
root filesystem image was made; it stopped at `raze-base::verity`, as expected here: this PC has no `veritysetup`
(the CI job installs cryptsetup). 67 steps, 1,775 s, from a store that held the sources only.

- Root filesystem: 36,188,160 bytes as EROFS; 74,364,638 bytes as files; 115 kernel modules.
- In it: lemnosd 2,431,800; orion 5,072,904 bytes (the sizes Gaia measured), lemnos-ctl, lemnos-orion.
- Store after the build: 11 GiB (6.3 GiB before).

Found by the build, not fixed here (reported to the coordinator for Gaia):
1. The root tree carries Buildroot's marker file `THIS_IS_NOT_YOUR_ROOT_FILESYSTEM` (Buildroot's own image
   steps leave it out; Gaia takes the target tree as it is).
2. `--jobs 13` does not bound Buildroot's `make`: it ran `-j26` (the cores the process may use) in up to three
   builds at once.

The hand-started job built `raze-base` end to end on a hosted runner, verity and slot included.

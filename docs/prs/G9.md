# G9: What must build on Windows and macOS is checked in CI

**Group:** G. Board runs and finish

**Needs:** nothing

Read `AGENTS.md` and `docs/design.md` first.

## Why

Atlas is a desktop app for Linux, Windows and macOS. Every crate that talks to a board depends on
Orion's client, and at the Orion rev the root `Cargo.toml` locks (`455a956e`) that client is
`#![cfg(target_os = "linux")]`. So those crates cannot build elsewhere. Everything else must build on
all three systems now and must not regress while Orion's portable client is in flight.

## What this PR adds

- `scripts/orion-bound.txt`: the data. The Orion-bound list (one crate per line, with the Orion crate
  that binds it), one `[does-not-build <triple>]` list per OS (first error), and one `[not-yet <triple>]`
  list per OS (the PR that is to make the crate build).
- `scripts/check-portable.py`: the logic. It reads `cargo metadata`, derives the Orion-bound set and
  checks it against the list in both directions. Its verdict mode reads cargo's log and passes or
  fails each portable crate.
- `scripts/check-portable.sh <target-triple>`: runs `cargo check --locked --keep-going --target <triple>
  --lib --bins --tests` for exactly the portable crates. `--classify` runs only the list check (any
  host). Every run prints each skipped crate and why.
- `scripts/gate.sh`: runs `--classify` (the mechanical part that needs no target).
- `.github/workflows/next.yml`: a `portable` job on `windows-latest` (`x86_64-pc-windows-msvc`) and on
  `macos-latest` (`aarch64-apple-darwin`), native, with Rust and Python set up and the cargo cache.
  The existing `gate` job is unchanged.

## How the Orion-bound set is derived

Mechanically from the locked graph, not by hand:

- An Orion crate is **Linux-only** when its `lib.rs` has a crate-level `#![cfg(target_os = "linux")]`.
  The 16 Linux-only crates at the lock are `orion`, `orion-broker`, `orion-broker-buffers`,
  `orion-broker-proxy`, `orion-comm-app`, `orion-connect`, `orion-hello`, `orion-link-serial`,
  `orion-nt4-gateway`, `orion-outbound`, `orion-stubs`, `orion-tcp`, `orion-time`, `orion-topics`,
  `orion-unix`, `orion-ws`.
- An Atlas crate is **Orion-bound** when a dependency path (normal, build or dev) from it reaches one.
  All Orion edges in the locked graph are unconditional (no `target.'cfg(...)'`), so the set does not
  depend on the target triple.

Note on the brief's example list: at this lock `orion-config`, `orion-wire` and the `orion-msg-*`
crates have no crate-level Linux gate and reach no Linux-only crate, so they are portable and are not
on the exception list. `orion-nt4` has no crate-level gate either, but it reaches `orion-ws` through a
normal dependency, so `atlas-nt` is Orion-bound. Its `net` module is itself gated; whether `atlas-nt`
would compile on Windows without `orion-ws` is not checked here.

Both are on D18's branch (`pr/D18`), where the disk writer goes behind a platform seam. They are
not fixed in this PR: the fixes that were tried here were reverted at the coordinator's request.
A crate that starts to build while excused fails the check until its entry is removed.

The exception list shrinks in one place: `scripts/orion-bound.txt`. The check fails when an entry no
longer reaches a Linux-only Orion crate (b), and when a portable crate gains such a dependency (c).
Negative tests run in this PR: a portable crate listed as bound fails (b); an unlisted bound crate fails
(c); an unknown name fails.

## What CI proves on each OS

- The portable crates compile on Windows (`x86_64-pc-windows-msvc`) and macOS (`aarch64-apple-darwin`)
  natively: lib, bins and tests, compiled and not run.
- The Orion-bound crates are skipped on every run and printed with their binding.
- Nothing runs against hardware. No test is executed on Windows or macOS.

## Findings (portability review, read-only except where noted)

Each finding is a file and line at `9ed108a6`.

1. `crates/tools/helper/src/main.rs:497`: `std::os::unix::fs::symlink` in an ungated test. Breaks
   `cargo check --tests` on Windows (first native error: `cannot find unix in os`). Excused for D18.
   Tried here and reverted at the coordinator's request; the shape of the fix is a per-OS link shim.
2. `crates/flash/disk/tests/common/mod.rs:8`, `:92`, `:100`: `FileTarget` uses `write_all_at` and
   `read_exact_at` from `std::os::unix::fs::FileExt`. `xz_stream.rs:10` includes this module without a
   cfg gate, so atlas-disk's test target breaks on Windows (3 errors; the library builds). Excused for
   D18. Tried here and reverted; the shape of the fix is seek-then-write (the same bytes at the same
   offsets), which passed every atlas-disk test binary on Linux.
3. `crates/flash/disk/src/lib.rs:16-18` and `:30-32`, `unsupported.rs:10`: disk discovery and writing
   are Linux-only today; the other platforms return `DiskError::Unsupported` ("only available on Linux
   so far"). Honest, not silent. The non-Linux writer is D18's work and is not touched here.
4. `crates/flash/disk/src/disk.rs:15`, `:63`, `:110`: the system-tree list (`/boot`, `/efi`, `/usr`,
   `/var`, `/home`) and `device_path` (`/dev/...` only) are Unix path rules in portable code. On Windows
   and macOS the helper refuses every device, which is the honest outcome until D18. Left for D18.
5. `crates/flash/disk/tests/write.rs:4` and `resume.rs:6` are `#![cfg(unix)]`. They are the write-path
   tests; they stay gated until D18 gives the non-Linux backend something to test.
6. `crates/core/inventory/src/persist.rs:277-285`: `sync_dir` is a no-op off Unix (a directory cannot
   be opened and fsynced the same way). Renames are not made durable by an explicit directory sync on
   Windows. This is the one durability difference between platforms. Not fixed; the behaviour is the
   OS's, so noted here for the store's review.
7. External tools run only in tests: `crates/flash/fel/src/thunk.rs:221-271` (inside `mod tests` at
   `:200`: objcopy, nm, clang, an assembler), `crates/flash/image/tests/common/mod.rs:197`, `:249` (xz,
   mke2fs), `crates/flash/disk/tests/common/mod.rs:114` (xz), `crates/core/bundle/tests/veritysetup.rs:32`,
   `:93` (veritysetup). They compile everywhere and need the Linux tools to run. No product code shells
   out.
8. `crates/core/release/src/catalog.rs:153` `safe_file_name` keeps only ASCII alphanumerics, `.`, `-`
   and `_`. Cache file names are therefore valid on Windows (no `:`, `*` or `?`). Correct as written.
9. `crates/core/catalog/src/load.rs:445`: `replace('\\', "/")` normalises a path to forward slashes. Fine
   on Windows.
10. `crates/flash/usb` uses `nusb` 0.2.7 (WinUSB on Windows, IOKit on macOS). The crate compiles
    everywhere; that a device opens and enumerates on either OS is unproven.
11. `crates/core/bundle/src/write.rs:234`, `crates/testing/sim-node/src/bundle.rs:355`: tar header
    modes. Tar stores modes; no filesystem mode is set. Fine.
12. No app data directory is in the workspace yet (`apps/` is not a member), so there is no code to
    review for the platform data directory. Nothing in the portable crates reads `HOME`, `XDG_*` or
    `/run`.

## Still unproven on Windows and macOS

- Running anything: no test is executed there, and no USB, disk, or board code is exercised.
- The liblzma static build (`xz2` with `static`, through `cc`) compiles on Windows MSVC only if CI says
  so; the job result is the evidence.
- `nix` (under `cfg(unix)` in `atlas-disk`) compiles on macOS only if CI says so.
- The disk writer's non-Linux backend is `Unsupported` by design; writing a disk on Windows or macOS
  is not built here (D18).

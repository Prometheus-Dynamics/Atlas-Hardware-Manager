# B16: Each family's kernel trimmed to what its boards use, stripping on, and dtbs built with symbols

**Group:** B. Board descriptions

**Wave:** 5

**Needs:** B2, B3, B14 (merged); Lemnos `4c6678f3` for `docs/kernel-config.md` (read at that rev, not locked)

Read `AGENTS.md` and `docs/design.md` first.

## Why

Gaia measured the ZERO 3E OS build: the kernel is half of it (1,608 of 3,170 s), built from an untrimmed
arm64 default config, giving a 43 MB `Image`. The bring-up image is 798 MB raw, 189 MB `.xz`, with the
kernel present twice (see "For Gaia"). The standing rule is lean, stripped installs with before and after
sizes. Trimming each family's kernel to what its boards use is Atlas's job, and it pays in build time and size.

## The RK35xx trim (`families/rk35xx/assets/trim.fragment`)

Every line says why it is here in the file. Groups:

- **Other SoC vendors' platforms** (`ARCH_*` except `ARCH_ROCKCHIP`): their clocks, pinctrl, PHYs and drivers go with them.
- **Virtualization** (`VIRTUALIZATION`, `KVM`) and **server NICs** (Intel, Mellanox, Broadcom, Cavium): no board runs them.
- **Wireless and Bluetooth** (`WLAN`, `BT`): no board has them built in. An M.2 module is a later board choice.
- **USB audio** (`SND_USB_AUDIO`), **filesystems** no product mounts (`OVERLAY_FS` off, as the Raze's trim: Lemnos
  refuses layered manifests), `NFS_FS`, `FUSE_FS`, `BTRFS_FS`, `CIFS`, the NXP TDA998x DRM bridge.
- **Debug information and kallsyms**: `CONFIG_DEBUG_INFO_NONE=y` (the defconfig has `DEBUG_INFO=y`), `KALLSYMS_ALL`,
  `KPROBES`, `FTRACE` off. Oopses still name functions.
- **USB gadget functions**: after B14 made `USB_CONFIGFS=y`, every configfs function the defconfig asks for
  takes effect. Kept: FunctionFS (Orion's link), NCM (the board's network function), ACM (the serial console).
  Everything else is off, and so are the legacy `USB_G_*` and `USB_MASS_STORAGE` modules. `USB_ETH` stays,
  set by the ZERO 3E's own fragment for its bring-up's single ECM function; no other legacy module is needed by any
  pending product (`devices/pending/` has the ZERO 3E and cubie bring-ups, which use ECM).
- **Built in for the slot**: `BLK_DEV_DM`, `DM_BUFIO`, `DM_VERITY` set `=y`. The arm64 defconfig leaves dm-verity
  off, and Lemnos's slot initramfs needs it (`docs/slots.md`: "The kernel needs ... loop and dm-verity").

the reference SoC's config (its table), and B14's `=y` lines for the three are what the Raze needs for the flasher.

`PCI_MSI=y` and `MFD_RP1=y` both come out `=y`, with no line of ours for `PCI_MSI`. So the bcm2712 fragment sets only
`MFD_RP1=y`, as a guard, and this PR does not claim a `PCI_MSI` fix.

## The ZERO 3E, ROCK 5C and ROCK 4D device trees (enabled nodes only)

Method: `dtc -I dtb -O dts` of each board's built dtb, keeping only nodes whose status is absent or `"okay"` with
every ancestor enabled. Each compatible of those nodes is mapped to the source that binds it, and that source's
Kconfig symbol, read in the trimmed config.

- ZERO 3E (the gadget variant, compiled from the gadget DTS with the in-tree `rockchip/` directory on the
  include path): enabled-node drivers all on. The `absent` symbols the mapper prints belong to other platforms'
  glue (`USB_DWC3_IMX8MP`, `_MESON_G12A`, etc.), not the bound driver. `rockchip,rk817` binds `MFD_RK8XX_I2C=y`.
- ROCK 5C: one enabled node had its driver off, `verisilicon,iommu-1.2` (`VSI_IOMMU`, the av1 decoder's IOMMU).
  Its driver is off in the defconfig too, so this is the board's own need, not a trim regression. It is set in
  `boards/radxa-rock-5c/assets/linux.fragment`. The av1 VPU itself is `rockchip,rk3588-av1-vpu` on
  `hantro-vpu`, `VIDEO_HANTRO=m` (on).
- ROCK 4D (enabled nodes, 60 compatibles, mapped in the trimmed config): every bound driver is on. `=y`: GPIO and
  pinctrl, the RK3576 gmac (`DWMAC_ROCKCHIP`), the PCIe host (`PCIE_ROCKCHIP_DW`, via the `rockchip,rk3568-pcie`
  fallback), the DW MMC (`MMC_DW_ROCKCHIP`), the USB2 PHY (`PHY_ROCKCHIP_INNO_USB2`), the combo PHY, DWC3, and the
  UART (`SERIAL_8250_DW`, via `snps,dw-apb-uart`). `=m`: the HDPTX and USBDP PHYs, the SFC. Compatibles marked
  "no symbol" are either syscon (grf) nodes or RK3576 strings that bind through a fallback above (`rockchip,rk3399-i2c`
  to `I2C_RK3X`). `snps,dwc3`'s other platform symbols are absent: they are other SoCs' glue. Resolved config:
  `=y` 1959, `=m` 737.

## Stripping

Under allnoconfig, a bool's default does not apply. Buildroot's `BR2_STRIP_strip` (`config BR2_STRIP_strip`,
`default y`, `depends on BR2_BINFMT_ELF`) is off unless set, and `BR2_BINFMT_ELF` is a choice member whose
default follows the MMU. Both are now set explicitly in each base product's OS fragment (the four products have no
shared OS layer). `INSTALL_MOD_STRIP=1` follows `BR2_STRIP_strip` in `linux/linux.mk`, so the kernel's modules
are stripped too. Measured sizes in the table below.

Not changed, candidates: the Raze's kernel debug information (`DEBUG_INFO` in its defconfig, not checked
against a Raze config here); kernel image compression (`BR2_LINUX_KERNEL_IMAGEGZ` exists in Buildroot's
`linux/Config.in` at `679b9ead`). U-Boot's `booti` path loads the uncompressed `Image`; whether a
pinned U-Boot's distro boot takes `Image.gz` was not verified. Left as `Image`.

## The slot root chain (must be built in to reach a slot's root)

Why: `lemnos-slot-init` opens a slot's root (EROFS under dm-verity) from its initramfs, before any root
filesystem with `/lib/modules` exists. Lemnos's loader for the dm modules (`service/slot-init/src/sys.rs`,
`load_module`, at `4a2d3b7d`) reads `/lib/modules/<release>/modules.dep` from the initramfs, and our products
have no initramfs that carries modules (no product names an initramfs input). So every symbol on the chain must
be `=y` on each slot-booting family, and no board fragment may turn one into `=m`. Lemnos is also removing that
loader, so a module here would stop booting a slot altogether. The check that keeps this true is in
`scripts/check-devices.sh` (`slot_chain_check`, below).

Resolved values, from a `merge_config.sh -m` run with the final fragments and `olddefconfig` (the proof, per board;
the check script reads the fragments, this table reads the resolved configs):

| Symbol | Raze (`53679a5`, 7.2.9) | ZERO 3E (7.3.3) | ROCK 5C (7.3.3) | ROCK 4D (7.3.3) |
|---|---|---|---|---|
| `BLK_DEV_DM` | y | y | y | y |
| `DM_BUFIO` | y | y | y | y |
| `DM_VERITY` | y | y | y | y |
| `BLK_DEV_LOOP` | y | y | y | y |
| `EROFS_FS` | y | y | y | y |
| `EXT4_FS` (data partition) | y | y | y | y |
| `CRYPTO_SHA256` (dm-verity's sha256) | y | y | y | y |
| storage host | `MMC_SDHCI_BRCMSTB` y (eMMC), `MMC_BCM2835` y (SD) | `MMC_DW_ROCKCHIP` y | `MMC_DW_ROCKCHIP` y | `MMC_DW_ROCKCHIP` y |

The sha256 symbol is `CRYPTO_SHA256` on every family (the verity table names `sha256`). The storage host is the
controller of the root and data partitions: on the Raze, the CM5's eMMC host (`MMC_SDHCI_BRCMSTB`) and the SD host
(`MMC_BCM2835`); on the RK35xx boards, the DW MMC host (`MMC_DW_ROCKCHIP`). Each of the RK35xx resolved
configs has every requested line in effect (127, 128 and 130 lines).

Conflicting `=m` lines removed: `CONFIG_BLK_DEV_DM=m`, `CONFIG_DM_BUFIO=m`, `CONFIG_DM_VERITY=m` in
`boards/raze/kernel/raze.config` (they were dev's "dm as modules" for an initramfs that Gaia cannot fill).
The bcm2712 family fragment now sets them `=y`, with `BLK_DEV_LOOP`, `EROFS_FS`, `EXT4_FS`, `CRYPTO_SHA256` and
`MMC_SDHCI_BRCMSTB` (the Raze) and the RK35xx family fragment sets the same chain with `MMC_DW_ROCKCHIP`.

sun60i: not a slot family today (no product uses its board with a slot recipe), so the check does not require it.
When sun60i becomes a slot board, the same chain must be `=y` in its family fragments, and `scripts/check-devices.sh`
will refuse it until they are.

## Raze: pstore is required (board fact)

The Raze keeps pstore: required. There is no wired console until Gaia can mask a unit, so the early boot's log
and the previous boot's log live in pstore. The kernel side is built in (`raze.config`: `PSTORE=y`,
`PSTORE_RAM=y`, `PSTORE_CONSOLE=y`, `PSTORE_PMSG=y`; the resolved Raze config has all four `=y`). The reserved
memory node that `ramoops` needs is supplied by the Pi firmware overlay `ramoops-pi5`: the pinned tree's
`arch/arm64/boot/dts/overlays/ramoops-pi5-overlay.dts` adds `ramoops@b000000` (reg 0x0b000000, 64 KiB) and it is
in the product's firmware overlay list (`products/raze-base/os/raze.fragment`). The config.txt line is
`dtoverlay=ramoops-pi5,total-size=0x40000,record-size=0x10000,console-size=0x20000`
(`boards/raze/boot/raze-device.txt`). Nothing missing that we add: the node is the firmware overlay's, not a
hand-written dts, and the address is the overlay's default, not ours. What is NOT verified here: that the
firmware release pinned at `1.20260915` ships `ramoops-pi5.dtbo`, and that Gaia's OS config.txt includes
`raze-device.txt` at boot (both are checks on the board).

## RK35xx: ramoops

None of the three RK35xx trees (ZERO 3E, ROCK 5C, ROCK 4D) has a `ramoops` node: the only `ramoops` in
`arch/arm64/boot/dts/rockchip/` is another board's (`rk3566-lckfb-tspi.dts`). Their resolved `PSTORE=y`,

## Checks

`scripts/check-devices.sh` now runs `slot_chain_check` on every run. It is a textual check of the fragments, not of a
resolved config (the script has no kernel tree): on each family that a slot-recipe product (`sd-image` or `slot`)
boots through (bcm2712 and rk35xx today; the family list is read from the products, not hard-coded), every
symbol of `SLOT_CHAIN` must be `=y` in the family's kernel fragments, and no family or board kernel fragment may
set one of them to `=m` or `# ... is not set`. A failure names the file, the symbol and the value found, and says
why in one line.

Negative test (`slot_chain_self_test`, run by the default self-check): on a scratch copy of `devices/`, a line
`CONFIG_DM_VERITY=m` added to the Raze's `raze.config` must fail, and the removal of `CONFIG_EXT4_FS=y` from the
RK35xx fragment must fail. Both were also run by hand, with their messages: each named the file, the symbol and the
value. The real tree passes.

## For Gaia

Duplicate Image (Gaia at `aa987cc`):

- `recipes/sd-image.toml`, line 53: `build = ["root.tree", "erofs.tree"]`. The rootfs ext4 and the root slot
  (`erofs.tree`) are built from the same tree, so `/boot/Image` is in both the rootfs and the slot file on the data
  partition. The bring-up boots the rootfs copy (extlinux `kernel /boot/Image`). The slot boot takes the kernel from
  the boot partition's slot directory, so the copy inside the slot EROFS is one nothing boots from.
- What should change, in Gaia: the slot's EROFS tree must not carry the kernel (the kernel is an input of the slot
  boot, not part of its root). A recipe that builds `erofs.tree` from the OS tree minus `boot/` (or takes the kernel
  out of the tree at the slot step) removes the duplicate. Atlas cannot do this: the slot and the rootfs share one tree
  in Gaia.
- Where the kernel enters the tree: Buildroot's `BR2_LINUX_KERNEL_INSTALL_TARGET` (`linux/linux.mk`
  `LINUX_INSTALL_KERNEL_IMAGE_TO_TARGET`). Gaia's `examples/products/zero-3e-demo/os.fragment` line 23 sets it.
  Atlas's three RK35xx bring-up products now set it too (before: no `/boot/Image` in their rootfs).
- `recipes/sd-image.toml` comment (lines 6-8): "the kernel ... is a component's to install". That
  says the kernel comes from a component; the working path is `INSTALL_TARGET`. One of the two is stale.

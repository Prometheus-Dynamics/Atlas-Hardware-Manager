## Build

- `slot.json` schema 3 carries `verity.root_hash`, `verity.salt` (hex, may be empty), `verity.data_blocks` and `verity.hash_offset`. Fixed by convention and not in the manifest: format 1, sha256, 4096-byte data and hash blocks, no verity superblock, the hash tree appended right after the data. So `hash_offset` is `data_blocks` times 4096 and `image.size` is `hash_offset` plus the tree's size; both are checked.
- The image reader returns those four values from `slots/<id>.json`, and the bundle's source takes them, so a bundle is made from a first-flash image in one call and the root hash is recomputed from the data and the salt and compared.
- Signing protects install, not boot: the names and docs here never call a signed slot "verified boot".

## Proof

Tests: a bundle from a test image in one call; a wrong salt, block count or offset is refused; the computed root equals `veritysetup format --no-superblock` on the same data and salt (run it where the tool exists, and say if it was not run).

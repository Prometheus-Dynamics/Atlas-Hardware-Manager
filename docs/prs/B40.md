# B40: raze-base takes dev's lzma options and an explicit BusyBox

Data only: `devices/products/raze-base/` (product.toml, os/raze.fragment, the new os/busybox.config) and this file.
Nothing else is touched. The two coordinator rulings of 2026-11-14 are below; where a ruling's stated fact did not
hold on the tree, it is said here.

## Ruling 1: compression. Dev's lzma options become the product's settings

`[images.settings]` keeps `compression = "lzma"` and adds the five slot-boot parameters, each with its reason
written in the settings comment block of product.toml:

| setting | value | reason (short) |
|---|---|---|
| level | 6 | lzma level of the measured row |
| dictsize | 2097152 | lzma dictionary, 2 MiB, same row |
| cluster | 1048576 | compressed cluster, 1 MiB (a multiple of 4096), same row |
| fragments | true | `mkfs.erofs -Efragments`, same row; kernel 6.1+ |
| ztailpacking | true | `mkfs.erofs -Eztailpacking`, same row; kernel 5.17+ |

The measured row (Gaia's build from Atlas f8e7a2c6, as the ruling states): EROFS root 18,178,048 bytes with these
options, 26,841,088 with lzma defaults, 38,621,184 with lz4hc; dev's root was 39,817,216. I did not re-measure.

Kernel check, against the tree as it is:
- The Raze kernel is `raspberrypi/linux` at 53679a5, branch rpi-7.2.y, Linux 7.2.9 (devices/families/bcm2712/family.toml).
  The ruling said 6.12; that is wrong for this tree. Both floors (6.1 for fragments, 5.17 for ztailpacking) are met either way.
- devices/boards/raze/kernel/raze.config has `CONFIG_EROFS_FS_ZIP=y` and `CONFIG_EROFS_FS_ZIP_LZMA=y`, the lzma decoder.
- `scripts/check-devices.sh` reads the product's plan and checks its erofs compression against the kernel lines
  (`erofs_rule`): it prints the lzma NOTE and does not fail for raze-base (see the output below).
- NOT checked: the kernel's own limit on the lzma dictionary size. No kernel tree is on this machine (the Gaia store
  has none). The 2 MiB dictionary is held by one stream per CPU up to 4 streams (raze.config), so up to 8 MiB of
  dictionary while the image is mounted. The board measurement decides whether these stay a fixed set.

## Ruling 2: BusyBox. An explicit applet list, nothing setuid

### How the config reaches Buildroot

- Gaia's fragment text: a line `BR2_PACKAGE_BUSYBOX_CONFIG="@here@/busybox.config"`. Gaia's `plan.here`
  (crates/core/graph/src/os.rs, `fn here`) turns `@here@/<file>` into an input file tree, `@files.N@/busybox.config`,
  and `os-buildroot/src/lib.rs:252` substitutes the store path into the fragment text before Buildroot sees it.
  `busybox.mk` takes that name as `BUSYBOX_CONFIG_FILE` (`BR2_PACKAGE_BUSYBOX_CONFIG`).
- Why this form and not `BR2_PACKAGE_BUSYBOX_CONFIG_FRAGMENT_FILES`: the default config resolves to 280 applets, and a
  fragment on top of it would still start from that default. A full file starts from a known set; Gaia's
  `not_taken` check (os-buildroot/src/config.rs) still tests that the fragment line survives.
- The file is Buildroot's own default (package/busybox/busybox.config, BusyBox 1.38.0 from the pinned Buildroot tree
  `d5180309`) resolved as Buildroot does (`yes "" | make oldconfig`), then with every applet not in the table switched
  off, `CONFIG_FEATURE_SUID` off, and resolved again. The BusyBox source is the tarball in Gaia's download cache, sha256
  34f9ea6f... checked against package/busybox/busybox.hash. The applet names were mapped to CONFIG symbols from the
  source's `//applet:` lines (a script in the scratch directory, not in the repo).
- Verified: the final file enables exactly the 39 names in the table, and no others (set comparison, scratch tool).

### Set-uid

- `CONFIG_FEATURE_SUID` is off in the file. None of the 39 needs set-uid to work for root on the console (login runs as
  root from agetty).
- BUT Buildroot 2026.08's busybox.mk installs `/bin/busybox` as mode 4755 whatever the config says: its
  `BUSYBOX_PERMISSIONS` is `/bin/busybox f 4755 0 0` in the non-individual branch, with no condition on
  CONFIG_FEATURE_SUID (package/busybox/busybox.mk, read in the Buildroot tree of the store, `d5180309`). The
  ruling's premise (that it is setuid "when the config has CONFIG_FEATURE_SUID") does not hold for this pin.
- The built root confirms the mode on the default build: `usr/bin/busybox` and `bin/busybox` are `-rwsr-xr-x` in the
  store tree `35/355b120a...` (858,560 bytes).
- So: with this config, /bin/busybox is still set-uid root. The requirement "not installed setuid" is NOT met by the
  config alone. The only Buildroot switch that changes the table is BR2_PACKAGE_BUSYBOX_INDIVIDUAL_BINARIES (each applet
  its own file, linked to libbusybox.so). In that mode the table lists 12 set-uid applets, and ping is one of ours,
  so it would still need a decision. That is a different image layout, not a config line, so it is NOT made in this
  PR. Decision for the coordinator.

## Open doubts (read these first)

1. **Console login: resolved by the coordinator's ruling (a).** `serial-getty@ttyGS0.service` runs `/sbin/agetty`
   (util-linux, 113,720 bytes in the built root), and agetty execs `/bin/login` by default (its strings). `login` is
   kept as the one BusyBox login: it runs as root from agetty, needs no set-uid, and there is no autologin. `su` and
   `passwd` stay out.
2. **/bin/busybox stays set-uid: finding, not fixed here (ruling (b)).** busybox.mk sets 4755 unconditionally in the
   single-binary build at Buildroot 2026.08. Gaia will strip set-uid/setgid bits when it makes a slot root unless the
   product lists the file; the coordinator is briefing Gaia. B40 does not wait for it and does not change the build
   mode. The next build's size report states whether the bit survived.
3. **/etc/profile EDITOR: resolved by ruling (c).** The profile is Buildroot's skeleton (system/skeleton/etc/profile).
   Buildroot has no option for EDITOR, and a component file cannot override it (Gaia's merge refuses two claims on one
   path). The fix is `BR2_ROOTFS_OVERLAY="@here@/overlay"` with os/overlay/etc/profile = the skeleton's profile minus
   the EDITOR line (PATH written out). The overlay is copied over the root filesystem after the install.
4. **Kernel version**: the ruling said 6.12; the tree says Linux 7.2.9 (rpi-7.2.y, 53679a5). Floors are met either way.
5. **lzma dictionary limit in the kernel** is not checked (no kernel tree here).
6. **Size** is not measured: one real build at a time, Gaia runs it (the measurement list is above).
7. **The gate**: not run locally (every slot is busy, per the brief). The CI `gate` check on this push is the gate.
8. **check-config-only** proves the BusyBox lines are taken (Gaia's `not_taken`), not that BusyBox builds or boots.

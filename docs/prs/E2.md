## Build

Decided 2026-11-13 (coordinator's ruling): the gateway's USB-boot agent is ATLAS's, an Orion provider program. Not a
Lemnos driver (the first gateway, a SystemCore, has no Lemnos and is never reflashed by us) and not Orion's (Orion moves
bytes and knows no boot ROM protocol). The loader crates of D1-D5 and D10-D13 run on the gateway unchanged: one
implementation, on the PC and on the gateway, talking to USB through `nusb`.

- `crates/tools/gateway` (binary `atlas-gateway`): connects to the local Orion node and
  1. publishes each board it sees in USB boot or maskrom as a resource: family, serial, and the gateway's port path. A
     resource appears and disappears with hotplug.
  2. serves `flash` as a DETACHED action with a deadline. It takes a pushed file by its digest (Orion files: `push_file`
     with `Transfer.digest`) and the family's boot files, streams progress, and its result is readable after a
     reconnect. The flash goes on when the app closes or the link drops.
  3. holds nothing else: no HTTP, no SSH, and no state beyond pushed files in a cache with a stated bound.
  It uses only Orion's guaranteed update-path calls (connect, file push, a detached run with a deadline, progress and
  result after a reconnect), so any newer app can drive any older gateway.
- `crates/drivers/controller`: Atlas finds a controller and offers to install its package: the Orion node and
  `atlas-gateway` as one `.ipk`, built by Gaia, installed with the controller's own package install. It shows what is
  installed and its version, updates it, and removes it. dev's USB agent and its HTTP port (:5809) do not come over;
  the package replaces them.
- On one of our own boards acting as a gateway, `atlas-gateway` is a component in the image.

Needs from others (asked through the coordinator): Orion: resources that appear and disappear at run time from a
provider, and the file cache's bounds and eviction as seen by a provider. Gaia: the `.ipk` recipe.

## The bar (user, 2026-11-13): nobody touches a board

The user had to handle three boards by hand in one day and asked whether `next` is on par, so that everything is done
through Atlas. This is the bar for `next` going onto any bench board. Every PR in D6, E2, E3 and F8 is accepted against
it, and the simulated node and bus prove each point:

1. From the PC, one command each, no SSH, no manual copy, no port argument:
   - list every board, including one in USB boot or maskrom behind a gateway, with its gateway path;
   - flash one (`atlas flash --image X` with exactly one such board anywhere just flashes it; `--device` picks among
     several);
   - restart a RUNNING board into USB boot remotely (the board's `usb-boot` action), so a reflash never needs the boot
     button;
   - install, trial and roll back a slot;
   - read why the last boot ended.
2. A board that fails to boot a slot returns to the previous one by itself. A board with no bootable slot enters USB
   boot or recovery by itself and does not sit dead. Per family, what the image must set and whether it is achievable
   is stated in D6 (BCM2712: the boot order falls through to USB boot; RK35xx: the boot ROM's maskrom when no valid
   loader is found; A733: FEL). A family that cannot meet it is named, not hidden.
3. `atlas doctor` reports boards in USB boot or maskrom behind gateways as well as on the PC's own USB.

## Proof

Test against a simulated controller: the simulated USB bus on the gateway side, the simulated node between; a board
plugged in and unplugged appears and disappears as a resource; a flash started and the client gone still ends and its
result is read by the next session. Real controller in G2.

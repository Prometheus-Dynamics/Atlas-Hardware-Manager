# T7: a refresh's answers belong to the refresh, so a failed refresh asks only what it still owes

DEBT. The test `a_board_that_refuses_describe_shows_its_devices_as_not_available_until_a_refresh`
(crates/board/topics/tests/hardware.rs) failed in another PR's gate at load ~150:
"one ask on the refresh, left: 4, right: 3".

## Cause (reproduced, and it is product code, not load)

A manual refresh sets a flag that makes the next read ask every device again. If that read failed
part way through (a session failure after some asks), the flag was re-armed, and the retry cleared
every answer and asked all devices again, including the ones that had already answered. The comment
"a read that failed asked for nothing" was wrong: the asks happened.

Reproduced by a scratch injection of one session failure right after the refresh's asks: the
refused-describe test then failed with exactly the gate's message (left 4, right 3). The uninjected
trace shows the two pre-refresh asks happen in the first reads, before the test's baseline, so the
brief's late-generation-sample hypothesis does not produce this failure.

## Fix

- The refresh is its own record (`describe::Refresh`, numbered per refresh) and keeps the answer each
  device has given it. Answers belong to the refresh, not to the connection.
- A device that has answered this refresh is held, whatever the connection did since. A device is
  asked when it has not answered this refresh, or when its generation has moved.
- The refresh is complete when a read gets through with every device's answer. A newer refresh is
  never ended by an older read.
- The connection's cache follows the refresh's answers, so a completed refresh does not make the
  connection ask again.
- The false comment is replaced by the rule above.

## Sim knob (reusable)

`SimNode::drop_session_at_describe(device)`: the next `describe` of that device ends the node session
unanswered, once. The node is published again on a new session (the existing reopen path), so the
client sees a real session failure and a reconnect. Used by a new test.

## Tests

- `a_refresh_whose_session_fails_asks_again_only_the_devices_that_have_not_answered` (new): two devices
  answer the refresh, the session ends on the third's ask, and it reconnects. The two answered devices
  are not asked again; the third is asked once; no ask on a timer after. Run against the old product code:
  fails with `bare0 answered before the session failed: not asked again, left 4, right 3`.
- `a_board_that_refuses_describe_shows_its_devices_as_not_available_until_a_refresh` (existing): keeps
  its exact count of 3. Passes with the fix.
- Scope note: the brief's case 1 (a failure with no reconnect) is not a separate test. The sim knob
  always reconnects, because a failed session is what the product sees; the in-refresh record is what
  makes the count hold either way.

## Runs

- Full topics test file, 25 runs under the machine's load (load about 165 to 240 during the runs):
  20 passed, 5 failed at the post-refresh check (4 vs 3). Cause: the refresh's answer was not written
  back to the connection cache. Fixed (the connection now follows the refresh's answers).
- Full topics test file, 30 runs after that fix (load about 165 to 180): 27 passed, 3 failed, in tests
  this PR does not touch: `a_board_that_refuses...` (asked 4, expected 1 to 2 at connect),
  `a_description_is_asked_once...` (asked 2 at connect, expected 1), `a_device_that_comes_back_from_off...`.
  These are the connect-time generation sample race the coordinator flagged; not fixed here. Open.

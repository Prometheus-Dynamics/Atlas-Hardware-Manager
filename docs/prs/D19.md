# D19: atlas-rpiboot boots a real BCM2712

**Group:** D. Flashing

**Needs:** D2

**Runs:** simulated ROM here; one board step on Raze #2 when the user is up

Every flash of a Raze on 2026-11-22 used Raspberry Pi's `rpiboot` (usbboot 20251209~095558, faf4fb9d). `atlas-rpiboot`
(D2) has passed only against the simulated bus and has never booted a BCM2712. AGENTS.md says "Loaders are our own Rust,
no vendor tools", and all of D6 stands on this loader. So it is its own item, and it comes first.

## Build

1. **Replay the real request logs.** Two verbose logs from Raze #2's second stage are the reference, kept in the bench
   session directory:
   - `a.log`: BAY-EXACT, `config.txt` 15 B, then `boot.img` 82837504 B, then `Done`;
   - `a0.log`: the tree form, config.txt 1702 B, default.txt 1024 B, `pieeprom.sig` missing, the bay's dtb, ...
   A simulated 2712 second stage in `crates/flash/rpiboot/tests` issues each log's GetFileSize, ReadFile and Done in the
   same order with the same names. The test asserts that atlas-rpiboot answers every size and every byte count as the
   log shows, a missing file with length 0, and ends as the log ends. The logs' request lines are copied into the test as
   data, with their source.
2. **Round one as the official tool does it on 2712.** State it from rpiboot's source at faf4fb9d, and change the crate
   where it differs:
   - the interface and OUT endpoint it claims when the device has one interface or two;
   - the second stage's file (`2712/bootcode5.bin`) and its boot message;
   - the bulk chunking;
   - the 1 s wait and the 4-byte reply;
   - how it tells the boot ROM (round one) from the second stage (round two) by the device's iSerialNumber. The log
     shows "Found serial number 4" for the file server.
3. **The lookup order.** atlas-rpiboot tries `<chip>/<name>` before `<name>`. The official tool serves round two from the
   folder's root. State whether a `2712/config.txt` beside a root `config.txt` can change what is served, and make the
   flasher's boot set unambiguous either way.

## Board step (proposed; the user's go)

Raze #2 is on its eMMC (build10). Put it in RPIBOOT, by the image's usb-boot action once Lemnos has it, or else the boot
button. Then `atlas-next usb-boot --serve-dir` with atlas-rpiboot as the server instead of the official tool, on a set
the official tool booted on 2026-11-22 (serve-A: the BAY-EXACT PM1 boot partition). PASS: the same request sequence as
a.log, and the image starts. The way back: the one-shot is spent, so the next reset boots the eMMC. Nothing is written.

## Proof

The replay tests above; the round-one comparison with rpiboot's source lines; then the board step's log beside a.log.

# D19: atlas-rpiboot boots a real BCM2712

**Group:** D. Flashing

**Needs:** D2

**Runs:** simulated ROM here; one board step on Raze #2 when the user is up

Every flash of a Raze on 2026-11-22 used Raspberry Pi's `rpiboot` (usbboot 20251209~095558, faf4fb9d). `atlas-rpiboot`
(D2) has passed only against the simulated bus and has never booted a BCM2712. AGENTS.md says "Loaders are our own Rust,
no vendor tools", and all of D6 stands on this loader. So it is its own item, and it comes first.

## Build

1. **Replay the real request logs.** Two verbose logs from Raze #2's second stage are the reference, kept in the bench
   session directory:
   - `a.log`: BAY-EXACT, `config.txt` 15 B, then `boot.img` 82837504 B, then `Done`;
   - `a0.log`: the tree form, config.txt 1702 B, default.txt 1024 B, `pieeprom.sig` missing, the bay's dtb, ...
   A simulated 2712 second stage in `crates/flash/rpiboot/tests` issues each log's GetFileSize, ReadFile and Done in the
   same order with the same names. The test asserts that atlas-rpiboot answers every size and every byte count as the
   log shows, a missing file with length 0, and ends as the log ends. The logs' request lines are copied into the test as
   data, with their source.
2. **Round one as the official tool does it on 2712.** State it from rpiboot's source at faf4fb9d, and change the crate
   where it differs:
   - the interface and OUT endpoint it claims when the device has one interface or two;
   - the second stage's file (`2712/bootcode5.bin`) and its boot message;
   - the bulk chunking;
   - the 1 s wait and the 4-byte reply;
   - how it tells the boot ROM (round one) from the second stage (round two) by the device's iSerialNumber. The log
     shows "Found serial number 4" for the file server.
3. **The lookup order.** atlas-rpiboot tries `<chip>/<name>` before `<name>`. The official tool serves round two from the
   folder's root. State whether a `2712/config.txt` beside a root `config.txt` can change what is served, and make the
   flasher's boot set unambiguous either way.

## Done here (2026-11-22, pr/D19)

The real fault was the round choice. Raze #2 enters USB boot through its EEPROM (the one-shot, or the button on a CM5 with a
bootloader), so it comes up as the bootloader's file server (`Found serial number 4` in both logs) and never asks for a second
stage. Before this change, atlas-rpiboot would have sent it the boot message as if it were the ROM.

### The lookup order

rpiboot `check_file()` with `-d`: `<dir>/2712/<name>`, then `<dir>/<name>`. atlas-rpiboot: `2712/<name>`, then
`bootfiles/2712/<name>`, then `<name>`. For a folder, both look in `2712/` first. A `2712/config.txt` beside a root
`config.txt` therefore wins in both tools, and the served config is the chip folder's. The two agree, so there is no
ambiguity between them. The rule for a flasher boot set: `2712/` holds only the second stage (`bootcode5.bin`), and every file
the board asks for sits at the top. serve-A is laid out that way. A leading `/` in a requested name (`/config.txt` in a0.log)
is trimmed by atlas-rpiboot; rpiboot joins it as `<dir>//config.txt`, and the result is the same file.

### Replay

`crates/flash/rpiboot/tests/replay.rs` holds a.log's and a0.log's request lines as data, with their sizes and missing files.
A simulated 2712 file server (iSerialNumber 4) asks them in order. The test checks every transfer against what rpiboot's
`file_server()` sends, the bytes of every file, and the events. A third test checks that indexes 0 and 3 still get the second
stage. Fail-before: with the round choice taken out, both replays fail.

## Board step (proposed; the user's go)

Raze #2 runs build10 on its eMMC. Nothing is written to the board: serve-A is served to its RAM.

1. Put it in USB boot as every flash tonight did. On the image's root console: `/tmp/vcmx` (re-pushed with
   `vcm/push.py` after the reboot) sets the one-shot, tag `0x0003808b` with value 3; then `reboot`. The board shows on
   3-4.2.1.4.4.2 as `0a5c:2712`.
2. Serve it with atlas-rpiboot in place of the official tool:
   `cargo run -p atlas-rpiboot --example serve -- 3-4.2.1.4.4.2 0a5c:2712 2712 /mnt/ssd-samsung/atlas-raze2-session/serve-A`
   Its log uses `rpiboot -v`'s words.
3. PASS: the log's GetFileSize, ReadFile and Done lines match a.log's (config.txt 15 B, boot.img 82837504 B, Done), and the
   image starts: the image console by-id `usb-1d6b_0104_a317bcbee5226d57-if03` comes back with a login.
4. The way back: the one-shot is spent, so the next `reboot` boots the eMMC (build10) again.

If it fails, the official tool on the same set is still the fallback for D6's flashing. The failure, with its log, becomes
this item's next fix.

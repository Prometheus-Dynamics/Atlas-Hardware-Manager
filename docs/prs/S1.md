## The ruling

raze-base stops hard-coding its OS version and slot id. The version and slot are computed from git by
`scripts/build-product.sh`, passed to Gaia as `--setting`, and the checks plan with a stated test value.
The coordinator ruled: write this now against Gaia c761d59 locally, and move the Gaia pin once, later, to a rev
Gaia has not sent yet.

## Where the version rule comes from

The Atlas dev scheme is `<release>-dev.<count>+<commit>`, from dev's `scripts/version.sh` and
`scripts/build-version.rs` (the same rule, one for the shell and one for the binaries' build.rs):

- `release` is `[workspace.metadata.atlas] release` in Cargo.toml. `next` had no such section, so this change
  adds it (`release = "2026.1.0"`, the same value dev has).
- `count` is `git rev-list --count HEAD`, `commit` is `git rev-parse --short=8 HEAD`.
- A tree with tracked changes is refused by `atlas_version` in `scripts/version-rule.sh`. Dev's rule has no dirty
  mark; the refusal is this change's own, because a built image would otherwise name a commit it does not hold.

The slot is `slot_id_for`, moved from `scripts/check-devices.sh` into `scripts/version-rule.sh`, which both
check-devices.sh and check-config-only.sh source, and build-product.sh too. The rule: `<product>-<version>`, every
`+` read as `-`, lowercased; Lemnos accepts `[a-z0-9._-]`, 1..64 bytes.

`slot_settings_args` emits `--setting IMAGE.version=…` and `--setting IMAGE.slot=…` for a slot-boot product. The
slot-boot recipe (c761d59, `recipes/slot-boot.toml`) declares `version` and `slot` with no default, so the product
leaves them unset and Gaia fills them. Gaia refuses a `--setting` for a name the product sets ("already sets it"),
and check-devices refuses a product that sets either (`slot_id_rule`, self-tested).

## The test value

The checks plan with `CHECK_VERSION = 2026.1.0-dev.0+check` (in `scripts/version-rule.sh`), slot
`raze-base-2026.1.0-dev.0-check`. It is a test value, not a release, and names no commit.

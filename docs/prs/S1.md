# S1: ruling 3, raze-base takes its version and slot from the rule

Branch `pr/S1`, on `next` eedb5d16. It also moves the Gaia pin b8585a0 → 498873cf (the single move).

## The ruling

raze-base stops hard-coding its OS version and slot id. The version and slot are computed from git by
`scripts/build-product.sh`, passed to Gaia as `--setting`, and the checks plan with a stated test value.
Written first against Gaia c761d59 locally; the coordinator then named the single Gaia move, 498873cf67126a4cf52f0fd4d8d88e9bbde798d0
(--setting PR 143, keep_setid PR 144, the [generate.data] placeholders PR 145), and this change carries it.

## Where the version rule comes from

The Atlas dev scheme is `<release>-dev.<count>+<commit>`, from dev's `scripts/version.sh` and
`scripts/build-version.rs` (the same rule, one for the shell and one for the binaries' build.rs):

- `release` is `[workspace.metadata.atlas] release` in Cargo.toml. `next` had no such section, so this change
  adds it (`release = "2026.1.0"`, the same value dev has).
- `count` is `git rev-list --count HEAD`, `commit` is `git rev-parse --short=8 HEAD`.
- A tree with tracked changes is refused by `atlas_version` in `scripts/version-rule.sh`, naming the changed paths:
  "commit first (a WIP commit is fine)". Dev's rule has no dirty mark. Ruled by the coordinator (2026-11-14): keep the
  refusal, no `.dirty` mark (two different images would share a name prefix, and the slot id rule would get harder).

The slot is `slot_id_for`, moved from `scripts/check-devices.sh` into `scripts/version-rule.sh`, which both
check-devices.sh and check-config-only.sh source, and build-product.sh too. The rule: `<product>-<version>`, every
`+` read as `-`, lowercased; Lemnos accepts `[a-z0-9._-]`, 1..64 bytes.

`slot_settings_args` emits `--setting IMAGE.version=…` and `--setting IMAGE.slot=…` for a slot-boot or slot-disk
product. Both recipes (498873cf, `recipes/slot-boot.toml`, `recipes/slot-disk.toml`) declare `version` and `slot` with no default, so the product
leaves them unset and Gaia fills them. Gaia refuses a `--setting` for a name the product sets ("already sets it"),
and check-devices refuses a product that sets either (`slot_id_rule`, self-tested).

## The test value

The checks plan with `CHECK_VERSION = 2026.1.0-dev.0+check` (in `scripts/version-rule.sh`), slot
`raze-base-2026.1.0-dev.0-check`. It is a test value, not a release, and names no commit.

## The Gaia pin move

- `devices/gaia.lock`: b8585a0 → 498873cf. No product lock changed (`gaia lock --check` passes for every product).
- keep_setid (PR 144) needs nothing here: raze-base lists none (busybox's bit is cleared by ruling; dbus is gone, B41).
- The [generate.data] placeholders (PR 145) are used by the slot-disk draft (PR 114), which rebases onto this.
- The raze-base product.toml header names the new pin.
- The `slot-boot`/`slot-disk` parameter names (`version`, `slot`) are Gaia's; if a later Gaia renames them,
  `slot_settings_args` changes with it.

## Checks

- `scripts/check-devices.sh` exits 0, self-check included (the slot id rule now refuses a product that sets
  version or slot, an id over 64 bytes, a bad product name, and checks the settings it hands Gaia).
- `scripts/check-config-only.sh` exits 0: every product's configuration resolves with the settings given.
- `scripts/build-product.sh raze-base --plan` prints the version and both `--setting` values, runs `gaia plan`, and
  builds nothing. It refuses a tree with tracked changes.

## Kept markers and why

- `crates/testing/sim-node/src/readings.rs` (module note and the `LOCK:` at the per-tick write): the device `status` and `generation` topics are provider topics. At `dbd5fc08` `Describing::topic` declares every topic `FromNow` and takes no argument for it, so the per-tick write stays until the provider can declare `Latest`. Orion C29 covers `TopicDecl` only.
- `crates/board/files/src/source.rs` (`push_with`): kept. The digest is known from the first attempt, so a resend could skip the hashing pass. It stays because a changed source on a resend would then fail with the board's `Rejected(digest)` instead of this guard's "source changed" refusal, a change in the error a person sees. The first attempt has no digest and must hash.
- `crates/board/access/src/carrier.rs` (terminal and operator key install) and `crates/testing/sim-node/src/access.rs`: kept. Orion has `Orion::shell` and `Orion::enroll`, but the `Carrier` trait is `Send + Sync` and blocking, while Orion's `Shell` and enrol live on the client handle, which is not `Send` and stays on the session thread. A production carrier needs a long operation on that thread (`Handle::long`) that pumps the shell and takes its input from a queue. That is Orion's and Atlas's own next PR, after this one, and this PR does not build it.
- `crates/flash/usb/src/link.rs` (F12a `LinkRead`/`LinkWrite` mirrors): unchanged, as briefed (next PR).

## App and image are on different Orion revisions

After A17, three revisions are in play:

- App (Atlas, this PR): `dbd5fc08`.
- Board node and Lemnos bridge in the image: `455a956e` (Lemnos `d6b9361d` pins it), until the Lemnos L2 move.
- Image pins under `devices/`: deliberately unchanged in A17, and the image's `orion`, `orion-recovery` and the bridge move together at L2 (one shm rev per board). These are the lines the coordinator will decide on:
  - `devices/components/orion-recovery/component.toml:11` (`ref = "455a956e…"`)
  - `devices/components/orion/component.toml:3` (comment naming the rev) and `:18` (`ref`)
  - `devices/components/orion/files/orion.conf:1` and `:23` (comments: `Orion's … (455a956)`, `Orion 455a956`)
  - `devices/products/raze-base/gaia.lock:62-63` and `:73-74` (`ref` and `commit`)

Every R2 message-body change is additive. Everything an old node has keeps working against an R2 app: `Run.on_behalf`, `Claim.session`, `Cancel.reason`, digest push, enroll, `OtherKey`, and the reconnect order (ignored by the old node or done client-side).

Four things do not work against a pre-R2 board, and how each fails today:

1. Shell (`0x80`-`0x87`) and link offers (`0x90`-`0x94`) are dropped silently by the old node, so the call ends by its own timeout.
2. A signed serial or USB link (`expect` set) fails closed (`Lost` or `TimedOut`), and never downgrades.
3. `on_subscribe = Latest` silently behaves as `FromNow`.
4. `CALLER_GONE` never arrives, so the bridge keeps its 60 s lease.

Consequence in our app, checked by reading, not run: the topic reader asks for each field's newest value immediately after it subscribes (`crates/board/topics/src/read.rs:139` calls `read_topic` for every topic of each device resource; `read_topic` calls `subscriber.latest(..)` per field at `crates/board/topics/src/read.rs:240`). Against an old node, that call finds nothing until the next write to the topic. What the person sees: a device whose values, status or description topic has not been written since the app subscribed shows those fields empty (no value, no health, no description text) until the board next publishes them. Readings are written on the board's own schedule, so they fill in at its next write. Status and description may stay empty until the board next writes them; how often a real board writes them was not checked against Lemnos in this PR. The app does not version-check, so nothing says why; that is the gap C35 closes. Whether real Lemnos topics are provider topics (which are `FromNow` on any node, so no change) was not checked against Lemnos in this PR; the change matters only where a real board declares `Latest`.

No version detection is added. The session maps connect errors to words; `ClientError::Revision{node, client}` arrives with Orion C35, and gets a `// LOCK: Orion C35` note where the session maps connect errors. (Not yet placed; it arrives with C35.)

## Hello `state` since R2 (the five failing tests)

Orion's comm core writes the hello `state` fact itself, and a program's `state` fact is dropped. Read at `fd61df3e` (`/mnt/ssd-samsung/atlas-next-scratch-A17/orion-src`):

- `crates/comm/hello/src/lib.rs:55`: `STATE_FACT = "state"`, Orion's fact.
- `crates/comm/hello/src/lib.rs:140`: a comm core starts `BoardState::Running`.
- `crates/comm/hello/src/lib.rs:175-176`: a program's topic named `state` or `recovery_why` is skipped (`continue`). This is finding (4): a provider-published `state` is silently dropped. Asked of Orion.
- `crates/comm/hello/src/lib.rs:234-238`: the identify answer writes `state` (the board's `BoardState::word()`), and `recovery_why` in recovery.
- `crates/comm/comm-app/src/recover.rs:107`: `recover(settings, why, with)` is the only way a comm core becomes `BoardState::Recovery`; `recover.rs:228` and `:237` return `Started::Recovery` when settings cannot start it.
- `crates/comm/comm-app/src/recovery_comm.rs:72`: `Hello::new(..).in_state(BoardState::Recovery(why))`.

What is missing for the simulated board to say `recovery`: the simulated node runs `orion-stubs` (`crates/testing/stubs/src/lib.rs:99-179`), which starts a plain comm core and has no path to `recover` (nothing in `crates/testing/stubs/src` names `recover`, `Started` or `InRecovery`). Running recovery needs `orion-comm-app`'s start path (settings that fail, a recovery keys file, listen addresses, `RecoverWith`), which the simulated node does not run. So the simulated board does not say `recovery` or `flasher` in this PR. Recovery is modelled the way the access crate reads it: a `Node` whose `state` fact says `recovery` (unit tests in `crates/board/access/src/kind.rs`).

Changes made for the five failing tests:

- `crates/testing/sim-node/src/node.rs`: the simulated node no longer publishes `hello.state`; `Mode` documents what the comm core really answers.
- `crates/testing/sim-node/tests/identity_facts.rs`, `a_plain_node_publishes_no_hello_facts_but_the_hello_document_still_answers`: now asserts the only fact is Orion's `state = running` (since R2 it is Orion's fact).

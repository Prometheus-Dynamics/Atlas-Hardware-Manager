# T3: one client identity per PC user, and boards with security off

Two rulings by the coordinator (2026-11-14), recorded in /mnt/ssd-samsung/atlas-next-scratch-root/INPUTS.md
("RULINGS: client identity and security-off wording"):

1. Every Atlas session today connects with a client key made fresh per monitor (`Identity::generate()`,
   crates/board/session/src/monitor.rs:577). A fresh key per run cannot be authorized by anyone. From now on there is
   ONE client identity per PC user: made once, stored with mode 0600 in the user's Atlas config directory (never in a
   repository), used by the test tool and later the app alike.
2. A board with security off proves no key (Orion: a plain session; the node's key is never seen). Then there is
   nothing to pin, and the tool says so once, quietly.

## Part 1: the identity (crate `atlas-session`, and a small new module or crate for the file)

- The file: `<config>/atlas/identity.key`, where `<config>` is `$XDG_CONFIG_HOME`, else `~/.config` on Linux; on
  macOS `~/Library/Application Support`; on Windows `%APPDATA%`. Content: the 32-byte Ed25519 secret as 64 hex and a
  newline, the same text form as the signing seed (S1). Mode 0600 on Unix, created with `create_new` in a directory
  made 0700 if missing; a file readable by group or others is refused naming its mode and `chmod 600` (as
  `atlas_bundle::Seed::read` does: read crates/core/bundle/src/seed.rs and reuse its reader and writer if the
  dependency direction allows; if it does not, say why and keep the same rules).
- `load_or_create(path) -> Identity`: reads it, or makes it once if absent; a damaged file is refused (never
  silently replaced).
- `Sessions` takes the identity: a constructor `Sessions::with_identity(pause, secret: [u8; 32])` (or an equivalent
  builder); every monitor it starts connects with THAT secret. `Sessions::new` keeps today's behaviour (fresh per
  monitor) so tests and other callers are unchanged; say in its doc comment that a real program uses the identity.
- Do not change how pins, `accepts`, or `other_key` work.

## Part 2: the tool (`crates/tools/next`)

- Every board command uses the user's identity (load or create) via the new constructor. `--identity <file>` overrides
  the path (tests use it; a test never touches the real config directory).
- New command `atlas-next identity`: prints the identity's fingerprint in the SAME text form the rest of `next`
  prints node fingerprints (Orion's), and the file's path. Creates the identity if absent and says it did.
- SECURITY OFF: find how a plain (security-off) session shows in what the tool receives (the hello `Node`, its
  `public_key`/`fingerprint`, or an Orion session fact). Read Orion's client at the pinned rev in the cargo git
  checkout (`~/.cargo/git/checkouts/orion-*/<short rev>/`, the rev in the root Cargo.toml) and the sim node
  (crates/testing/sim-node) to see whether the sim can run security-off. Then:
  - `pin` on such a board refuses with exactly: `this board runs with security off: it proves no key, so there is
    nothing to pin` (exit 1).
  - `fingerprint` says the same fact instead of a fingerprint.
  - every other board command runs unpinned on it and prints exactly ONE first line `security off: board not
    authenticated`, then its normal output. No other warning, nowhere repeated.
  - If the pinned Orion cannot tell the tool that a session was plain (no way to know), STOP that part, do the rest,
    and say exactly what is missing (file:line in Orion) in the PR text.

## Proof (mandatory)

1. `load_or_create` on a fresh path makes a 0600 file in a 0700 directory and returns the same identity on the
   second call; a 0644 file is refused; a damaged file (63 hex) is refused and left as it is.
2. Two `Sessions::with_identity` monitors with the same secret present the same client key to a sim node (prove it
   from the node side if the sim exposes the client key; else from the identity the connect uses).
3. `atlas-next identity --identity <tmp file>` prints a fingerprint and the path; a second run prints the same.
4. Security off (if the sim can run it): `pin` refuses with the exact words; `list` prints exactly one
   `security off: board not authenticated` line first. If the sim cannot, say so and what the sim lacks.
5. The existing T1/T2 tests still pass unchanged (they may pass `--identity`).

## Not in this PR

Enrolment of the client key on a board (waits on Orion's answer); the app; anything that changes a pin.

## As built

Rulings applied (coordinator, 2026-11-14, later): `pin`, `fingerprint` and `repin` work the same on every
board, security on or off. A board command on a security-off board prints one first line,
`security off: the board's key is checked, the session is not signed`. Enrolment on a security-off board says
`this board runs with security off: there is nothing to enrol`. The probe runs once per run of the tool. `enrol`
is added and the simulated board has a security switch.

- `crates/board/session`: `Sessions::with_identity(pause, secret)` and `Monitor::start_identified` (the monitor
  takes the key). `Sessions::new` and `Monitor::start_full` make a fresh key per monitor, as before. Pins,
  `accepts` and `other_key` are unchanged. A held secret prints as `Held(..)`.
- `crates/tools/next/src/identity.rs` (no new crate): the identity file at `<config>/atlas/identity.key`
  (`$XDG_CONFIG_HOME`, else `~/.config`; macOS and Windows as the brief says, not tested there). It holds 64 hex and a
  newline, mode 0600, made with `create_new` in a directory made 0700. A file readable by others is refused,
  and a damaged file is refused and left as it is. The module reads and writes the file itself, because
  `atlas-bundle::Seed` keeps its bytes private (no accessor), and that crate is not on the edit list. The
  fingerprint is `orion_identity::fingerprint`'s form (`sha256:` and 32 hex digits), written out here.
  `atlas-next identity [--identity <file>] [--json]` makes the identity if absent and prints the fingerprint and the path.
- `atlas-next enrol <address>`: needs a pin (the pin rule). Calls `Orion::enroll(public, "atlas-next", None)`
  (`crates/client/orion/src/lib.rs:343`) on a signed session that expects the pinned key. The answer is
  Pending (the sentence the brief asks for), Enrolled, or Revoked (refused, exit 1). A session the board turns
  away comes back as Orion's own `ClientError`, typed, and is printed in its words (`crates/client/connect`,
  `transport.rs:323`: `the node refused this client's key`).
- `crates/tools/next/src/link.rs`: `security()` is the single probe. It is commented with the J9 line from the
  ruling. A plain session that opens is security off. Orion's `ClientError::Denied(NEEDS_SIGNED)` (`transport.rs:287`)
  is security on. Anything else is unknown.
- The denied-key line. A board command's refusal crosses `atlas-board-slots` and `atlas-session` as a string
  (`SessionError::Failed(String)`, `crates/board/session/src/monitor.rs`), so the tool matches Orion's word
  `denied` there. That is text only. `enrol` makes its call directly and matches the variant.
- `crates/testing/sim-node`: `SimNode::start_secured(dir, kind, port)` (default `start_with` stays security off).
  `trusted(&key)`, `grant_as_root(key, name)` (the store's `approve_operator` and `grant` with every action),
  `revoke(key)`. Its actions now use `Policy::new(Admits::ROOT.and(Admits::OPERATOR))` with grants required
  (`action_policy`). With security off the check admits everything, so nothing changes for the default node.
- Tests. `tests/identity.rs`: the file (0600/0700, 0644 refused, damaged refused and kept), the `identity`
  command, the fingerprint form against the sim node's own, two sessions on one identity reaching a node, the
  security-off rules (pin and fingerprint work; `enrol` refuses; one first line). `tests/security.rs`: the four
  security-on proofs. Unit tests: the classifier, the denied word, the identity file's text. The six T1 tests in
  `tests/slots.rs` are unchanged.

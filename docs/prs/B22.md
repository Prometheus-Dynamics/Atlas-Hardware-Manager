## What changed in the checker (`scripts/check-devices.sh`)

1. **The binary must say its commit (step 3a).** `gaia --version` must print `gaia <version> (<commit>)`
   and the commit must be devices/gaia.lock's. The check dies naming both when the commit differs, when it
   ends in `-dirty`, or when the binary prints none. The self-check now runs this refusal too (two fake
   binaries: one prints another commit, one prints none; both must be refused and the refusal must name the pin).
   Checked by hand: `bin-aa987cc` and `bin-4abf626` print no commit and are refused.
2. **The plain check is offline (step 3b).** For each product: the committed `gaia.lock` must pass
   `gaia lock --check`; then `gaia lock` runs on a copy with `--tool git=/bin/false --tool curl=/bin/false`,
   so any request it would make is an error; the regenerated copy must equal the committed lock byte for byte.
   Then the product is planned with the committed lock. Only `--write-locks` asks the network.
3. **`--write-locks` starts from the committed lock.** A source the lock already holds for what its
   description says is not asked again (gaia lock's rule). The first version of this change regenerated from
   empty and hit Docker Hub's HTTP 429 for `docker.io/library/rust:1.99-slim` in six components; starting from
   the committed lock avoids it. A host that is unreachable or rate limited is retried 3 times and then is a
   FAILURE: the committed lock is left as it was, and the check fails naming the product.
4. **Named input for the bench key (step 3c).** The bench key component installs `{ input = "bench-key" }`.
   A product that names `bench-key` is planned with `--input bench-key=<temp>/key.pub`. The check makes a
   throwaway ed25519 key for each run with `ssh-keygen`, deletes the private half at once, and passes the
   `.pub`. Only products whose files name `bench-key` get the input (gaia refuses an input nothing uses).
   Nothing key-like is committed (`git grep` for key material: none).
5. **PR 48 pattern, unchanged.** The grep on `to = "..."` for `/data/`, `/var/lib/orion`, `/etc/dropbear/`,
   and any `host_key`, `node-identity` or `.ed25519` path is not loosened. The bench key installs to
   `/root/.ssh/authorized_keys`, which that pattern does not match. That is correct for an authorized_keys
   file for a dev-only bring-up (a bench key, not a host key or node identity). A bench input installed at a
   listed path would still fail. The pattern does not catch a host key given through an input to a path it
   does not list; that is a gap the pattern never covered.

## Suspected Gaia issues (verbatim, for the coordinator)

No Gaia bug was found while doing this PR. Two observations about `gaia lock` (at `f5a32f9`; the same code at `7db227f`), for the coordinator:

1. `gaia lock --check` compares a tree source only by its path, and a git source only by url and ref
   (`crates/core/lock/src/check.rs`, `Want::matches`). A branch or tag ref whose commit moved is not seen by
   `--check`, and the offline regenerated copy keeps the committed commit (a locked source is not asked again).
   The plain check therefore cannot see a moved branch; only `gaia lock --update SOURCE` (with the network)
   refreshes it. The check's directory hashes are seen (the regenerated copy re-hashes every directory).
2. Docker Hub answers `HTTP 429` for an image written by tag; the error names the fix:
   `gaia: lemnos-ctl.root: https://registry-1.docker.io/v2/library/rust/manifests/1.99-slim: HTTP 429; writing the digest in the description avoids this request: ...`
   This is a rate limit of the host, not a defect in Gaia; it is recorded because it blocked a fresh lock here.

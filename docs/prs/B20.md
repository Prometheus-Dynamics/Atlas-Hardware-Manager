### How each name is derived (`6905b681`)

- **Watchdog.** The map's `[controllers.watchdog]` path is `/soc@107c000000/watchdog@7d200000`, and Raze #2 shows the same node (`107d200000.watchdog`, INPUTS). The device names it as the form `watchdog:<node>` in its `uses` (the driver's need is `watchdog`), and the `[[hardware]]` entry is `controller = "watchdog"` with no name. The old file's `device = "watchdog0"` is the numbered form, which can change on reboot. `hw-watchdog` uses its `device` setting only when no `watchdog` name is given, so the stable name replaces it.
- **Camera I2C.** The map's `i2c10` alias is `/axi/pcie@1000120000/rp1/i2c@88000` (RP1 I2C at 0x88000), with pin set `gpio38_39` (label `rp1_i2c6_38_39`). Raze #2 shows the runtime name `i2c-10` on alias `i2c10`.
- **Camera power line.** `gpio:pinctrl-rp1:34`. The map's `[chips.rp1]` label is `pinctrl-rp1`, and the base `module-io` holds line 34 at node `/cam0_reg` (`[bases.module-io.lines]`), so the overlay disables that node.
- **UDC.** `udc:1000480000.usb`: the map's `[controllers.usb]` `sysfs` name, which Raze #2 shows in `/sys/class/udc` (INPUTS).

## Command line (`cmdline.txt`): decision

**The Gaia side has no field at `aa987cc`.** `recipes/slot.toml` and `recipes/sd-image.toml` have no command-line input and no `boot_args` parameter. The `cmdline.txt` design is F10 (`docs/prs/F10.md`: "the image's own, then `<P>.slot=<id> <P>.roothash=<hex> <P>.data=PARTUUID=<uuid> panic=5`"), and the boot partition it sits in is not in any recipe at this lock (`sd-image` has no FAT boot partition, and F12 is not built). A grep of `crates/`, `recipes/` and `docs/` at `aa987cc` finds no other place. **Missing field, reported to the coordinator:** an image-level input for the image's own command line (a string), and the slot recipe's `<P>` prefix (our `boot_args = "os"`). No file is added to the component, and no mechanism is invented.

**The intended content** (for the slot's `cmdline.txt` once Gaia has the field):

```
dhash_entries=16384 ihash_entries=8192 thash_entries=4096 uhash_entries=1024 os.slot=<id> os.roothash=<hex> os.data=PARTUUID=<uuid> panic=5
```

- The four hash sizes are dev's, measured on Raze #1 (dev's own comment: the kernel's defaults cost about 6 MB). The reason is that measurement. It is not re-measured here.
- `os.*` and `panic=5` are F10's slot arguments; `os` is the prefix, the same `boot_args` the slots device names.

**Console: none.** The line names no `console=`. Each reason:

1. `console=tty1` (dev) is impossible here: `raze-trim.config` has `# CONFIG_VT is not set`, so there is no virtual terminal, and no `getty@tty1`.
2. A UART console (`console=serial0,...`, the Pi's `ttyAMA10` on this board) would make systemd's generator start a second login on that tty (B13's rule). A mask for it needs a Gaia form, and Gaia at `aa987cc` has none (B13's open point).
3. A kernel console on the gadget's ACM (`ttyGS0`) is not possible: the gadget is built by lemnosd after boot, and a USB gadget port is not a kernel console.

So the one getty is `serial-getty@ttyGS0.service` (the existing `raze-base-files` unit, enabled). Nothing needs masking, which matches B13's rule (same tty, nothing to mask).

**Consequence for early boot messages.** There is no kernel console on any wire. Messages from before lemnosd builds the gadget and the getty starts are kept in two places: pstore (`CONFIG_PSTORE_CONSOLE=y`, ramoops console region 128 KiB, `config.txt`), which survives a reset and is read in the support bundle on the next boot, and the journal (persistent, on `/data`) once systemd-journald runs. The live signs of life are the LED ring, USB enumeration and the NCM link. Whether pstore records everything with no `console=` is not verified on a board (G1).

**Dropped from dev's line, with reasons:** `quiet` (no console to quiet, and it changes only what a console shows); `splash` (no splash program in the base OS); `rootwait` (the slot's root is in the initramfs, not a device on the line); `systemd.unified_cgroup_hierarchy=1` (no reason written for it on this image; the G1 check reads the default on the board).

**Open, not in this PR:** the getty's login policy follows the board's security setting (INPUTS, "the console on a managed board"). `raze-base-files` does not write it yet. The default (security off) is the one the policy names; the switch that changes it is not defined.

## Not in this PR (the next two changes this file needs)

1. **Indicator and LED-ring states.** The file gets a `status-indicator` device (`driver = "indicator"`, `uses = { pixels = "ring" }`) with per-state patterns, when Lemnos's indicator driver (W1, `indicator/1`) is in a rev the lock contains. The states and the approved look are in INPUTS ("LED ring look"): checking purple orbit; writing blue arc with a bright head over a faint white track; staged green; reboot static dim amber over the whole ring; trial boot white twin orbit; confirmed flash and burst, then a fill draining to the bottom; error red slow breath `ff2828`; every chase has a dim same-colour glow (base 0.18); 16 LEDs in 8 sections, radially 1,3,1,3,1,3,1,3. States without an approved look (receiving, verifying, idle) are proposed for the user to approve.
2. **The gadget drop-in pairing.** Lemnos R1d (`554319df`, after the lock): a board whose file has a `usb-gadget` device must also install `packaging/systemd/lemnosd.service.d/gadget.conf` (CAP_SYS_ADMIN, mount and umount2 in the syscall filter, configfs and FunctionFS `ReadWritePaths`). A board without a gadget must not. Our `raze-lemnos-board` component installs it exactly when the board file has the gadget: derived from the board data, not set by hand. The device check enforces the pairing both ways. Not added here: R1d is not in the lock.

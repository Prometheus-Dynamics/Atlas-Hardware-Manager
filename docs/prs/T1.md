# T1: `atlas-next slots`, the milestone's slot test tool

A small command-line program for one job: run the slot cycle on a board that runs a `next` image, from the PC,
with nothing but an Orion address. It is a test tool for milestone 2 (the first `next` image on a Raze), not the
product CLI (that is F8, parked). It adds no new board logic: every operation is a call into crates that exist.

## Where

New crate `crates/tools/next` (package `atlas-next`, binary `atlas-next`). It may depend on `atlas-session`,
`atlas-board-slots`, `atlas-slots`, `atlas-trial`, `atlas-jobs`, `atlas-files`, `atlas-types`, `atlas-log`, `orion`
and tokio. No other crate is edited. If something it needs is not public in those crates, stop that part and say so.

## Commands

    atlas-next slots <address> fingerprint
    atlas-next slots <address> pin
    atlas-next slots <address> repin --reflashed
    atlas-next slots <address> list
    atlas-next slots <address> install <bundle file>
    atlas-next slots <address> trial <slot id>
    atlas-next slots <address> confirm <slot id>
    atlas-next slots <address> remove <slot id>

Common options: `--state <dir>` (where pins and the trial follower's files live; default
`$XDG_DATA_HOME/atlas-next`, else `~/.local/share/atlas-next`), `--json` (one JSON document on stdout instead of text).

- `<address>` is what `orion::Address` parses. It must accept `127.0.0.1:9200`, `[::1]:9200` and a scoped IPv6
  literal (`[fe80::1%eth0]:9200`). Prove each by test; if Orion's `Address` refuses a form, do not work around it:
  report it in the PR text with the exact error.
- `list`: the board's slots as `BoardSlots::list` gives them (id, state words, default, trial, starred), one line each.
- `install`: submits the bundle through `SlotInstalls`, prints the stage and byte counters as they change (one line
  per change, not a spinner), ends with the installed slot's id. A refusal prints the board's words unchanged.
- `trial`: starts a trial of the slot and FOLLOWS it (`Follower`) to its end: the board restarts into the slot, the
  tool waits for it to come back, and prints the outcome in words (came back in the trial slot / came back in the
  previous slot: the trial failed / did not come back). It never gives up waiting on its own: it keeps trying on the
  session's backoff until the outcome is known or the user stops it (Ctrl-C). That is the failure-handling rule.
- `confirm`: makes the slot the default (`set_default`).
- `remove`: removes a slot; never a starred one, never the default (the board refuses; print its words).

Exit status: 0 done; 1 the board refused or the outcome is a failure; 2 usage; 3 the pin rule refused the board.

## The pin rule (coordinator's ruling, 2026-11-14)

1. FIRST CONTACT: a board (address) the tool has never seen. Every command except `fingerprint` and `pin` refuses,
   in words, showing the node's key fingerprint and naming the `pin` command. `fingerprint` only shows it. `pin`
   shows the fingerprint and records it for that address. No silent trust: nothing is pinned by any other command.
2. LATER CONTACT with the pinned key: works.
3. LATER CONTACT with a DIFFERENT key: every command refuses, in words that name BOTH fingerprints (the pinned one
   and the one that answered) and say that a reflash is the one legitimate cause.
4. `repin --reflashed` is the explicit step after a reflash: it shows both fingerprints and replaces the pin. Without
   `--reflashed` it refuses. There is never an automatic re-pin.

The session is opened with the pinned key wherever the session takes one, so a board that changes key while a
command runs is noticed by the session, not only at the start. The fingerprint's text form is the one the rest of
`next` uses for a node (see `DeviceKey::node` and where a fingerprint is made from a public key); do not invent a
second form. The pin file is plain text or JSON, one record per address, written whole to a temporary file in the
same directory and renamed.

## Proof (mandatory)

Tests in the crate, against `atlas-sim-node` (see how `crates/drivers/board-slots/tests/common/mod.rs` stands up a
simulated board and a relay), running the real binary's command functions (not a copy of them):

1. First contact: `list` refuses and prints the fingerprint; `pin` records it; `list` then lists.
2. A second simulated node with another key on the same address: `list` refuses and its words hold both
   fingerprints; `repin` without `--reflashed` refuses; `repin --reflashed` replaces; `list` works.
3. The cycle on the simulated board: `install` a bundle the sim accepts, `trial` it, the sim restarts into it,
   the tool reports the trial slot came back, `confirm` makes it default, `list` shows it default.
4. A failed trial: the sim comes back in the previous slot; `trial` says so and exits 1.
5. Address forms: IPv4, `[::1]`, a scoped literal (parse only, where no such interface can be bound).
6. A refused install (a bundle for another board id): the board's words are printed unchanged, exit 1.

Tests tolerate load (no real-time sleeps as conditions; see the `answered` helper for calls that may be slow).
Paste the output of one real run of the binary against a sim node in the PR text.

## Not in this PR

the product CLI's other commands; reading the Lemnos `job` record (L2).

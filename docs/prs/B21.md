- Q2f's rules (`docs/device-tree.md`, "VBUS of a device port"): `vbus` + `vbus_off` + `vbus_reason` (a line that switches VBUS);
  `vbus_undriven = true` + `vbus_reason` (an assertion from the schematic, checked by a meter); nothing when the base has no supply.

  `[board] base`. A port with no fact (no base, or a base that is silent) and no statement is refused.

### ZERO 3E (`devices/boards/radxa-zero-3e/lemnos-board.toml`)

- **Change:** `[board] base = "usb-no-vbus"` added. The rk3566 map's `usb-no-vbus` fact says the base's OTG port has no
  `phy-supply`. Without the line the generator refuses the port (checked below). The Lemnos testing board for the RK3566 names the same base.
- **Q2f case:** "no supply in the base tree: nothing to state". The base tree (v7.3.3 `rk3566-radxa-zero-3e.dts`, its includes)
  has no `phy-supply` on `usb2phy0_otg`, and B15/B18 found the same. The entry needs no `vbus` key.
- **Evidence:** the RK3566 OTG PHY `usb2phy0_otg` (`rk356x-base.dtsi` line 1891) has no `phy-supply`. The PMIC `vbus`
  OTG_SWITCH regulator (`rk3566-radxa-zero-3.dtsi` line 410) has no consumer, no always-on and no boot-on flag.
  Schematic V1.2.00 (`radxa_zero_3e_v1200_schematic.pdf`, from Radxa's download page): sheet 18 "Power IN": USB-C 1 (J2)
  VBUS pins go to `+5V_INPUT`, the board's input to `VCC_SYS`, so VBUS on this port comes from the host by design.
  CC1/CC2 are pulled down with 5.1 K (a sink). The OTG detect (`USB_OTG0_VBUSDET`) is a divider on `VCC_SYS`, not a driver.
- **Doubt (for the meter):** sheet 17 (PMIC RK817) has a net named `VBUS` (the charger input, through a PMOS to `VCC_SYS`).
  No sheet read connects it to J2's VBUS, and the names differ (`VBUS` vs `+5V_INPUT`). It is not connected on the sheets read.
  The meter check below settles it.
- **Validation (96080d36):**

  - `lemnos-ctl tree` (with `base`): rc 0. Overlay: `target-path = "/usb@fcc00000"` with `dr_mode = "peripheral"`, `phys = <&usb2phy0_otg>`;
    `/usb2phy@fe8a0000` `status = "okay"`; a stand-in `regulator-lemnos-no-vbus`; `/usb2phy@fe8a0000/otg-port` `phy-supply = <&lemnos_no_vbus>`.

  - Same file without `base`: `tree` rc 1: "the base (none is named by [board] base) does not describe its VBUS ... state how VBUS
    is handled". So the `base` line is the one the rule needs, and nothing else is stated.
- **Fixups (item 7):** `dtc -@ -I dts -O dtb` of the generated overlay, then `dtc -I dtb -O dts`: `__fixups__` has one label,
  `usb2phy0_otg = "/fragment@0/__overlay__:phys:0"`. Labels/paths in the base at v7.3.3 (B15 scratch, `rk356x-base.dtsi`):

### ROCK 5C (`devices/boards/radxa-rock-5c/lemnos-board.pending.toml`): complete on paper, held by Q2g

- **Entry (commented, in the pending file):** `udc:fc000000.usb`, `usb-otg0`, `role = "peripheral"`, `options = ["usb3"]`,
  `vbus = "gpio:gpio0:28"`, `vbus_off = "low"`, `vbus_reason = "..."`. No `[board] base`: no map base describes this board's tree,
  and the map's `usb-gpio-vbus` base is GPIO4 line 11, a different line, so naming it would be refused.
- **Line arithmetic:** PD4 is GPIO0 bank D (D = 3), pin 4: line = 3 × 8 + 4 = **28**. The map's chip is `gpio0` with `number_base 0`,
  so the boot-hold number is 28 (`gpio=28=op,dl`). Label form: `gpio:<chip label>:<line>`, as in the RK3588 testing board (`gpio:gpio4:11`).
- **Polarity:** `enable-active-high` on `vcc5v0_usb_otg0` (`rk3588s-rock-5c.dts`) gives `vbus_off = "low"`.
- **Evidence:** `rk3588s-rock-5c.dts` line 112: `vcc5v0_usb_otg0` is `regulator-fixed`, `enable-active-high`,
  `gpio = <&gpio0 RK_PD4 GPIO_ACTIVE_HIGH>`, no always-on, and `&u2phy0_otg { phy-supply = <&vcc5v0_usb_otg0> }` (line 908).
  Schematic V2.10 (`radxa_rock_5c_schematic_v2.10.pdf`, 25 sheets, downloaded from Radxa into scratch):
  - sheet 5 (SoC pinout): net `USB_OTG_PWREN_H` is `GPIO0_D4_u`, ball AL39.
  - sheet 14 "USB2/USB3 Port" (sheet rev 2.1): U9 SY6280AAC load switch: IN from `VCC_SYSIN`, EN (pin 4) from `USB_OTG_PWREN_H`
    through R82 (1 K), VOUT (pin 1) = `VCC5V0_USB_OTG0`. J4 (`USB3_TYPE_A_TOP`, the upper USB 3.0 OTG port) VBUS_1 (pin 10) is on
    `VCC5V0_USB_OTG0`. R83 (1 K) is marked NC: the EN has no pull-down, so it floats until the pinctrl drives PD4.
  - sheet 14, SuperSpeed: J4 pins 14-18 go through 0 ohm R78-R81 to the USBDP PHY0 lanes (`TYPEC0_SSRX1/SSTX1`, shared with DP0 on
    sheet 7). So `usb3` is wired. The lane sharing with DP is a PHY mode choice, not checked on a board.
  - nothing else drives VBUS on J4: VBUSDET (R86, R89) only senses. Sheet 23 "DC IN": the upper USB-C (J1) is a sink (CC pulled
    down with 5.1 K), its VBUS feeds `5V_DCIN`, not the OTG net; the WNM2030 switch there feeds the SoC 5 V rail. No Type-C PD controller.
- **Generator output (96080d36):**
  - `validate --no-live`: rc 0.
  - `tree`: rc 0. Overlay: `target-path = "/usb@fc000000"` `dr_mode = "peripheral"`; `/syscon@fd5d0000/usb2phy@0` enabled;
    `/syscon@fd5d0000/usb2phy@0/otg-port` `phy-supply = <&lemnos_no_vbus>`; `/phy@fed80000` (USBDP) enabled for `usb3`.
  - boot fragment: `gpio:gpio0:28: VBUS of usb-otg0 held low (off) from power-on ...` and `gpio=28=op,dl`. Not applied by any
    Rockchip loader in this repository (Q2g not merged).
  - fixups: `u2phy0_otg = "/fragment@0/__overlay__:phys:0"`, `usbdp_phy0 = "/fragment@0/__overlay__:phys:4"`.
  - Labels/paths at v7.3.3 (`rk3588-base.dtsi`): `u2phy0_otg` (line 667, `otg-port` under `u2phy0: usb2phy@0` in
    `usb2phy0_grf: syscon@fd5d0000`, line 649) present; `usbdp_phy0: phy@fed80000` (line 3398) present; `/usb@fc000000` (`usb_host0_xhci`,
    line 467) present; `/syscon@fd5d0000/usb2phy@0` present. Missing: none.
- **Remaining before activation:** (1) Lemnos Q2g merged, and the lock moved to a rev with Q2e, Q2f and Q2g; (2) the meter check
  below, with the line read in `/sys/kernel/debug/gpio`; (3) the pin behind ball AL39 is from sheet 5 and the dts; the RK3588 ball map was not read.

- **Base tree (rk3576-rock-4d.dts, v7.3.3):** `&u2phy0_otg { phy-supply = <&vcc_5v0_otg> }`, and `vcc_5v0_otg` has `enable-active-high`,
  `gpios = <&gpio2 RK_PD2 GPIO_ACTIVE_HIGH>`, `regulator-always-on` and `regulator-boot-on`. So the base tree forces the port's
  5 V on from boot. `vcc_5v0_host` (drd1's supply) is the same shape on gpio0 PD3.
- **Schematic V1.12 (`Radxa_ROCK_4D_SCH_V1.12.pdf`, 28 sheets, downloaded into scratch), what it shows:**
  - sheet 21 "USB HUB/USB2/USB3": a stacked USB 3.0 Type-A J26; its lower port is the OTG port (VBUS_0 on `5V_USB_OTG0`, USB3_OTG0 nets);
    its upper port is the host (`5V_USB_HOST`).
  - the OTG port's 5 V is a **load switch**: U23 SY6280AAC, IN = `VCC5V0_SYS_S5`, VOUT = `5V_USB_OTG0`, EN (pin 4) = `USB_OTG0_PWREN_H`
    through R359 (1 K), OCB with a 6.8 K pull-up. The host port is the same shape: U27 SY6280AAC, EN = `USB_HOST_PWREN_H`.
  - So the hardware CAN switch the OTG port's 5 V off. The always-on is a setting in the base dts, not a fact of the board.
  - **Not settled:** which SoC pin is `USB_OTG0_PWREN_H`. Sheet 14's pin rows (GPIO2_D1_d, GPIO2_D2_d) and balls (B17, B18) do not line up
    unambiguously in the text layer or the render. The dts says PD2 (line 26). The RK3576 ball map was not read.
  - SuperSpeed: sheet 21 wires `USB3_OTG0` SSRX/SSTX to J26 (pins 14-18) through 0 ohm R364-R366; sheet 9 names them the USB3 OTG0 lanes.
- **What it means:** an always-on 5 V cannot be a device port, and the base tree says always-on. The schematic says the 5 V is
  switchable. Only a meter (below) and an Atlas-owned board dts (dropping `regulator-always-on` on `vcc_5v0_otg`, reviewed and run on a
  board; not made here) can move this forward. Then a `vbus = "gpio:gpio2:<line>"` statement, once the ball map and polarity are confirmed,
  or `vbus_undriven = true` only with the meter behind it.

## The meter check (for every device-mode board's bring-up list)

Copied from Lemnos `testing/board-runs/Q2f.md` at `96080d36`, section "The check to run on a board", steps 3 and 5, in our words.
(Steps 1, 2 and 4 are the Lemnos overlay and live-tree checks, and the GPIO line read, which apply to Lemnos boards only.)

1. **Device mode, cable unplugged:** meter VBUS on the device-mode port. It must read 0 V.
2. **Plugged into a host that supplies its own VBUS:** the board must not add 5 V to the host's line. The meter reads what the host supplies.
   Record both readings with the board and its `vbus_reason`.
3. **If the board holds VBUS by a line** (`vbus` in the board file): read the line's level in `/sys/kernel/debug/gpio` once the kernel runs
   (`out lo` with `vbus_off = "low"`), and measure the regulator's enable pin during firmware or U-Boot, where the boot hold is the only thing holding it.
4. **If the board says `vbus_undriven`:** measure as in step 1. If it reads 5 V, the statement is wrong and the board must say `vbus`.

Per board: **ZERO 3E** (steps 1-2; the USB-C 1 is also the power input, so its VBUS is the host's by design; the PMIC `VBUS` net doubt
is settled here). **ROCK 5C** (steps 1-3; not before Q2g). **ROCK 4D** (steps 1-2 are the decision for the held entry). **Cubie A7S** (steps 1-2, see B19).
**Raze** (steps 1-2, see G1).

## Fixups and labels procedure (item 7, for each board)

1. Build `lemnos-ctl` at the rev (here `96080d36`).
2. `lemnos-ctl tree --socs socs BOARD -o board.dts` (add `--boot`, `--modprobe`).
3. `dtc -@ -I dts -O dtb -o board.dtbo board.dts`; `dtc -I dtb -O dts board.dtbo` and read `__fixups__`.
4. For each label, grep its `label:` in the base dts at the pinned rev. For each path, check the node exists. Report any missing.

Results (this PR): ZERO 3E `{usb2phy0_otg}`, all present. ROCK 5C `{u2phy0_otg, usbdp_phy0}`, all present. ROCK 4D: refused, no overlay, so none
(a future statement would need the same check). Raze: not run on the base (B20).

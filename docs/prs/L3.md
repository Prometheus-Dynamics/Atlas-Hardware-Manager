# L3: Atlas reads and verifies slot bundles through Lemnos's crate

Ruling by the coordinator: Atlas stops carrying its own copy of Lemnos's slot-bundle format. It reads and
verifies bundles through Lemnos's `lemnos-slot-store` crate, pinned to the image's Lemnos rev.

## The defect, and why the tests missed it

`crates/core/bundle` implemented the first bundle version: `slot.sig` was a raw 64-byte Ed25519 signature over
`slot.json`. Lemnos (f4a295c6, `docs/slots.md` "A bundle"; `drivers/slot-store/src/signing.rs`) writes a 108-byte
record: `LMNSSIG1`, algorithm 1, three zero bytes, the 32-byte key id (SHA-256 of the public key), then the
64-byte signature over `signing::slot_bundle_message` (tag `lemnos-slot-bundle\0`, version 1, length, manifest).

Atlas's writer and Atlas's reader agreed on the 64-byte form, so every Atlas test passed. Gaia's real bundle
(written by `lemnos-ctl`) was refused: `atlas-next usb-boot --dry-run` said "slot.sig is 108 bytes, not 64". The
same mistake sat in three places: `sign.rs` and `inspect.rs` (signature), and `seed.rs` (its own record and message,
built from `atlas_image::Record`). The test source (`Synthetic`) also used junk tree bytes and a fake salt, so
nothing compared Atlas's output with Lemnos's. Two more defects surfaced on the way (below): the reader refused
Lemnos's `boot/` directory member, and the writer never agreed with Lemnos's verity tree.

## The change

- `Cargo.toml` (workspace): `lemnos-slot-store` as a git dependency on `https://github.com/Prometheus-Dynamics/Lemnos.git`,
  `rev = "f4a295c611972ba422df20a78112b9fb409c47d0"`, `default-features = false`. `crates/core/bundle` and
  `crates/tools/next` use it (`workspace = true`).
- Signing (`sign.rs`): `sign_slot` returns the 108-byte record (`signing::record_bytes`, `key_id`,
  `slot_bundle_message`); `verify_slot` parses it (`signing::parse_record`, so a bare 64-byte signature is
  `Malformed`), matches the key id, and verifies. The `ed25519:<hex>` public key text is decoded in one place
  (`sign::raw_public`).
- Seed (`seed.rs`): `key_id`, `slot_message` and `sign_slot_record` use the same Lemnos functions. The local record
  struct and the `atlas_image::Record` use are gone.
- Manifest (`manifest.rs`): `to_json` is `Manifest::to_json` and `parse` is `Manifest::parse`; the bytes read are
  the bytes `slot.sig` signs and are not re-serialized. Atlas's `validate()` still runs after the parse (see audit).
- Reader (`inspect.rs`): Lemnos's optional `boot/` directory member is taken once (it was refused before). Any
  other directory is still refused.
- Writer (`write.rs`): doc now says TEST AND SIM ONLY; real bundles come from `lemnos-ctl bundle`.
- `crates/tools/next/src/usb_boot/fat.rs`: `BAY_PATHS` is `lemnos_slot_store::bays::ROLES`, not a second list.

## Dependency and pin rule (`scripts/check-devices.sh`)

`lemnos_cargo_pin_rule` reads the `lemnos-slot-store` rev from the workspace `Cargo.toml` and fails, naming both
revs, when any product's `gaia.lock` pins a different Lemnos rev or no product pins Lemnos. The self-test
(`lemnos_cargo_pin_self_test`) rewrites the rev to `1111…` and requires a refusal that names the products' rev, then
passes the real tree. It is in check-devices because that is where the image's Lemnos rev is held
(`devices/products/*/gaia.lock`), the checker already runs in the gate, and it takes no cargo run.

## Duplicate-crate check (`scripts/check-devices.sh`)

`lemnos_duplicate_crates` reads `Cargo.lock` (`--locked` already holds it to the manifests, so no `cargo metadata`
run is needed) and prints each package whose git source is the Lemnos repository at two or more revs. The
self-test (`lemnos_duplicate_self_test`) refuses one crate at two revs and passes one rev. Current result: no
package at two revs. The Lemnos packages in the lock are `lemnos-slot-store` at `f4a295c6` and five `shm-*` crates
at `d1a8939a` (through Orion `fd61df3e`). The brief said Orion brings `bded77a0`; the lock says `d1a8939a`. No name
appears at both, so the check passes; the discrepancy is noted in doubts.

## The fixture

`crates/core/bundle/tests/fixtures/lemnos-f4a295c6/`:

- `slot-a1.bundle`: 16384 bytes, written by the REAL `lemnos-ctl bundle` built from Lemnos f4a295c6. Contents:
  `slot.json`, `slot.sig` (108 bytes), `rootfs.erofs` (one 4096-byte erofs block from `mkfs.erofs`, no tree), and
  the five boot files (kernel 3000 zero bytes, initramfs, device tree, board overlay, cmdline). It carries
  `boot.overlay`.
- `test-key.pub`: the public half of a THROWAWAY key from `atlas-next bench-key` (key id `600ebf63…8c44`). Its seed
  was never read, copied or committed; `bench.seed` stays in the scratch dir.
- `README.md`: the rev, the exact commands, the test-key statement, the refresh rule.

The tests (`tests/lemnos_fixture.rs`): Atlas reads and verifies the bundle; the record is 108 bytes and carries the
fixture key id; a changed `slot.json` byte is `BadSignature`; a changed root image byte is refused; a bare 64-byte
signature is `Malformed`; another key does not verify.

The reverse check (`tests/bundle.rs`, `lemnos_verifies_the_bundle_this_writer_makes`) runs Lemnos's own
`bundle::verify` on a bundle Atlas's writer makes, with Lemnos's tree and role names: all checks pass. It found two
things first: the synthetic source's tree and boot names were not Lemnos's (test data, now fixed), and Atlas's
reader refused the `boot/` directory (a real reader defect, now fixed).

## Dry run (the real proof)

`atlas-next usb-boot --agent 127.0.0.1:9 --port 3-1.1.4.1 --bundle …/store-next/objects/file/ab/ab503cb9…d5e --boot-partition <image> --pubkey /mnt/ssd-samsung/atlas-bench-key/bench.pub --dry-run`

NO IMAGE PASSES: each run refuses with exit 1, and nothing is sent. The bundle itself is read and verified (no
signature or record refusal any more). The refusals are the boot partition's:

- Image 1 (`665f0bb8…`): `cmdline.txt` SHA-256 differs from the bundle's; no `ramoops-pi5` link.
- Image 2 (`ac7212f6…`): `cmdline.txt` differs; no `ramoops-pi5` link.
- Image 3 (`c1e7b38f…`): `cmdline.txt` agrees with the bundle; no `ramoops-pi5` link (the only blocker).
- Image 4 (`20d42dba…`): `cmdline.txt` differs; no `ramoops-pi5` link.

The ramoops blocker: `config.txt` has no `dtoverlay=ramoops-pi5` and `overlays/ramoops-pi5.dtbo` is not in the boot
partition, so link 1 cannot be judged. That is the boot image's content (Gaia's), not the bundle reader. Full outputs:
`/mnt/ssd-samsung/atlas-next-scratch-L3/dryrun-image1.out` … `dryrun-image4.out`.

## Doubts

1. No image passes the dry run. Image 3 agrees on the cmdline; the ramoops link is the open item, and it is Gaia's
   boot image (or the board's pstore rule) to settle. Not fixed here: the store objects are read-only.
2. The reader drops `boot.overlay`: `SlotManifest` has no overlay field, so an Atlas view of a Lemnos bundle with an
   overlay loses that key. The signature is still checked over the exact bytes, so this is a view gap, not a
   verification gap. Fixture has one (`boot.overlay`).
3. The writer omits the optional `boot/` directory member. Lemnos's reader accepts both (tested in the reverse check).
4. Verity tree bytes: Atlas's reader still does not recompute the tree (its documented scope). Lemnos's installer does
   (`bundle::verify` refuses a tree that is not the tree of the image). Atlas bundles from real images therefore
   depend on the image's tree, not on Atlas.
5. The Orion Lemnos rev is `d1a8939a` in the lock, not `bded77a0`. Check that the brief's figure was not a different
   pin.
6. The duplicate check reads `Cargo.lock`; it cannot see a rev that is in `Cargo.toml` but not yet locked (`--locked`
   fails first in the gate, so that is covered).
7. The fixture's seed (`fixture-key/bench.seed`) lives only in the scratch dir, never in the repo. A refresh re-signs
   from that scratch seed with the same command (see the fixture README); if the scratch dir is gone, make a new
   test key and update `test-key.pub`, `KEY_ID` in `tests/lemnos_fixture.rs`, and the README.

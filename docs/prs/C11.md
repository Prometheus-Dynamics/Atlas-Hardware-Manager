# C11: The device description as Lemnos sends it

**Group:** C. One board driver

**Wave:** 4

**Needs:** C2

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first. The format is Lemnos's `describe 1` text, as its encoder
writes it at Lemnos `e5c0ff0e` (I6h): `service/orion/src/description.rs`, with the format stated in
`docs/daemon.md` ("The description through `.call`"). The encoder is the definition; where the docs
and the encoder differ, the encoder wins and the difference is listed in the PR text for Lemnos.

## Creates

- `crates/board/topics` (edit: `description.rs`, `describe.rs`, `device.rs`, `read.rs`, `hardware.rs`,
  `value.rs`, `lib.rs`; tests: `tests/description.rs`, `tests/hardware.rs`, `tests/fixtures/`)
- `crates/testing/sim-node` (edit: `readings.rs`, `node.rs`, `lib.rs`; new `describe.rs`, a mirror of
  the encoder, not a Lemnos dependency)

## Build

- The description is fetched through the session with `lemnos.<device>.call describe` (no arguments).
  One function asks (`describe::fetch`), so a paged form can replace it in one place.
- A text is parsed whole: an unknown version is refused by name; a malformed line refuses the whole
  text with its line number; unknown keys and unknown records are ignored and counted; a missing key is
  not reported for its field. Bounds are named constants with their reasons (`description.rs`).
- The device model is built from the description and the topics: no labels, no table in Atlas. A
  description that is not available (the board refuses `describe`, or the device is not running) is a
  state of the device, and the device is still listed with its readings.
- A description is asked when a connection first sees a device, and again only when its generation
  topic (`lemnos.<device>.description`) moves. A manual refresh asks every device again.
- The simulated node answers `describe` from its device model, through the encoder mirror, with a
  generation that moves once per change.

## Proof

- Lemnos's own vectors parse to the expected model: the `tracked` device (`tests/fixtures/`), the labels
  of Lemnos's round-trip test, and its item record.
- Each refusal is a test: unknown version, malformed line, oversized text, too many records, a
  reference the text does not give.
- Unknown keys and record types are ignored and counted; every optional field absent reads as not
  reported; the three unit states; real-valued ranges and the exponent; a settable item's setter; a
  three-axis group.
- The fetch goes through the simulated node; a generation change asks once; a board that refuses
  `describe` shows the devices "not available" until a refresh.

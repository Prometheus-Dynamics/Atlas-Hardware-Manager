# B14: The flasher's built-in kernel options, per family

**Group:** B. Board descriptions

**Wave:** 4

**Needs:** B2, B3, B9

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

The flasher image has no kernel modules, so every option its daemon (lemnosd) or Orion needs must be built into the board's kernel (`=y`). One kernel per board: there is no separate flasher kernel config. The options go in the family fragments, not in boards or products.

## Creates

- `devices/families/bcm2712/assets/linux.fragment`: the BCM2712 family's built-in options (new file).

## Changes

- `devices/families/bcm2712/family.toml`: `[kernel] fragments` names the new fragment.
- `devices/families/rk35xx/assets/linux.fragment`: two lines added (USB gadget for the flasher).
- `devices/boards/raze/board.toml`: the family fragment is named in the Raze's `fragments` list (a list replaces the family's, as the ZERO 3E already does).
- `devices/boards/raze/kernel/raze.config`: the Raze's `=m` lines for these options are removed (they would override the family's `=y`, and two of them are not user-settable). Each removal leaves a comment pointing at the family fragment.

## Options

| Family | Option | Why (the flasher has no modules) | Dependencies it forces, from the pinned Kconfig |
|---|---|---|---|
| BCM2712 | `CONFIG_USB_CONFIGFS=y` | lemnosd's gadget is built through configfs | `depends on USB_GADGET` (=y in bcm2712_defconfig); `select USB_LIBCOMPOSITE` (which `select CONFIGFS_FS`; CONFIGFS_FS=y in raze.config) |
| BCM2712 | `CONFIG_USB_CONFIGFS_F_FS=y` | Orion's link is a FunctionFS function | `depends on USB_CONFIGFS`; `select USB_F_FS` (no prompt, so it cannot be set directly) and `select DMA_SHARED_BUFFER` |
| BCM2712 | `CONFIG_I2C_CHARDEV=y` | `/dev/i2c-N` for the BMM150 and INA238 | none beyond I2C (=y) |
| BCM2712 | `CONFIG_I2C_DESIGNWARE_CORE=y` | the RP1 DesignWare adapter | none beyond I2C; it is m in bcm2712_defconfig |
| BCM2712 | `CONFIG_I2C_DESIGNWARE_PLATFORM=y` | the platform binding for the RP1 I2C controllers | its Kconfig entry is inside `if I2C_DESIGNWARE_CORE`, so CORE=y is required; `!ACPI` holds |
| BCM2712 | `CONFIG_RP1_PIO=y` | Lemnos's PIO transports (PIO I2C, LED ring) | `depends on FIRMWARE_RP1 \|\| COMPILE_TEST` |
| BCM2712 | `CONFIG_FIRMWARE_RP1=y` | the firmware driver RP1_PIO needs (it is m in bcm2712_defconfig) | `depends on MBOX_RP1` |
| BCM2712 | `CONFIG_MBOX_RP1=y` | the mailbox FIRMWARE_RP1 uses (m in bcm2712_defconfig) | `depends on MFD_RP1` (=y in bcm2712_defconfig) |
| RK35xx | `CONFIG_USB_CONFIGFS=y` | lemnosd's gadget (m in the arm64 defconfig) | `depends on USB_GADGET` (=y in the defconfig; the ZERO 3E board fragment sets it too); selects USB_LIBCOMPOSITE |
| RK35xx | `CONFIG_USB_CONFIGFS_F_FS=y` | Orion's FunctionFS link (off today: it stayed m behind USB_CONFIGFS) | as above: selects USB_F_FS |

Side effect, found by resolving the merged config (`conf --olddefconfig`, see Proof): `CONFIG_USB_CONFIGFS=y` makes the configfs functions that the boards already ask for take effect. Those were inert while USB_CONFIGFS was m, because a configfs function can only be as built-in as its parent. On the Raze these flip from m to y: `USB_F_ACM`, `USB_F_NCM`, `USB_F_MASS_STORAGE`, `USB_U_ETHER`, `USB_U_SERIAL` (raze.config asks for NCM and ACM; the defconfig asks for the rest), and, from the defconfig, `USB_F_EEM`, `USB_F_HID`, `USB_F_OBEX`, `USB_F_PRINTER`, `USB_F_SS_LB`. No line of ours names them; they are the defconfig's and raze.config's own choices, now real. On the ZERO 3E the set is worked out the same way (see Size).

Not changed, checked: the Raze's UDC is `CONFIG_USB_DWC2=y` and the RK35xx one is `CONFIG_USB_DWC3=y`, both already built in. `CONFIG_CONFIGFS_FS` is y on both (raze.config; the arm64 defconfig).

The RK35xx family fragment is inherited by every RK35xx board: the ZERO 3E (the flasher's board), and also the ROCK 5C and ROCK 4D (their kernels grow too; see Size).

## Size

Derived, not a rebuilt Image. The number is the allocated size (text, data, rodata, bss, init and export tables) of each module that becomes built-in, read with `size` and `readelf` from module builds of the same kernel releases that already exist on this machine. Debug sections are not allocated and are not counted. The host `strip` cannot read aarch64 ELF, so the figures are the allocated sizes, which is what a stripped module loads. Built-in code also adds kallsyms names, which are not counted, so the figure is a floor for the Image's growth.

ZERO 3E (RK35xx, Linux 7.3.3): libcomposite was already built in on this board (`CONFIG_USB_ETH=y` in the board fragment selects it), so only the configfs glue inside it is new (not measured separately). The flipped modules, from the ROCK 5C build of 7.3.3 (`/mnt/ssd-samsung/gaia/work/.gaia/examples/rock-5c/build/image/buildroot-output/target/lib/modules/7.3.3`; the same kernel release, not an RK35xx build): usb_f_fs 30,867; usb_f_mass_storage 27,335; usb_f_ncm 11,692; u_serial 9,759; usb_f_eem 5,896; usb_f_acm 5,339; usb_f_obex 3,411; usb_f_serial 3,239. Total 97,538 B (about 95 KiB). Expected Image growth for the ZERO 3E: about 0.1 MB, derived, plus the unmeasured configfs glue.

The ROCK 5C and ROCK 4D inherit the RK35xx family fragment, so their Images grow by the same derived amount. Their boards have no flasher, so this is growth without a need in those products.

The `.ko` files of these modules leave the installed module set on every board that builds them. Their installed size is not measured here.

Not measured: a rebuilt Raze or ZERO 3E Image. The real number is the board kernel's `Image` size from a build of this branch, against the same build on `next` (`afd8f5b`).

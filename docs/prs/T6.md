# T6: a read cut at its window keeps its run, so a slow list completes

DEBT. The test `a_list_over_the_size_bound_is_passed_on_by_name_and_not_truncated` (crates/drivers/board-slots/tests/slots.rs)
failed once in another PR's gate at load ~113: "the oversized list did not answer within 60s". 17 others passed.

## What was measured

Cause under test: a short call waits at most `DIRECT_WAIT` (2 s, half the call wait). A direct run that is not finished
by then is cancelled (`Run::cancel`) and reported `NotFinished`, and `answered()` makes the call again from zero. If one
attempt takes longer than the window, every attempt is cut and restarted, and the call never answers.

- Deterministic reproduction (sim knob added in this PR: a run of `system.slots.list` takes 150 ticks = 3 s, 20 ms each).
  Before the fix: 26 direct attempts, every one `LATE` at 2.07 to 2.24 s wall, each cancelled, and the test panics at 60 s
  with "the slot list did not answer within 60s". This is the livelock: a call that is correct and slow never converges.
- The 300-entry oversize list (the failing test's case) at load 146 to 162 on the machine: 6 full-suite runs, every
  oversize call answered in ONE attempt, 171 to 303 ms wall, no `LATE`. So the failing gate's slowness was not reproduced
  here; the gate's per-attempt timing was not captured. The mechanism above is what turns any slow attempt into a
  failure, and the fix below removes it.
- Cost of the pieces (debug build, temporary timing, removed before commit): `list_json` for 1 slot ~0.4 ms; for 300 slots
  44 to 59 ms (100 KB of JSON, refused by name over 60 KiB); `evaluate()` is a no-op without a trial. One tick measured
  27 ms once. Nothing per tick is quadratic, so the cost is not the cause.

## Cause

Atlas's read is a direct run: started non-detached, and cancelled at the window. The only result a retry can get is a
fresh run. Lemnos at f4a295c6 says the same thing about `list`: a reply over the bridge's 60 KiB is refused by name, and a
board whose slots do not fit uses `list_page` (method 13). Paging would change `list` (the refusal this test pins), so it is
not this fix.

## Fix (choice: a kept read, not paging)

The coordinator's options were (a) keep the attempt running and land its result later, or (b) page the list. (a) is
chosen. (b) would change `list` so that an oversize list is no longer refused by name, which is the contract the test
`a_list_over_the_size_bound...` checks (and the coordinator's instruction was to keep that assertion). Paging stays a
separate, later change (the LOCK note in `calls.rs` names it).

`crates/board/actions/src/board.rs`:
- `BoardActions::read(action, words)` (new) and `catalog()` go through `read_named`. A read is started DETACHED with a
  deadline (`READ_DEADLINE_MS`, 60 s, under the node's one-hour cap for detached runs), and waited for in the window.
- A read not finished in the window is NOT cancelled. The run stays on the board, its number is kept in
  `BoardActions.reads` (shared by clones, keyed by action name and the node's public key), and the call returns
  `NotFinished`. The next call for that read follows the same run by number (`attach`) instead of starting it again.
- A kept run that the board no longer has (`Attach` answers `NotFound`) is started again. A run the board ended while
  nobody was attached is kept by the board for its starter (Orion's action list keeps ended detached runs for 10 min);
  the next call gets that answer (test `a_read_the_board_finished_unattended...`).
- A node without detached runs (`ClientError::Level`, `DetachedRun`) takes the old direct path, cancelled at the window.
- `run()` (short actions, lease-renewing calls) is unchanged: still direct and cancelled at the window.
- The module header and the retry-safety list are updated to match. `NotFinished`'s message no longer says "it was asked to
  stop" for a read.

`crates/drivers/board-slots/src/calls.rs`: `list()` calls `actions.read(...)` instead of `actions.run(...)`. Its refusal
path is unchanged (the board's words, by name, never truncated and never retried).

`crates/testing/sim-node/src/script.rs` and `node.rs`: additive knob `Script::slow_action(action, ticks)` (a run takes N
ticks, 20 ms each). No default behaviour changes.

## Proof

Tests added (crates/drivers/board-slots/tests/slots.rs):
- `a_list_longer_than_one_window_completes_and_is_not_started_again`: the sim's list takes 3 s (150 ticks) against the 2 s
  window. Completes, and the sim started the list ONCE (`runs_started == 1`). It FAILS on the old code (reproduction above).
- `a_read_the_board_finished_unattended_is_answered_by_the_next_call`: the sim's list takes 2.1 s; the first call is cut
  at its window, the caller waits 1 s, and the next call gets the board's answer; the list was started once.

Kept unchanged: `a_list_over_the_size_bound_is_passed_on_by_name_and_not_truncated` (the "60 KiB" words are still checked).
No `DEADLINE` or `DIRECT_WAIT` change.

Runs (this machine, load 121 to 162; each binary built in cargo slot 2 `/mnt/ssd-samsung/atlas-next-target-2`):
- `atlas-board-slots` `slots` (20 tests): 5 of 5 runs passed, 5.8 s each.
- `atlas-board-slots` `trial` (10 tests): 3 of 3 runs passed.
- `atlas-actions` (8 + 13 tests) and `atlas-sim-node` (11, 7, 35, 17 tests): passed, before the final message edit in
  `error.rs`; the gate below runs them again.
- Gate: see the PR body.

  (see Lemnos docs/daemon.md on detached runs), not tested here.
- `list_page` paging for boards whose list exceeds 60 KiB is not in this PR (see Fix).

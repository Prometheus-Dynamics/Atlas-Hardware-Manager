## Board files: where the entries live

No Lemnos board file for the ZERO 3E, ROCK 5C or ROCK 4D existed in `devices/`. The Raze's lives in
`components/raze-lemnos-board/files/board.toml` because the Raze image installs it; the RK boards' base products

the check does not parse these files (the check passes with them present). Nothing installs them yet.

## Part 1: the device-mode port

Every entry is data for Lemnos's generator (`lemnos-ctl tree`, Q2e). No board .dts is written by hand.

| Board | Entry | Status | Evidence (kernel tree v7.3.3 unless stated) |
|---|---|---|---|
| ZERO 3E (RK3566) | `udc:fcc00000.usb`, `usb-otg0`, `role = "peripheral"`, no options; gadget `uses = { function = "udc:fcc00000.usb" }` | WRITTEN, active in its file | (a) `usb_host0_xhci` is the only OTG controller (`usb2phy0_otg`); Radxa names USB-C 1 as USB 2.0 OTG and power input. | Raze (BCM2712) | `udc:1000480000.usb`, `controller = "usb"` (already in the board file) | UNCHANGED | Lemnos `socs/bcm2712-rp1.toml` at e99d51c0: `[controllers.usb]` `sysfs = "1000480000.usb"`. The name matches. |

### phy-supply findings (asked for by the coordinator)

- **ROCK 5C: YES.** `rk3588s-rock-5c.dts` sets `phy-supply = <&vcc5v0_usb_otg0>` on `u2phy0_otg`. That is host
  VBUS on the device-capable port. The generator writes no `phy-supply` and the overlay does not remove it.
- **ROCK 4D: YES, on both candidate ports.** `rk3576-rock-4d.dts` sets `phy-supply` on `u2phy0_otg`
  (`vcc_5v0_otg`) and on `u2phy1_otg` (`vcc_5v0_host`); both regulators are always-on.
- **ZERO 3E: NO.** Nothing sets `phy-supply` on its OTG PHY.

A device-mode entry on the ROCK 5C or ROCK 4D would source 5 V from the device port, so both are held. Removing
the `phy-supply` needs an Atlas-owned board dts (not the overlay), reviewed and run on a board.

### OPEN points

1. ROCK 5C: SuperSpeed lanes on the upper USB 3.0 port. Settles: the V2.10 schematic's USB Type-C page
   (`dl.radxa.com/rock5/5c/docs/radxa_rock_5c_schematic_v2.10.pdf`). Not read; `usb3` stays off.
2. ROCK 5C and ROCK 4D: the `phy-supply` removal (above). Settles: an Atlas-owned board dts, reviewed and run on a board.
3. ROCK 4D: which DRD the upper port is on (drd0 by the pinout reading; the schematic is not read) and its SuperSpeed lanes.
   Settles: `Radxa_ROCK_4D_SCH_V1.12.pdf`, the PCIe/SATA/USB3 page.
4. ZERO 3E: the connector evidence is Radxa's interface page (summary read, not a schematic). Settles: the V1.2 schematic's USB sheet.
5. Lemnos lock: every entry above is written to e99d51c0 and UNVALIDATED. The products lock Lemnos at `b0bf0101`,
   which predates Q2e. `lemnos-ctl tree` and the start check cannot read these entries until the lock moves to a
   green rev containing Q2e. The lock was not moved here.

## Part 1: the ZERO 3E bring-up's hand-written gadget dts: NOT replaced

`boards/radxa-zero-3e/assets/dts/rockchip/rk3566-radxa-zero-3e-gadget.dts` is the board's own kernel dts (the base
product boots it too). Replacing it needs `lemnos-ctl tree` to run at build time, and the locked Gaia (4abf626) has no
step for that. It is replaced when the Lemnos lock moves and Gaia takes the generator's output. Until then it stays,
and it is the same `dr_mode = "peripheral"` change the generated overlay makes.

## Part 2: stable gadget addresses on the bring-up products

Addresses are locally administered and unicast (first octet 02), different for device and host, and different per board.

| Product | Gadget driver in its kernel | Addresses | Where |
|---|---|---|---|
| zero-3e-bringup | legacy `g_ether` (built in: `CONFIG_USB_ETH=y`, `boards/radxa-zero-3e/assets/linux.fragment`) | device `02:3e:00:00:00:01` (`g_ether.dev_addr`), host `02:3e:00:00:00:02` (`g_ether.host_addr`) | `pending/zero-3e-bringup/components/dev-zero-3e-usb-extlinux/extlinux.conf` (the `append` line) |
| cubie-a7-bringup | NONE: `families/sun60i` enables no USB gadget option, so `dev-usb0-gadget` has no driver | not set | OPEN (below) |
| rock-5c-bringup, rock-4d-bringup | no gadget (Ethernet and serial only) | n/a | n/a |

**Why a copy of the extlinux.** The shared `radxa-zero-3e-extlinux` is in the base product too. The addresses are
dev-only data, so they cannot go there. Gaia 4abf626's component form takes no per-product value, so the bring-up
product lists `dev-zero-3e-usb-extlinux` instead of the shared one. The copy is four lines; its only difference
from the shared file is the two `g_ether` arguments. Both install `/boot/extlinux/extlinux.conf`, so they cannot both
be in one product.

**OPEN:** the Cubie's gadget. Its kernel has no USB gadget config, so the bring-up's usb0 link cannot appear at all.
Settles: adding `CONFIG_USB_ETH=y` to `families/sun60i`, which is a kernel change and needs a board run. Not made here.

The managed image's MACs come from Lemnos `function ncm derive`; these are bring-up only.

## DRAM part (finding 3)

The SDK does NOT name the DRAM part. What it names:
- `CONFIG_DDR_SIZE=0x8000000` = 128 MiB: `k230d_canmv_bpi_defconfig:20` and `k230d_canmv_defconfig:20`.
- `CONFIG_SIPLP4_2667`: `board/canaan/k230d_canmv/Kconfig:20`, selects the table; `arch/riscv/cpu/k230/dram.c` 138-139
  (`CONFIG_SIPLP4_2667` calls `sip_ddr_init_2667()`). The table file is `board/canaan/common/sip_lpddr4_init_32_swap_2667.c`.
- The name "sip" and "lpddr4" give the LPDDR4 type and the speed (2667 MT/s). The vendor, the part number and the
  package-in-package nature are NOT in the SDK (no `K4`/`H9`/`MT53` part number in the configs or board files).
- The memory node is 128 MiB at 0x0: `arch/riscv/dts/k230d.dtsi` memory@0 (reg 0x0 0x8000000).

Per the coordinator, the table is used as it is. The part is "from the SDK, unconfirmed until first boot".

## The env (Lemnos BB1b uboot record, against the SDK) (finding 2 and 4)

**Burn layout (the env does not overlap any SPL or U-Boot raw area):** `board/canaan/k230-soc/genimage.cfg`
- SPL copy 0: `offset = 1M` (line 19-20), SPL copy 1: `offset = 0x180000` (line 25-26).
- env (copy 0, partition `uboot_env`): `offset = 0x1e0000`, `size = 0x20000` (lines 28-33), image `env.env`.
- U-Boot: `offset = 2M` (lines 34-39), image `fn_ug_u-boot.bin`, sized 1.5 MiB by its comment (line 35).
- env (copy 1, partition `env`): `offset = 0x380000` (lines 40-45), image `env.env`.
- All three env and raw areas are `in-partition-table = false`, all start at or above 1 MiB, so they sit outside the
  primary GPT (LBA 0-33, bytes 0x0-0x4200) and outside every GPT partition (boot at 30M, genimage.cfg:54-60).
- Copy 0 0x1e0000..0x1effff ends before U-Boot at 0x200000. Copy 1 0x380000..0x38ffff starts after U-Boot's 1.5 MiB
  slot (ends at 0x380000). No overlap. So `uboot_env_size` 0x10000 holds with both offsets.
- Lemnos's `uboot_env_size <= 0x1A0000` bound: 0x10000 is well inside it.

**Size:** `uboot_env_size = 0x10000` = `CONFIG_ENV_SIZE` (`k230d_canmv_bpi_defconfig:5`) = `mkenvimage -s 0x10000`
(`board/canaan/k230-soc/post-image.sh:234`). The header is inside the 0x10000 (`env_t` is crc + data over ENV_SIZE).

**Offsets (checked, not swapped):** `uboot_env_offset = 0x1E0000` is the primary copy, equal to `CONFIG_ENV_OFFSET`
(`k230d_canmv_bpi_defconfig:6`, `genimage.cfg:30`). `uboot_env_offset_redund = 0x380000` is the redundant copy
(`genimage.cfg:43`). The draft file `lemnos-board.toml.pending` carries those values in that order.

**Device and index:** `uboot_env_device` is the whole SD disk, `/dev/mmcblk1`. `uboot_env_mmc_index = 1`. Both follow
from the alias pin below. The SDK's SD card is `mmc1` (`mmc1@91581000`, `k230.dtsi:161-170`), because the boot mode is
`SYSCTL_BOOT_SDIO1` (`board/canaan/common/k230_spl.c:65` and `:167`).

**Alias pin (added in K1 after Lemnos's follow-up):** `k230.dtsi` has no `mmc` aliases (its only alias is `uart0`,
`k230.dtsi:34-36`), so without a pin U-Boot's index and Linux's `/dev/mmcblkN` depend on probe order and can disagree.
`devices/pending/k230/assets/mmc-aliases.dtsi` adds `aliases { mmc1 = &mmc1; }` to the U-Boot dts patch and to the
kernel dts. The alias fixes both names to the SD host. The eMMC node (`mmc0`) is not aliased. The bpi dts enables it
(`snps,dwcmshc-sdhci-k230`, 8-bit, `have-emmc-phy`; `k230d_canmv_bpi.dts:49-55`), and the AI-CAM has no eMMC (Atlas's
B7 record). So `mmc0` must not be the env disk. The B7 draft's alias `mmc0 = SD` is replaced by this pin.
**CONFIRM ON BOARD before the first Lemnos write:** the index 1 and `/dev/mmcblk1` are expected from the alias but have not
been seen on a board. A wrong device makes Lemnos refuse with "no valid environment", and it never writes blindly.

**Redundant copies (finding 4): the SDK on disk has no redundancy code.** The SDK's U-Boot overlay has `env/env.c` only,
no `env/common.c`, and `CONFIG_ENV_REDUNDANT` is not set in its defconfigs. So the 2022.10 rule itself cannot be read
from the SDK. The check below uses the mainline 2026.10 copy in `research/scratch-uboot-mainline` as the reference, and
it is NOT the SDK's 2022.10 code.

| Point (Lemnos) | Mainline 2026.10 (reference) | Result |
|---|---|---|
| CRC over the data bytes | `env/common.c:504-508`: `crc32(0, data, ENV_SIZE) == crc` for each copy | matches |
| Serial byte | `env_t.flags` (`include/env_internal.h:80-82`); `env_export` sets `flags = ++env_flags` (`env/common.c:597`) | matches |
| Higher serial wins | `env/common.c:542-545`: flags1 > flags2 gives copy 1 (buf1, primary) valid; flags2 > flags1 gives copy 2 | matches |
| 255 wraps to 0 | `env/common.c:538-541`: flags 255 vs 0 picks the 0 copy as the newer | matches |
| Tie | `env/common.c:546-547`: "flags are equal - almost impossible", `env_valid = ENV_VALID` = buf1 = primary (copy 0) | matches Lemnos's corrected rule: the PRIMARY copy wins a tie |

The primary (buf1) is the copy at `CONFIG_ENV_OFFSET` (0x1e0000 here, `env/common.c:569-570`); the second (buf2) is at
`CONFIG_ENV_OFFSET_REDUND`. In mainline's GPT form the primary is the top copy (`env/mmc.c:145-146`). The SDK writes the
identical `env.env` into both offsets (`genimage.cfg:30-31`, `:43-44`), so both serials are equal on first flash. That is
the tie case, and the primary wins it.
The 2022.10 rule itself is still OPEN: the SDK on disk has no `env/common.c`, so it cannot be read until Gaia's B8 tree
is there. Until then the table above is the 2026.10 reference only.

## Lemnos board file (slot form), what it has and lacks

Has: `format`, `schema_version`, `[board]` id `canmv-k230d-ai-cam`, soc `k230`, `form = "fragment"`; the watchdog0 row at
`/soc/wdt0@91106000` (per Lemnos); the system-slots uboot record in the model's syntax (`config = { ... }`, with
`uboot_env_size = 0x10000`, device `/dev/mmcblk1`, offsets 0x1E0000 and 0x380000, `uboot_env_mmc_index = 1`,
`uboot_watchdog_ms = 10000`). The gadget row (usb-otg0, `udc:91500000.usb-otg`) is pre-filled from Lemnos's
6b84e099, not pinned. `boot_sources` uses Lemnos's SD path `/soc/sdhci1@91581000`.

Lacks, and open:
1. The VBUS statement (coordinator's ruling).
2. The pstore reserved region: a dts item; the address is not chosen.

**Watchdog (uboot_watchdog_ms = 10000):** the SDK on disk has no watchdog node, so its DW WDT clock is unknown. A DesignWare
watchdog's maximum timeout is 2^31 cycles, so the largest period is 2^31 / clk seconds. For 10 s to be under the maximum,
the clock must be at most 214.7 MHz. The value is a 10 s rescue timer, short enough to recover a stuck download quickly,
long enough for a boot ROM to start. The clock value is UNVERIFIED and must be read from the map or the board.

## VBUS and the MMC hosts (from Lemnos's K230-MAP, pr/K230-MAP 6b84e099 on pr/BB1b e8472620; NOT pinned)

**Gadget:** `[[hardware]] name = "udc:91500000.usb-otg"`, controller `usb-otg0` (usb-peripheral, `/soc/usb-otg@91500000`).
Pre-filled in `lemnos-board.toml.pending`. Lemnos's test `service/devtree/tests/k230_port.rs` names the same UDC, and it
refuses `udc:91500000.usb` by name. The UDC name is UNCONFIRMED on a board (Lemnos: "not checked on a board").

**VBUS (TODO, the coordinator's ruling):** the generator needs a VBUS statement (`vbus_undriven` plus `vbus_reason`, the
form in `k230_port.rs`). The SDK on disk names NO VBUS supply for usbotg0:
- `k230.dtsi:209-216`: the node has `compatible`, `reg`, `g-tx-fifo-size`, `dr_mode`, `otg-rev`, `status` only. No
  `vbus-supply`, `phy-supply`, regulator or GPIO.
- `k230d_canmv_bpi.dts:56-58`: `&usbotg0 { status = "okay"; }`, nothing else.
- `k230d.dtsi` has no USB node or regulator.
So the SDK is silent on VBUS. The statement is not written from guesswork; the coordinator decides it.

**MMC node names and the SD host (`/soc/sdhci1@91581000`):** Lemnos's map names the SD host by that path, and its
`boot_sources` uses it. The SDK U-Boot dts names the same node `mmc1@91581000` (`k230.dtsi:161`). So the kernel dts must name
it `sdhci1@91581000` to match the path. U-Boot keeps its `mmc1` label. The alias `mmc1` pins both numbers (see the alias
section). The SD host node is in no map row by design (Lemnos). The eMMC is `sdhci0@91580000`, unused on the AI-CAM.

**Which host boots:** Lemnos's header says the SDK's board file does not state it. The SDK's `SYSCTL_BOOT_SDIO1` boot mode
(`k230_spl.c:65,167`) points at SD. The eMMC node is enabled in the bpi dts (`k230d_canmv_bpi.dts:49-51`). Both are
CONFIRM ON BOARD.

## The env (Lemnos BB1b uboot record, against the SDK defconfig)

The SDK defconfig (`k230d_canmv_bpi`, `k230d_canmv`) has `CONFIG_ENV_OFFSET=0x1e0000`, `ENV_IS_IN_MMC=y` and
`ENV_IS_IN_SPI_FLASH=y` together, `ENV_SIZE=0x10000`, and no `ENV_REDUNDANT`, no `ENV_MMC_DEVICE_INDEX`. So the
series must change the env. The fragment (`uboot-bench.fragment`) uses the device form the SDK layout needs:
`uboot_env_device` `/dev/mmcblk0`, offsets 1920K (0x1e0000) and 3584K (0x380000), `uboot_env_size` 65536.

- Redundancy rule: the scratch copy of mainline U-Boot (2026.10, `research/scratch-uboot-mainline/env/common.c` 537-550)
  uses the 255/0 wrap rule and "higher serial wins". The SDK's 2022.10 `env/common.c` is NOT on disk, so the match is
  UNVERIFIED. Lemnos asked for this check; it is open.
- The SDK's 2022.10 `CONFIG_ENV_OFFSET_REDUND` is not set anywhere in the overlay. 0x380000 is our assumption (the SDK's
  env copy at 3584K, B7).
- Device path: `/dev/mmcblk0` is from the bootargs `root=/dev/mmcblk0p2` (B7) and the dts `mmc0` alias, which the dts
  still has to set. UNVERIFIED.

## Flash crate check (`crates/flash/k230`, against the K230 USB boot protocol)

- The crate follows Canaan's `k230_flash` at 33a75f0. That C source is NOT in this repo or the SDK on disk, so every
  byte layout is UNVERIFIED. The crate says so.
- Existing sim tests (no board): `tests/bootrom.rs` 7 tests (stage by cpu info, pages, reset-into-image success,
  mid-upload reset, stalled page, start timeout, address and empty-image refusal); `tests/burner.rs` 9 tests (probe, read
  range, stale reply, refusal text, partial packet, stall, bad chunk sizes, medium codes); `tests/write.rs` 9 tests
  (chunked write with pad, verify, reboot mark, mid-write reset, cancel); `tests/vectors.rs` (packet layout).
- What a sim test can prove: the framing and sequence the C source predicts, against a fake device. It cannot prove the
  boot ROM's real answers, the load address the ROM accepts, or whether the header is needed.
- Address: the crate accepts `0x8030_0000..=0x8040_0000`. B7 says the SDK tool sends `0x80360000` and the Zero's burner
  links at `0x80300000`. Both are in range. The ROM's own limit is UNCONFIRMED (the crate says so).
- Untested on a board: all of it. The return path after a start (the ROM resets into the image) is coded as success;
  the board test is the proof.
- Lemnos has nothing for K230 USB reflash. The coordinator said: if we take it on, arm the watchdog first and test the
  return path before any write. Not started; it needs the user's go.

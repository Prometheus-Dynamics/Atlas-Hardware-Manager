# G10: the gate's grep guards fail on a match

Found by U2 (PR 119): a board name in a module comment printed a match, and the gate still said `gate passed`.

## Cause

The two guard steps ran `bash -c '! grep -rn … crates/*/*/src apps/*/src-tauri/src 2>/dev/null'`.
`apps/*/src-tauri/src` names no directory until the app lands. GNU grep returns 2 when an operand is missing, even
when it also matched, and `! 2` is 0. So both checks passed whatever the code held. Proof, on this machine:
a file holding `raze` plus a missing path gives grep status 2 and step status 0.

## Fix

`no_match` in scripts/gate.sh searches only directories that exist, and maps grep's status: 1 (nothing found)
passes, 0 (a match) fails with "found above: not allowed here", and 2 (an error) fails with "the check did not
run". A self-test step runs first, on a scratch dir: a match beside a missing glob must fail, and a clean tree must
pass.

## Checks

- The self-test passes.
- The current tree passes both guards. Run by hand before the fix with the missing path left out: no names, no ssh
  shell-outs, so no hidden violation was waiting on next.
- A planted `// raze` in crates/tools/next/src/main.rs fails the names step (status 1), then reverted.

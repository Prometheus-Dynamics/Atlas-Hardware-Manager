### ZERO 3E (`boards/radxa-zero-3e/lemnos-board.toml`): validated

- `lemnos-ctl validate --socs socs --no-live BOARD`: passes (1 device).
- `lemnos-ctl tree --socs socs BOARD -o ... --boot ... --modprobe ...`: passes. The overlay:
  `target-path = "/usb@fcc00000"`: `status = "okay"`, `dr_mode = "peripheral"`, `phys = <&usb2phy0_otg>`,
  `phy-names = "usb2-phy"`; plus `/usb2phy@fe8a0000` and its `otg-port` enabled. No `phy-supply` and no
  `extcon`. The boot fragment and the modprobe file have no entries (the port needs neither).
- The comparison with `boards/radxa-zero-3e/assets/dts/rockchip/rk3566-radxa-zero-3e-gadget.dts` (the
  hand-written dts the bring-up and base products boot): that file only sets `dr_mode = "peripheral"` on
  `usb_host0_xhci`. The generated overlay also sets the controller's `phys` and enables the USB 2 PHY, which
  Lemnos's comment says the base tree disables (not read here). The two are not the same change.
- Not run on a board: the bench ZERO 3E is the first check that the port probes.

### ROCK 5C and ROCK 4D (`lemnos-board.pending.toml`): syntax accepted, still held

- The commented candidates were put in scratch files, uncommented, with `soc = "rk3588"` and `"rk3576"`.
  `lemnos-ctl tree` accepts both (rc 0). The ROCK 5C overlay: `/usb@fc000000` peripheral, `phys = <&u2phy0_otg>`.

### Raze (`components/raze-lemnos-board/files/board.toml`): refused, on record

## Lemnos rule in the device check

`scripts/check-devices.sh` now reads each product's lock as `gaia lock` writes it (the `lockfile`, so
`--write-locks` is covered) and fails the product when two or more Lemnos sources (a `[source.*]` block whose
`url` is the Lemnos repository) pin different commits. The message names the product and the revs:

`check-devices: FAIL products/<p>/product.toml: Lemnos is locked to more than one rev in this product, <rev1> and <rev2>: every Lemnos component of a product must be locked to one rev`

Negative test: the self-test (both `--self-test` and the default self-check) writes a lock with two Lemnos
commits and requires the refusal to name both, and a lock with one commit must pass. Output:
`check-devices: self-test: the Lemnos one-rev rule refuses two revs and passes one`.

## Not done, and why

- **ZERO 3E gadget dts, re-evaluated at Gaia `aa987cc`: expressible, not adopted.**
  - Expressed (scratch copy, not committed): the generated overlay (`lemnos-ctl tree` output at 4a2d3b7d) as the
    board's own source `assets/dts/rockchip/radxa-zero-3e-usb-device.dts`, named in `[kernel]`
    `overlays = ["rockchip/radxa-zero-3e-usb-device"]`. `gaia validate --kind board` passes, and the check
    (`--root` on that copy, `aa987cc`) plans `products/zero-3e-base` (`ok ... (gaia plan)`).
  - Not adopted, for three reasons. (1) The overlay would be a committed copy of generator output: the device
    check cannot regenerate it (no Lemnos binary in the check), so it could go stale on a rev move. (2) A built
    overlay is only applied if the boot path loads it. `components/radxa-zero-3e-extlinux/extlinux.conf` has
    `devicetree` and no `fdtoverlays` line, so the overlay would be built and never applied, and the port would stay
    in host mode. Adopting it needs an extlinux change and the overlay under `/boot`, a boot-path change for a
    board run. (3) Gaia's own plan for generating a board's overlay at build time (F12, "a tool built for the build
    machine, run at build time") is not a route in `aa987cc`'s recipes. So the hand-written
    `rk3566-radxa-zero-3e-gadget.dts` stays; it changes the same `dr_mode` and nothing else.
  - What it would take: a Lemnos-generated overlay produced at build time (Gaia F12), or a committed copy with a
    check that matches it to the locked Lemnos rev, plus `fdtoverlays` in the ZERO 3E extlinux and a board run.
- **Board-side changes.** None. No board, no SSH, nothing booted.

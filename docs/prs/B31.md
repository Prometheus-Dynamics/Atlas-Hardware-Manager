Fragments now set: CONFIG_DW_WATCHDOG=y (rk35xx/assets/linux.fragment, stated although the defconfig has it) and
CONFIG_SUNXI_WATCHDOG=y (sun60i/assets/linux.fragment: the defconfig has it =m, so it had to be set).

Values, one shared drop-in (components/bringup-alive/files/10-watchdog.conf):
- RuntimeWatchdogSec 30s -> 16s. Why: 30 s is not a value the hardware has. On RK35xx dw_wdt picks the smallest TOP that is at
  least the request (dw_wdt.c:123-143): 30 s becomes 2^30/24 MHz = 44.7 s, a slow hang. 16 s becomes 2^29/24 MHz = 22.4 s on RK35xx,
  and is the A733 hardware maximum exactly (served by the hardware, no core pings: watchdog_dev.c:79-96 keeps the core out of it).
  systemd pings every 8 s (half). A PID 1 stall of 16 s or more resets the board (22.4 s on RK35xx).
- RebootWatchdogSec 2min, unchanged. Above the hardware maximum the core does not refuse or clamp: it keeps the watchdog fed while
  the kernel runs (watchdog_dev.c:79-125, watchdog_need_worker and watchdog_next_keepalive), so the request is served. A
  dead kernel is reset by the hardware at most 89.5 s after its last ping (RK35xx) or 16 s (A733). On the A733 the served
  request needs the series patch sunxi-wdt-heartbeat (patches/series:543): without it the mainline driver returns -EINVAL
  for 2 min and systemd disarms the watchdog for the shutdown (that patch's own message says so).

Margin for a slow first boot: the watchdog is not open until PID 1 starts (nothing resets during the kernel or the initramfs).
After that PID 1 pings every 8 s from its event loop. Services do not run in PID 1: a key made in ExecStartPre, a mount, or
a DHCP wait can take longer than 16 s and does not stop the pings. Only a stall of PID 1 itself does.

## Point 2: no-button way back to the loader (SETTLED in round 3; UNVERIFIED on a board)

The register is read by U-Boot v2026.10 (tree: /mnt/nvme-wd/lemnos-gates/tmp/I5i8/u-boot-src, commit 5508406, read with
`git show HEAD:<path>`; the arch/arm/mach-rockchip files are tracked but not on disk in that sparse clone).

### U-Boot: the register and what it acts on
- Per-SoC defaults (ROCKCHIP_BOOT_MODE_REG): RK3568 (the RK3566 defconfig selects ROCKCHIP_RK3568): `default 0xfdc20200`
  (arch/arm/mach-rockchip/rk3568/Kconfig:70-71). RK3576: `default 0x26024040` (rk3576/Kconfig:9-10). RK3588 (the ROCK 5C
  defconfig selects ROCKCHIP_RK3588): `default 0xfd588080` (rk3588/Kconfig:418-419).
- boot_mode.c, setup_boot_mode(): reads the register (line 89), then `writel(BOOT_NORMAL, reg)` (line 97: it clears the register),
  then acts only on:
  `case BOOT_FASTBOOT: env_set("preboot", "setenv preboot; fastboot usb 0")` (lines 100-102) and
  `case BOOT_UMS: env_set("preboot", "setenv preboot; ums mmc 0")` (lines 104-106). There is NO case for BOOT_LOADER (0x5242C301).
  So a `reboot loader` that writes BOOT_BL_DOWNLOAD is read, cleared and ignored.
- The value that sends a board to the BootROM download: BOOT_BROM_DOWNLOAD = 0xEF08A53C (arch/arm/include/asm/arch-rockchip/
  boot_mode.h:19). U-Boot writes it on its own download key (boot_mode.c:25-28, 82).
- bootrom.c:46-59, check_back_to_brom_dnl_flag(): `if (CONFIG_ROCKCHIP_BOOT_MODE_REG) { boot_mode = readl(...);
  if (boot_mode == BOOT_BROM_DOWNLOAD) { writel(0, ...); return true; } }`, and bootrom.c:72-73 returns to the BootROM with
  BROM_BOOT_ENTER_DNL. The comment at bootrom.c:35-45 says the BootROM never checks this register itself: the return is U-Boot's.
- Who calls it: save_boot_params (arch/arm/cpu/armv8/start.S:57) runs at the first stage's entry. bootrom.c is compiled only with
  ROCKCHIP_BROM_HELPER (Makefile:10-12), which is selected by SPL_ROCKCHIP_BACK_TO_BROM or TPL_ROCKCHIP_BACK_TO_BROM
  (mach-rockchip/Kconfig:602-612, 613-620). Those are selected for RK3066, RK3188 and RV1126 (Kconfig:50, 87, 551) only.
  RK3568 selects SPL but not TPL (rk3568/Kconfig:415-425); RK3588 selects SPL but not TPL (Kconfig:499-...). Neither defconfig
  sets the option. So without a line in our fragment the check is not built.
- Config added: families/rk35xx/assets/u-boot.fragment `CONFIG_SPL_ROCKCHIP_BACK_TO_BROM=y` (depends on SPL; selects
  ROCKCHIP_BROM_HELPER and SPL_BOOTROM_SUPPORT). It applies to all three RK35xx boards.

### Round 3: the ROCK 5C LED conflict (reconciled from the resolved config and the sources)
Question: the tree sets `led-1` to heartbeat, Gaia's built image shows no trigger. Which is true for the image?
1. Resolved kernel config (arm64 defconfig + trim.fragment + rk35xx/linux.fragment + radxa-rock-5c/linux.fragment, `make
   olddefconfig` at 7.3.3, the same resolution the fragment check does): CONFIG_LEDS_CLASS=y, CONFIG_LEDS_GPIO=y,
   CONFIG_LEDS_TRIGGER_TIMER=y, CONFIG_LEDS_TRIGGER_HEARTBEAT=y, CONFIG_LEDS_TRIGGER_DEFAULT_ON=y (the resolved .config in the
   scratch out-tree, lines 6393-6492). So the heartbeat trigger is built in.
2. Which dtb: the ROCK 5C extlinux named /boot/rk3588s-rock-5c.dtb (radxa-rock-5c-extlinux/extlinux.conf:7, before this round),
   i.e. the IN-TREE board dtb built from rk3588s-rock-5c.dts (board.toml device_tree). That file has `led-1` with
   default-state "on" (rk3588s-rock-5c.dts:64) and linux,default-trigger = "heartbeat" (rk3588s-rock-5c.dts:67).
3. Does default-state win? No. default-state only sets the initial brightness (drivers/leds/led-core.c:612-623,
   led_init_default_state_get; leds-gpio.c applies it at create). The trigger is attached separately: led_trigger_set_default
   matches a default_trigger at LED registration (led-triggers.c:289-312), and a trigger that registers later binds the LEDs
   whose default_trigger it names (led-triggers.c:344-345). So the source says the heartbeat should run from kernel boot.
4. What I could not reproduce: Gaia's report of "no trigger". No Gaia image or dtb is on disk here, so the cause (a different
   dtb in the image, or a dtb read without the trigger property) is not settled from this side.
5. Fix in this PR: the ROCK 5C now boots its own dtb, /boot/rk3588s-rock-5c-loader.dtb (extlinux updated), which includes the
   in-tree dts and states `linux,default-trigger = "heartbeat"` on `led-1` again (rk3588s-rock-5c-loader.dts, the leds block), so
   the image states the trigger in its own dtb. The unit still sets the heartbeat when it starts. To confirm on Gaia's image:
   `fdtget -t s /boot/rk3588s-rock-5c-loader.dtb /leds/led-1 linux,default-trigger` must print `heartbeat`.
Which LED carries which state on the ROCK 5C: led-0 (colour green, function POWER, default-state on) is the power LED, always
on; led-1 (colour blue, function HEARTBEAT) beats from kernel boot and blinks at 1 s once the Ethernet has its address.

### ROCK 5C and ROCK 4D LED nodes (checked against the trees, 7.3.3 at 28e401350981d74c)
- ROCK 5C (rk3588s-rock-5c.dts:50-65): `led-0` green, function POWER, default-state on, no trigger; `led-1` blue, function
  HEARTBEAT, default-state on, linux,default-trigger = "heartbeat". So the tree does set one heartbeat. Gaia's build of our
  product reports two gpio-leds with default-state "on" and no trigger. The two readings conflict; not reconciled from here (the
  built image's final dts would settle it). The signs do not depend on it after systemd starts: the bring-up unit sets the
  heartbeat on `led-1` and the 1 s blink when the Ethernet has its address. Before systemd, `led-1` is only as Gaia's build has it.
  Which LED carries which state: led-0 (green) = power, always on; led-1 (blue) = heartbeat, then blink on the link.
- ROCK 4D (rk3576-rock-4d.dts): `power-led` green, function STATUS, default-state on; `user-led` blue, function HEARTBEAT,
  linux,default-trigger = "heartbeat" (no default-state). Same rule: power-led = power; user-led = heartbeat, then blink.

### The Ethernet name (the fourth failure)
- Buildroot's BR2_SYSTEM_DHCP="eth0" (base fragments: zero-3e-base:52, rock-5c-base:52, rock-4d-base:52) writes
  /etc/systemd/network/eth0.network with `Name=eth0`. The GMAC is normally named end0 by systemd's predictable naming, so that file
  would never apply and no lease would be asked for. Confirmed the risk is real by the rule, not a board run.
- Fix: every bring-up product's own os.fragment sets `# BR2_SYSTEM_DHCP is not set` (it comes after the base, so it wins):
  zero-3e-bringup/os.fragment, rock-5c-bringup/os.fragment, rock-4d-bringup/os.fragment, and cubie-a7-bringup/os.fragment (which
  set `BR2_SYSTEM_DHCP="eth0"` itself: that line was replaced).
- New shared component devices/components/bringup-network: 10-bringup-ethernet.network with `[Match] Type=ether, Name=!usb0`,
  `[Network] DHCP=yes`, installed to /etc/systemd/network/10-bringup-ethernet.network; enables systemd-networkd.service. Type=ether
  finds the GMAC under any name. Name=!usb0 keeps networkd off the gadget's interface.
- The gadget's interface name is exactly `usb0`: usb-gadget-network's script S41usb0 (Gaia 7177d72,
  examples/components/usb-gadget-network/files/S41usb0) creates `functions/ncm.usb0` (line 74) and runs
  `ifconfig usb0 10.55.0.1 netmask 255.255.255.0 up` (line 94), and it names usb0 in every message. No wildcard is used for it.
- The LED link and the network file agree, derived from one fact per product (the link the user reaches the board by):
  | product | reached by | LED link setting (files/board-alive.links) | network that matches it |
  |---|---|---|---|
  | zero-3e-bringup | the USB gadget, usb0 | `usb0` | usb-gadget-network creates usb0; bringup-network excludes usb0 |
  | cubie-a7-bringup | the USB gadget, usb0 | `usb0` | same |
  | rock-5c-bringup | the only Ethernet | `ether` | bringup-network, Type=ether |
  | rock-4d-bringup | the only Ethernet | `ether` | bringup-network, Type=ether |
  The LED script (board-alive-led) resolves `ether` as: any sysfs link of type 1 except usb0, the same set networkd matches.
- The gate rule (bringup_rule, extended) checks: the product lists bringup-network; its own os.fragment unsets BR2_SYSTEM_DHCP;
  the bringup-network file matches Type=ether and never a legacy `Name=eth0` (comments excluded); and each LED link is `ether`
  (needs bringup-network) or `usb0` (needs usb-gadget-network); any other name is refused. Self-test refuses all four cases on
  a scratch copy (eth0 as a link; DHCP left on; a network file matched by name) and passes the real tree.

## Scope change (round 3, from the coordinator): the Cubie A7S does not build
Gaia's build of cubie-a7-bringup stopped in TF-A ("Invalid platform (sun60i_a733)"): devices/families/sun60i/family.toml names
three patch series (TF-A, U-Boot, kernel) in comments and nothing applies them. So this PR lands for the three RK35xx bring-up
products (ZERO 3E, ROCK 5C, ROCK 4D). The Cubie keeps its plain-data changes (the shared bring-up component in its product, the
network file, the LED link setting `usb0`, the bare-# fix), is excused BY NAME in the gate rule for the loader point (the rule
prints a NOTE with the reason), and carries the banner "Planned, not built. Cannot build today: the TF-A, U-Boot and kernel
patch series this family names are applied by nothing." as the first line of its README, product.toml and the sun60i family.toml.
The A733 chain itself is not fixed here.

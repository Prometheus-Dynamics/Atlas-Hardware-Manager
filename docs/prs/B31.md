## Point 1: watchdog armed (all four)

Systemd is the init on all four bring-up products (BR2_INIT_SYSTEMD=y: zero-3e-base/os.fragment:18, rock-5c-base/os.fragment:18,
rock-4d-base/os.fragment:18, cubie-a7-bringup/os.fragment:12). No BusyBox-init product exists, so the drop-in is the mechanism.
The bases say no RuntimeWatchdogSec is set; the bring-up component adds it only to bring-up products, so the managed bases
are unchanged.

Fragments now set: CONFIG_DW_WATCHDOG=y (rk35xx/assets/linux.fragment, stated although the defconfig has it) and
CONFIG_SUNXI_WATCHDOG=y (sun60i/assets/linux.fragment: the defconfig has it =m, so it had to be set).

Values, one shared drop-in (components/bringup-alive/files/10-watchdog.conf):
- RuntimeWatchdogSec 30s -> 16s. Why: 30 s is not a value the hardware has. On RK35xx dw_wdt picks the smallest TOP that is at
  least the request (dw_wdt.c:123-143): 30 s becomes 2^30/24 MHz = 44.7 s, a slow hang. 16 s becomes 2^29/24 MHz = 22.4 s on RK35xx,
  and is the A733 hardware maximum exactly (served by the hardware, no core pings: watchdog_dev.c:79-96 keeps the core out of it).
  systemd pings every 8 s (half). A PID 1 stall of 16 s or more resets the board (22.4 s on RK35xx).
- RebootWatchdogSec 2min, unchanged. Above the hardware maximum the core does not refuse or clamp: it keeps the watchdog fed while
  the kernel runs (watchdog_dev.c:79-125, watchdog_need_worker and watchdog_next_keepalive), so the request is served. A
  dead kernel is reset by the hardware at most 89.5 s after its last ping (RK35xx) or 16 s (A733). On the A733 the served
  request needs the series patch sunxi-wdt-heartbeat (patches/series:543): without it the mainline driver returns -EINVAL
  for 2 min and systemd disarms the watchdog for the shutdown (that patch's own message says so).

Margin for a slow first boot: the watchdog is not open until PID 1 starts (nothing resets during the kernel or the initramfs).
After that PID 1 pings every 8 s from its event loop. Services do not run in PID 1: a key made in ExecStartPre, a mount, or
a DHCP wait can take longer than 16 s and does not stop the pings. Only a stall of PID 1 itself does.

## Point 2: no-button way back to the loader

Kernel (v7.3.3, 28e401350981d74c):
- CONFIG_SYSCON_REBOOT_MODE=y is in arm64 defconfig:751 (drivers/power/reset/Kconfig:333).
- No SoC dtsi carries a reboot-mode node for RK3566, RK3588 or RK3576 (grep of arch/arm64/boot/dts/rockchip/*.dtsi: the nodes
  exist for px30, rk3328, rk3308, rk3562, rk3368 and the LCKFB RK3566 board only).
- Where it belongs (the PMU GRF syscon, which is simple-mfd, so it takes a child node):
  - RK3566/RK3568: pmugrf, syscon@fdc20000 (rk356x-base.dtsi:367-369).
  - RK3588/RK3588S: the dtsi has pmu1grf@fd58a000 (rk3588-base.dtsi:577-580). U-Boot's register is 0xfd588080 (below), which
    is not inside that node, and no other rk3588 node at 0xfd588000 exists in the tree. UNVERIFIED mapping: not added.
  - RK3576: pmu0_grf, syscon@26024000, simple-mfd (rk3576.dtsi:876-879).
- Offsets and values, from the binding and the in-tree example: include/dt-bindings/soc/rockchip,boot-mode.h defines BOOT_NORMAL
  (REBOOT_FLAG+0), BOOT_BL_DOWNLOAD (+1), BOOT_RECOVERY (+3), BOOT_FASTBOOT (+9), with REBOOT_FLAG=0x5242C300. There is no
  BOOT_BOOTLOADER. The in-tree RK3566 LCKFB board uses offset 0x200 under pmugrf, mode-loader=BOOT_BL_DOWNLOAD,
  mode-bootloader=BOOT_FASTBOOT (rk3566-lckfb-tspi.dts:554-562); rk3562.dtsi:530-538 is the same shape.
  Dt-bindings pmu.yaml:63-70 allows only mode-bootloader, -loader, -normal, -recovery: "mode-fastboot" (the brief's key) is refused.

U-Boot (v2026.10, the tree at /mnt/ssd-samsung/gaia/tmp/ev/ub/u-boot-2026.10, VERSION 2026 PATCHLEVEL 10):
- The boot-mode register addresses (ROCKCHIP_BOOT_MODE_REG, Kconfig defaults): RK3568 (and the RK3566 defconfig, which selects
  CONFIG_ROCKCHIP_RK3568=y): 0xfdc20200 = pmugrf 0xfdc20000 + 0x200 (arch/arm/mach-rockchip/rk3568/Kconfig:70-71). RK3576:
  0x26024040 = pmu0_grf + 0x40 (rk3576/Kconfig:9). RK3588: 0xfd588080 (rk3588/Kconfig:418).
- setup_boot_mode() (boot_mode.c:86-111, called from board_late_init at board.c:195) reads the register, clears it to
  BOOT_NORMAL, and acts only on BOOT_FASTBOOT (env preboot "fastboot usb 0") and BOOT_UMS. It does NOT act on BOOT_LOADER
  (0x5242C301). So a BOOT_BL_DOWNLOAD written by `reboot loader` is read, cleared and ignored by U-Boot.
- The value that does take a board into the BootROM's download is BOOT_BROM_DOWNLOAD = 0xEF08A53C
  (arch/arm/include/asm/arch-rockchip/boot_mode.h:19). U-Boot's own download-key path writes it and resets
  (boot_mode.c:25-28, 82). The early check is bootrom.c:46-59 (check_back_to_brom_dnl_flag: if the register holds 0xEF08A53C,
  clear it and return to the BootROM's download, bootrom.c:72-73). bootrom.c's own comment (bootrom.c:35-45) says the BootROM
  does not check this register itself: so the loader entry depends on U-Boot, and U-Boot does it only for 0xEF08A53C.
- The early check is compiled only with ROCKCHIP_BROM_HELPER, selected by SPL_ROCKCHIP_BACK_TO_BROM or TPL_ROCKCHIP_BACK_TO_BROM
  (arch/arm/mach-rockchip/Kconfig:50, 87, 551 select them for RK3066, RK3188 and RV1126 only). The RK3566 defconfig
  (configs/radxa-zero-3-rk3566_defconfig) and the RK3576 board defconfig enable neither TPL nor the option, so the check is
  absent from the build. Config symbol needed: CONFIG_SPL_ROCKCHIP_BACK_TO_BROM=y (depends on SPL, which the RK3568 selects,
  Kconfig:415-425); it selects ROCKCHIP_BROM_HELPER and SPL_BOOTROM_SUPPORT. Added to families/rk35xx/assets/u-boot.fragment.
- Mode table:
  | reboot mode | value written (kernel) | what U-Boot v2026.10 does | what the BootROM does |
  |---|---|---|---|
  | normal | BOOT_NORMAL | cleared, boots | nothing |
  | loader | 0xEF08A53C (our choice, see the node) | back to BootROM download (with the option above) | rockusb download (closed code: UNVERIFIED) |
  | loader, with the mainline value BOOT_BL_DOWNLOAD | 0x5242C301 | cleared, ignored (boot_mode.c:99-108) | the tree says it never reads the register (bootrom.c:35-45): UNVERIFIED |
  | bootloader | BOOT_FASTBOOT | `fastboot usb 0` preboot; the command is only there if fastboot is built in (radxa-zero-3 defconfig: USB_FUNCTION_FASTBOOT not set) | nothing |
  | recovery | BOOT_RECOVERY | nothing in this tree | nothing |

  /etc/board-alive.leds and the links in /etc/board-alive.links, and changes nothing when a file is absent. The example

  - ROCK 5C: LED led-1; link eth0 (the only link; BR2_SYSTEM_DHCP=eth0 in the base).
  - ROCK 4D: LED user-led; link eth0 (the only link).
  - Cubie A7S: LED status-led; link usb0.
- Fragment lines (each is already =y in the arm64 defconfig, written so a defconfig change cannot drop one):
  CONFIG_LEDS_TRIGGER_HEARTBEAT=y and CONFIG_LEDS_TRIGGER_TIMER=y in rk35xx (defconfig:1333, :1331); CONFIG_LEDS_TRIGGER_TIMER=y in
  sun60i (the heartbeat was already there). CONFIG_LEDS_TRIGGER_NETDEV is NOT added: the timer trigger does the second state, and
  the netdev trigger would need a per-interface name the script already gets from its link list.
- The service never gives up (StartLimitIntervalSec=0, Restart=always, RestartSec=2: failure-handling rule).

What a person sees (the table is in each product's README):
| State | ZERO 3E | ROCK 5C | ROCK 4D | Cubie A7S |
|---|---|---|---|---|
| Power on, before kernel | off | off (blue), green on after the driver binds | off (blue), green on after the driver binds | off |
| Kernel alive, before systemd | green beats (the tree's trigger) | blue beats (the tree's trigger) | blue beats | blue beats (the dts's trigger) |
| systemd up, link has no address | beats | beats | beats | beats |
| link has its address | 1 s blink | 1 s blink | 1 s blink | 1 s blink |
| Hung (PID 1 stalled) | the last pattern keeps running (kernel triggers); after about 22 s the watchdog resets; the cycle restarts | same | same | same |

A hang is therefore visible only as the reset cycle, not as a stopped beat: the triggers run in the kernel. That is a limit of
the design, stated in the LED script's header.

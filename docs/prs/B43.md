# B43: check-devices checks the board's DHCP server against the lemnos0 scheme

**Group:** B. Board descriptions

**Needs:** B24

The board's address and the pool it hands the PC are computed at boot by `lemnos0-address` from
`lemnos0-addressing.conf` (serial-hash-v1: a /29 in 172.31.0.0/16, minus 172.31.250.0/24; the board takes network+1).
On Raze #2 on 2026-11-22 that gave 172.31.209.217/29 with the pool .218–.222, and the server answered on UDP 67. The PC
still got no lease; that was its own NetworkManager setting (no-auto-default), the user's to change. Nothing in
`scripts/check-devices.sh` checks the server side as data, so a wrong pool or a missing server would show only on a
board.

## Build

`scripts/check-devices.sh` (with `scripts/check-lemnos0-address.py`) refuses, naming the file and the key:
- a product with lemnos0 addressing whose network file has no `DHCPServer=yes`;
- a pool that is not exactly the /29's hosts minus the board's own address (no network, broadcast or board address
  handed out, nothing outside the /29);
- a lease time other than the conf's `lease_seconds`;
- a server that offers a default route or DNS. The PC must not route through the board: that is what keeps it safe for
  a PC's network manager to bring the link up by itself.

Each refusal has a self-test case.

## Proof

The self-test cases fail before the change and pass after; raze-base and zero-3e-bench pass.

9. **`devices/README.md`**: the layout line, the `[descriptions]` and `storage_drivers` keys, a section "The Lemnos board file",

## Where the INPUTS.md wording differs from Gaia at `e1cc295`

Gaia at the pin wins. Each difference is listed:

1. **A missing description file is refused at validate, not only at plan.** INPUTS.md (Gaia confirms) says plan/validate
   catch a description file that does not exist, and that `gaia validate` runs no step. At `e1cc295`, `gaia validate` on the
   board names the file and refuses it (case B above). Plan refuses it too.
2. **The check's gaia.lock comparison also fails for case B.** Not a Gaia refusal as such: with the file gone the committed lock
   no longer matches the descriptions (`check-devices` reports `gaia.lock beside it does not match the descriptions`).
3. **Gaia's `storage_drivers` is checked only under a `kernel_contract`.** INPUTS.md's table implies a check on every
   build. At the pin, `storage_drivers` is read by the kernel-contract step (`crates/core/graph/src/wire.rs`, the
   `kernel.storage_drivers` error) and nowhere else. The key's form (`CONFIG_NAME`) is checked there too.
4. **The bring-up gadget does not get its identity by default at `4509f6b`.** INPUTS.md says the products get `1d6b:0103`
   at this rev. True at `e1cc295`; at `4509f6b` the component's script presented `1d6b:0104`. The move of the source
   `ref` is what changes it, not any product description.
5. **`check-devices` counts 14 components** (the B22 text said 13): the count is what the check prints; no component was
   added in B26.

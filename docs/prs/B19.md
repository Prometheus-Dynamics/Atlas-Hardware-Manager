## Part 3: the boot chain, and where each part comes from

Order the boot ROM loads them, from the SD card (or FEL, see Part 5):

1. **BROM** (mask ROM) reads one file from the card at **128 KiB** (sector 256): `u-boot-sunxi-with-spl.bin`. UNVERIFIED: the 128 KiB rule is from DockSeed's `docs/boot-chain.md` (their A7S card test), not a board run here.
2. That file is **U-Boot SPL**, which runs the **closed DRAM init** (`ddr.bin`, built in through `SUNXI_LIBDRAM`) and then **BL31** (TF-A, built from source in the same make).
3. **U-Boot** (Radxa's tree plus DockSeed's patches), reading `/boot/extlinux/extlinux.conf` from the first partition (the rootfs, at 16 MiB).
4. **Linux 7.3.4** with the series, and the bring-up dtb.

**SCP:** nothing in this chain loads an SCP firmware blob. Whether the A733 needs one (PSCI, DVFS) is OPEN, not read in B19.

## Part 4: the three signs of life, and how each is produced

The bring-up board is `devices/pending/cubie-a7-bringup/board/`. Each sign comes from the kernel config or the device tree, not from userspace, so each works with no Lemnos, no Orion and no console.

1. **LED heartbeat (the first sign).** The blue status LED is `status-led`, GPIO PJ26 (`&pio 9 26`), from DockSeed's LED patch. The bring-up dts adds `linux,default-trigger = "heartbeat"` to it (`assets/dts/...-bringup.dts`, compiled and checked in B19 with dtc: the dtb's `status-led` carries `linux,default-trigger = "heartbeat"`). The kernel fragment has `CONFIG_LEDS_CLASS=y`, `CONFIG_LEDS_GPIO=y`, `CONFIG_LEDS_TRIGGER_HEARTBEAT=y`, all resolved to `=y`. The power LED (`power-led`, PM2, green) is on by DockSeed's default. U-Boot shows nothing (no LED code in this chain), so the first visible sign is the kernel's heartbeat.
2. **USB network on the PC.** Legacy `g_ether`, built in (`CONFIG_USB_ETH=y`, `CONFIG_USB_ETH_RNDIS=y`, `assets/bringup.fragment`). It binds the MUSB controller at boot, with no userspace, so it appears as soon as the kernel finds the controller. It presents RNDIS (Windows 10 and later bind it with no driver) and CDC ECM (Linux, macOS). MACs from extlinux: device `02:a7:01:00:00:01`, host `02:a7:01:00:00:02` (locally administered, unicast, not the ZERO 3E's). Why built in and not configfs: configfs needs a userspace that is not in this image, and a gadget that binds at boot is the earliest enumeration. The gadget must never reach a managed image (Lemnos's configfs gadget needs the same controller).
3. **Ethernet DHCP and usb0 DHCP.** eth0 is `CONFIG_STMMAC_ETH`, `CONFIG_STMMAC_PLATFORM`, `CONFIG_DWMAC_SUN55I` (built in): a DHCP client through systemd-networkd (`BR2_SYSTEM_DHCP="eth0"`). usb0 is the board's own DHCP server (systemd-networkd `DHCPServer=yes`, `10-usb0.network`, board `10.55.0.1/24`, PC gets `10.55.0.2`). The ZERO 3E's lesson: its BusyBox `udhcpd` never ran on the read-only root, so the PC got no IPv4. This one uses networkd, which keeps its state in /run. **Not checked on a board.**
4. **SSH with the bench key** (dropbear, `-s`: key only, `components/dev-bench-ssh-key/dropbear.default`). Port 22, on eth0 and usb0.

The serial console stays configured (getty on ttyS0, root login with no password, the base's default policy), with no adapter attached. It is not one of the three signs.

## What you should see (the test procedure, with no serial console)

Expectations, not observations. Nothing has been run. Timings are the order of events, not measured.

| Step | What you should see | If it is missing, boot stopped at |
|---|---|---|
| Power on (USB-C 1 with a 5 V supply, or the PC on USB-C 1) | The **green power LED** is lit at once (DockSeed's default-on). | The board is not powered. Check the supply first. The power LED is not an OS sign. |
| Card boots | The **blue status LED starts a heartbeat blink** a few seconds after power, once the kernel's LED driver loads. | Before the kernel: BROM, SPL (DRAM init), BL31 or U-Boot. There is no LED sign there, so this is the boundary: no blink = the kernel never started. Check the card layout (u-boot at 128 KiB) and the SPL's DRAM init first. |
| USB network appears on the PC | A **new network interface** appears on the PC when USB-C 1 is connected: "Remote NDIS" on Windows, a new `usb0`/`enx…` (CDC ECM) on Linux or macOS. Its address comes from the board (next row). `lsusb` shows the gadget with vendor `1d6b` (Linux Foundation, g_ether's default). | The kernel is up (the LED blinks) but the controller is not: check the port (it must be USB-C 1, not USB-C 2), the cable (data, not power-only), and the MUSB/PHY lines in the log if there is any. |
| usb0 DHCP | The PC gets `10.55.0.2` from the board. `ip addr` on the PC shows it; the board is at `10.55.0.1`. | The interface is up but networkd's DHCP server is not running on usb0. Set the PC's address by hand (`10.55.0.2/24`) and ping `10.55.0.1`; if that answers, the server is the fault. |
| Ethernet DHCP | The **board's eth0 lease** shows in the LAN router's DHCP table (or `arp -a` from a PC on the LAN finds the board's MAC). | The GMAC or its PHY is not up (the kernel is up, the USB network is up, so the kernel and the USB path work). Check the cable and the link LED on the RJ45. |
| SSH | `ssh -i <bench key> root@10.55.0.1` works (usb0), or `root@<eth0 lease>`. Key only. | The network is up but dropbear is not: the dropbear unit, or the key file (`authorized_keys` in the image). |

What each missing sign tells you about where boot stopped:
- No LED, no USB, no Ethernet: boot stopped before the kernel (BROM, SPL, DRAM, BL31 or U-Boot). The first step is the card layout and the SPL.
- LED blinks, no USB: the kernel runs; the USB controller or its PHY did not come up.
- LED and USB, no DHCP on usb0: networkd's DHCP server on the bring-up board.
- LED and USB and usb0 DHCP, no Ethernet lease: the GMAC or the cable or LAN.
- Everything but SSH: dropbear or the key.

## Part 5: the device-capable port, and VBUS, per board

Radxa's pages, read 2026-11-13 (no schematic read in B19):

- **Cubie A7S**: USB-C 1 ("USB 2.0, 5V power input and OTG") is the device-capable port. In DockSeed's dts it is the MUSB controller `usb_otg` (PHY index 0), set to `dr_mode = "peripheral"` by its gadget patch. The dts names it "the Type-C port J16 is the board's 5 V input" (DockSeed's comment). The match to Radxa's "USB-C 1" is by function, not by a schematic: OPEN, confirm against the schematic's USB-C page.
  - **VBUS finding (the B15 lesson):** the PHY's VBUS supply is named per index in the series' PHY driver (`usb%d_vbus`, `drivers/phy/allwinner/phy-sun4i-usb.c`, line 819). PHY 0 is `usb0_vbus`, and the A7S dts sets only `usb1_vbus` (the USB 2 host ports). So **device mode on USB-C 1 sources no 5 V**. The compiled bring-up dtb shows `usb@4100000` with `dr_mode = "peripheral"` and no supply. The GMAC's `phy-supply` is its own PHY rail, not USB.
  - USB-C 2 ("USB 3.2, DisplayPort and OTG") is host-only in DockSeed's dts, sourcing VBUS from `DRVVBUS` (PL2) through its own regulator. Not a device port.
- **Cubie A7A**: the only device-capable port on Radxa's page is "USB Type-C 1x OTG/power" (USB 2.0). Which PHY index, and whether the board sources VBUS: UNKNOWN, no dts. A device-mode entry is not written until the A7A dts shows no VBUS on that index (the B15 rule).
- **Cubie A7Z**: no dts and no defconfig in any public source read. UNKNOWN.

## Part 7: how the first proof gets on the board: SD card, not FEL

- **SD card (first proof):** the bring-up product's `sd-image` (`sdcard.img`) is written to a microSD card with dd or Etcher by the user. The card carries `u-boot-sunxi-with-spl.bin` at 128 KiB and the first partition at 16 MiB. Gaia builds it, and Atlas does not build the OS image here (out of scope).
- **FEL (not for the first proof):** the FEL crate (`crates/flash/fel`) is ARMv7 only: its thunk (`src/thunk.S`) is ARMv7, and `src/layout.rs` refuses any AArch64 layout ("no AArch64 thunk is written; the A733's FEL state is UNCONFIRMED"). So the A733 cannot be loaded over FEL by Atlas today. Writing that thunk and the sun60i SRAM layout is a Rust change to `crates/flash/fel`, out of scope for B19 (no Rust crate changes here). Nothing copied from sunxi-tools or any GPL source.

Why SD first: it needs no new Rust, the user has SD cards, and the boot ROM's SD path is the one DockSeed tested on the A7S. FEL stays a later proof.

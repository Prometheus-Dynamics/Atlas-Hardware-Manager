## Build

The flow, the same for every family, decided 2026-11-13:

1. **Loader.** The boot ROM loader gets U-Boot running from RAM (Rockchip: 471 DDR init, then 472 with U-Boot as the payload; Allwinner: FEL loads the SPL, then U-Boot; K230: the same if its boot ROM allows it). The Pi skips this step: its boot files start the flasher directly through rpiboot.
2. **U-Boot fastboot.** `atlas-fastboot` downloads and boots the flasher kernel and initramfs (B9's image for the family).
3. **The flasher boots.** It is a RAM-only initramfs: BusyBox init, lemnosd, the bridge and Orion's recovery build. No slots and no partitions are assumed on the board.
4. **An Orion node on the USB link.** The board appears with `hello.state = flasher`. Atlas tells a flasher from a running OS by that fact and nothing else.
5. **Atlas pushes the first-flash image as a file** over the session (`Files::push`, resumable after a lost session, as C4).
6. **Lemnos's `system.flash/1` `write`.** A blank board has nowhere for `install_file` to put a file, so the write is Lemnos's first-flash driver (brief: `/mnt/nvme-wd/lemnos-gates/W1-actions.md`, PROVISIONAL until Lemnos W1 and W2 land; mark what is built to it). The target is named only in the board file. The build's only output is the `.img.xz`. Atlas makes the `flash.json` manifest (schema 1: board, format, raw size and SHA-256) from the image when it flashes, in one streamed pass (D15), and carries an optional detached `flash.sig` beside the image under the same rule as slots. Atlas refuses an image whose board (read from its slots) is not this board before pushing anything, and it reads that board early in the pass so a wrong image is refused before the stream is decoded to the end. `write` is a long job fed in order by the file push, with Orion's chunk acknowledgements as back-pressure, and verified by read-back. Atlas starts it, follows its progress and reads its outcome. Atlas writes nothing to the board's storage itself. Raw NAND is refused in this version.
   The board shows the same states the app does: `indicator/1` has `idle`, `receiving`, `writing`, `verifying`, `done` and `failed` with a progress fraction. The app's flash flow names its steps after those states.
7. **Reboot into the one slot.** The board comes back as an ordinary node; the flow ends when its `hello.version.slot` is the image just written.

The same flow recovers a broken board. It runs detached, so it survives the app closing. Every step retries without limit with a short backoff and can be stopped by hand; a step never gives up on its own.

Outside blocks (the action and topic names come from their owners; do not invent them): Lemnos's raw first-flash action and LED progress states; Orion's `link-usb` in the recovery build and `hello.state`; Gaia's flasher outputs (PR 44).

## A board that cannot boot must not sit dead (the bar, point 2)

For each family this PR states, with the source of each claim, what the image must set so that a board with no
bootable slot enters USB boot or recovery by itself, and whether that is achievable:

- BCM2712 (Raze): the EEPROM boot order ends in USB boot (rpiboot), so a failed eMMC boot falls through to it. To state:
  the BOOT_ORDER value, who sets it (the image, the first flash, or the factory), and whether a boot partition that is
  present but broken falls through or hangs.
- RK35xx: the boot ROM enters maskrom when it finds no valid loader on any medium. To state: what "no valid loader"
  covers (a present idbloader with a broken U-Boot or kernel does NOT reach maskrom), and what the loader chain must do
  itself in that case (U-Boot falling back to its USB download mode).
- A733 (sun60i): the boot ROM enters FEL when no valid boot image is found. To state: the same limit as RK35xx, and what
  U-Boot must do.

A family that cannot meet this is named here and reported; it is not papered over with a retry loop on a dead board.

## The bar (user, 2026-11-13): nobody touches a board

The user had to handle three boards by hand in one day and asked whether `next` is on par, so that everything is done
through Atlas. This is the bar for `next` going onto any bench board. Every PR in D6, E2, E3 and F8 is accepted against
it, and the simulated node and bus prove each point:

1. From the PC, one command each, no SSH, no manual copy, no port argument:
   - list every board, including one in USB boot or maskrom behind a gateway, with its gateway path;
   - flash one (`atlas flash --image X` with exactly one such board anywhere just flashes it; `--device` picks among
     several);
   - restart a RUNNING board into USB boot remotely (the board's `usb-boot` action), so a reflash never needs the boot
     button;
   - install, trial and roll back a slot;
   - read why the last boot ended.
2. A board that fails to boot a slot returns to the previous one by itself. A board with no bootable slot enters USB
   boot or recovery by itself and does not sit dead. Per family, what the image must set and whether it is achievable
   is stated in D6 (BCM2712: the boot order falls through to USB boot; RK35xx: the boot ROM's maskrom when no valid
   loader is found; A733: FEL). A family that cannot meet it is named, not hidden.
3. `atlas doctor` reports boards in USB boot or maskrom behind gateways as well as on the PC's own USB.

Test with a simulated loader and the simulated node; board runs in G1 and G3.

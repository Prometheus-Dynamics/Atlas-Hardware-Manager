## Build

The flow, the same for every family, decided 2026-11-13:

1. **Loader.** The boot ROM loader gets U-Boot running from RAM (Rockchip: 471 DDR init, then 472 with U-Boot as the payload; Allwinner: FEL loads the SPL, then U-Boot; K230: the same if its boot ROM allows it). The Pi skips this step: its boot files start the flasher directly through rpiboot.
2. **U-Boot fastboot.** `atlas-fastboot` downloads and boots the flasher kernel and initramfs (B9's image for the family).
3. **The flasher boots.** It is a RAM-only initramfs: BusyBox init, lemnosd, the bridge and Orion's recovery build. No slots and no partitions are assumed on the board.
4. **An Orion node on the USB link.** The board appears with `hello.state = flasher`. Atlas tells a flasher from a running OS by that fact and nothing else.
5. **Atlas pushes the first-flash image as a file** over the session (`Files::push`, resumable after a lost session, as C4).
6. **Lemnos's `system.flash/1` `write`.** A blank board has nowhere for `install_file` to put a file, so the write is Lemnos's first-flash driver (brief: `/mnt/nvme-wd/lemnos-gates/W1-actions.md`, PROVISIONAL until Lemnos W1 and W2 land; mark what is built to it). The target is named only in the board file. The build's only output is the `.img.xz`. Atlas makes the `flash.json` manifest (schema 1: board, format, raw size and SHA-256) from the image when it flashes, in one streamed pass (D15), and carries an optional detached `flash.sig` beside the image under the same rule as slots. Atlas refuses an image whose board (read from its slots) is not this board before pushing anything, and it reads that board early in the pass so a wrong image is refused before the stream is decoded to the end. `write` is a long job fed in order by the file push, with Orion's chunk acknowledgements as back-pressure, and verified by read-back. Atlas starts it, follows its progress and reads its outcome. Atlas writes nothing to the board's storage itself. Raw NAND is refused in this version.
   The board shows the same states the app does: `indicator/1` has `idle`, `receiving`, `writing`, `verifying`, `done` and `failed` with a progress fraction. The app's flash flow names its steps after those states.
7. **Reboot into the one slot.** The board comes back as an ordinary node; the flow ends when its `hello.version.slot` is the image just written.

The same flow recovers a broken board. It runs detached, so it survives the app closing. Every step retries without limit with a short backoff and can be stopped by hand; a step never gives up on its own.

Outside blocks (the action and topic names come from their owners; do not invent them): Lemnos's raw first-flash action and LED progress states; Orion's `link-usb` in the recovery build and `hello.state`; Gaia's flasher outputs (PR 44).

## A board that cannot boot must not sit dead (the bar, point 2)

For each family this PR states, with the source of each claim, what the image must set so that a board with no
bootable slot enters USB boot or recovery by itself, and whether that is achievable:

- BCM2712 (Raze): the EEPROM boot order ends in USB boot (rpiboot), so a failed eMMC boot falls through to it. To state:
  the BOOT_ORDER value, who sets it (the image, the first flash, or the factory), and whether a boot partition that is
  present but broken falls through or hangs.
- RK35xx: the boot ROM enters maskrom when it finds no valid loader on any medium. To state: what "no valid loader"
  covers (a present idbloader with a broken U-Boot or kernel does NOT reach maskrom), and what the loader chain must do
  itself in that case (U-Boot falling back to its USB download mode).
- A733 (sun60i): the boot ROM enters FEL when no valid boot image is found. To state: the same limit as RK35xx, and what
  U-Boot must do.

A family that cannot meet this is named here and reported; it is not papered over with a retry loop on a dead board.

### BCM2712: the bootloader's BOOT_ORDER (measured 2026-11-13)

Measured on both Razes with `vcgencmd bootloader_config` (dev slot 993, bootloader 2025/12/08, 2226a853):
`BOOT_UART=1`, `POWER_OFF_ON_HALT=1`, `BOOT_ORDER=0xf2461`. The digits are read right to left (Raspberry Pi's
bootloader configuration documentation, "BOOT_ORDER": "read right to left, and up to eight digits can be defined"):
1 SD card or eMMC, 6 NVMe, 4 USB mass storage, 2 network, f restart. There is no 3 (RPIBOOT: "Boot via usbboot.
Normally enabled implicitly by the nRPIBOOT jumper on a CM4 or CM5 IO board"). So today a Raze whose eMMC has nothing
bootable loops through NVMe, USB mass storage and network and never offers USB device boot by itself. That is why the
boot button was needed.

To design in this PR, each with its source and none of it assumed:

1. The value. Proposed `BOOT_ORDER=0xf31`: eMMC, then RPIBOOT, then restart. No network boot (a robot never wants it,
   and it costs seconds per loop), no NVMe, no USB mass storage. Check each code and anything CM5-specific against the
   bootloader documentation and the rpi-eeprom release notes for the bootloader version on the boards. To state: what the
   bootloader does in RPIBOOT mode when no host answers (how long it waits before the next digit), so the loop's period
   is known.
2. How the first flash writes it. The EEPROM update goes through rpiboot's recovery path (`recovery.bin` over USB device
   boot, the EEPROM image with its `.sig` sha256 as the firmware requires). The config is part of the EEPROM image:
   say how the image with our config is produced, from which pinned rpi-eeprom release, and that the bootloader
   VERSION is not changed unless that is decided separately.
3. How a RUNNING board's value is read and corrected without a reflash. Reading: the firmware interface the dev image's
   `vcgencmd bootloader_config` uses. Correcting: `rpi-eeprom-config --apply` schedules the update as files on the
   boot partition (`pieeprom.upd`, `pieeprom.sig`, `recovery.bin`) for the next reboot; but from the Lemnos L2 move the
   boot partition is never mounted read-write at run time. So say how the update is delivered there (a Lemnos action
   that places those files as it places a slot's; or only through USB boot), and who owns that action.
4. `atlas doctor` reports a board whose BOOT_ORDER is not ours, with the value read and the value expected.

This writes the boards' SPI flash. It is designed here and proven in the simulator where the simulator can model it
(the loader side: a simulated board with nothing bootable shows up in USB boot without a button). On hardware it is
ONE reviewed step on one Raze before it becomes the default. No test writes an EEPROM.

### RK35xx and A733: what the boot script must do

The boot ROM's own fallback (maskrom; FEL) covers only "no valid loader on any medium". With a valid loader and no
bootable slot the fallback is U-Boot's: the boot script, after the slot record's default and previous both fail, enters
U-Boot's USB download mode (fastboot over the OTG port; rockusb on RK35xx as an alternative) instead of stopping at a
prompt. That script (`boot.cmd`) is Lemnos's; this PR states the requirement to Lemnos through the coordinator with the
U-Boot config symbols it needs, and states the uncovered case plainly: a damaged U-Boot behind a valid SPL still needs
the maskrom or FEL button. The loader area is outside the slots and no slot install rewrites it.

## The bar (user, 2026-11-13): nobody touches a board

The user had to handle three boards by hand in one day and asked whether `next` is on par, so that everything is done
through Atlas. This is the bar for `next` going onto any bench board. Every PR in D6, E2, E3 and F8 is accepted against
it, and the simulated node and bus prove each point:

1. From the PC, one command each, no SSH, no manual copy, no port argument:
   - list every board, including one in USB boot or maskrom behind a gateway, with its gateway path;
   - flash one (`atlas flash --image X` with exactly one such board anywhere just flashes it; `--device` picks among
     several);
   - restart a RUNNING board into USB boot remotely (the board's `usb-boot` action), so a reflash never needs the boot
     button;
   - install, trial and roll back a slot;
   - read why the last boot ended.
2. A board that fails to boot a slot returns to the previous one by itself. A board with no bootable slot enters USB
   boot or recovery by itself and does not sit dead. Per family, what the image must set and whether it is achievable
   is stated in D6 (BCM2712: the boot order falls through to USB boot; RK35xx: the boot ROM's maskrom when no valid
   loader is found; A733: FEL). A family that cannot meet it is named, not hidden.
3. `atlas doctor` reports boards in USB boot or maskrom behind gateways as well as on the PC's own USB.

## The flow library as built (2026-11-22, pr/D6)

`crates/core/flash-flow` (`atlas-flash-flow`) is the flow above as one runner, `Flow::run`. It does no I/O.
- Its steps are `StepKey`: `image`, `board`, `loader`, `flasher`, `write`, `boot`. These are the app's six steps.
- Each step's state is a `StepState`: `pending`, `running` (with the board's write phase and bytes), `retrying` (with
  the wait and when it ends), `refused`, `stopped`, `done` or `cancelled`.
- The whole flow is one `FlowView`, published whole on every change to the caller's observer.

The failure rule is in the runner, so every family gets the same behaviour:
- A failure that can change by itself is tried again after 1 s, then 2 s, 4 s and 5 s; the wait is capped at 5 s.
- A refusal that will not change (the board refuses the image, another board is on the port) waits for the person.
  It is never retried in a loop.
- `Control` is the person's hand: `stop()` (the manual off), `retry_now()` (cuts a wait short, ends a stop, asks a
  refused step again) and `cancel()`.
- An image built for another board, or a board of a family the loader does not serve, ends the flow before
  anything is sent.
- A failed write starts again from the manifest: the board writes from offset 0 and verifies.
- The restart into the slot is asked for once; after that the flow only watches `hello.version.slot`.

### The seams, and who fills each

| Seam | Step | Filled by | State |
|---|---|---|---|
| `Loader` | 3 | the family driver. The Pi: `atlas_rpi::RpiLoader` over `RpiDriver::boot`, which serves the flasher's boot set through `atlas-rpiboot` | built; tested against the simulated ROM. Real BCM2712: D19 first |
| `Flasher` | 4 | the Orion side: the board's node in the flasher state, with the board's identity | waiting on Orion (`hello.state`, recovery `link-usb`) and on Lemnos FLASH-BCM2712 (the flasher image's start-up) |
| `FirstFlash` | 5, 6 | the Orion side of Lemnos `system.flash/1` | waiting on Orion (see below) |
| `SlotWatch` | 6 | the device list: the board's node with `hello.version.slot` | to wire with the app |

The board's surface (Lemnos, 2026-11-22, on Lemnos next):
- `system.flash/1`: `info(out)`, `manifest(manifest, record)` (an empty record, or the 108-byte `LMNSSIG1`), and
  `write(size: u64, format: u8)`, a job (0 raw, 1 xz; the manifest's size and SHA-256 are the raw image's). Its result
  is the raw byte count, then the outcome: 0 verified, 1 not checked (unsigned), 2 not checked (unknown key).
- `data(offset, bytes)`, in order from 0, by the client that started the write. A frame is at most 1 MiB, header
  included.
- `verify()`, a job whose result is the byte count checked.
- `write` is refused unless the board file sets `allow_first_flash = true`, and the target must not be the running
  system.
- `indicator/1`: `set(state, per-mille progress or 0xFFFF)`, `states(out)` = `idle,receiving,writing,verifying,done,failed`.
  `WritePhase` names the three a running write passes through.
- `system.reboot/1` `reboot_to("rpiboot")` (Lemnos queue, after RESTART-UNIT): RPIBOOT by command from a running image.
  It is what D6's "restart a running board into USB boot remotely" needs. Until then a running next image enters
  RPIBOOT only by its button, or by slot-init's own `loop_return = "rpiboot"` at the boot-loop limit.

Orion's answer (2026-11-22, read from Orion next 3f60576c and Lemnos 4f19ce7e, not run; no pin moved for it):
- **The flasher image runs the comm core and node logic**, not `orion-recovery` alone. The recovery comm core passes
  file pushes, file sinks and actions to node logic, so on its own it refuses each as `unavailable`. The flasher image
  carries `orion` as `orion-comm` and `orion-node` (Orion's packaged service), with `hello.state = flasher` in
  orion.conf. `orion-recovery` stays the fallback a comm core that cannot start drops into.
- **The image goes by `files.push(destination, source, progress)`**, not by `data()` calls in action arguments, which are
  capped at one frame (8 KiB on a USB link).
  - The Lemnos bridge registers the sink `lemnos/<device>/`. Orion hands each FileBegin, Chunk and Commit straight to
    it and stores none of it. The bridge's FileStatus answers pace the sender.
  - The manifest goes to `lemnos/flash/image.img.json`, then the image to `lemnos/flash/<name>`, streamed into
    `system.flash/1`'s write job. The job's result is the push's answer. This is Lemnos's test
    (`service/orion/tests/flash_stream.rs`); the canonical destination names are Lemnos's to give.
  - A chunk is 32 KiB, or the link's max frame less 64 bytes, whichever is smaller.
  - The same digest pushed to the same destination is the same transfer, so after a dropped link, `FirstFlash::write`'s
    retry is a reconnect and a push again.
- **`Flasher::find` reads `Node::state() == Some("flasher")`** from the signed hello. No program on the board can publish
  `hello.state`: the broker refuses it, so a board cannot claim to be a flasher. The comm core's `orion/state` file says
  the same and can be fetched without a login.
- **In a RAM-booted flasher with no data partition:**
  - The node key is new every boot unless the image carries `<keys.dir>/node-identity.ed25519`, so the flasher's key is
    not the running image's. The flow knows the board by its USB serial, not by a pinned key.
  - `state.require_mount` stays false.
  - With `/etc/board/security` absent, the flasher accepts plain sessions over USB. With it on, an operator, recovery
    key or enrollment key is needed.
  - The USB link is `links.usb = <name>`, offered by lemnosd with the FunctionFS fds, including the "end" descriptor.
- **Rev:** Orion next 3f60576c, wire level 6, shm pins at Lemnos 0d37cc55. Lemnos 4f19ce7e pins Orion 172054f4, also level 6,
  with no wire or API change between the two. Atlas pins neither until the coordinator sends the revs.

Lemnos's answer (2026-11-22). The bridge is Lemnos's (`service/orion`), on Lemnos next; docs/slots.md, "First flash ›
Over Orion":
- **Destinations** are `lemnos/<device>/<name>`: first the manifest to `<name>.json`, then the image to `<name>`.
  - `<device>` is the system-flash device's id in the flasher's board file.
  - `<name>` is one the flasher sets in `LEMNOS_ORION_STREAMS` (e.g. `flash=image.img.xz+image.img`).
  - The bcm2712 flasher's exact id and names come with FLASH-BCM2712. "flash" with `image.img.xz` and `image.img` is
    expected, but they are read from that rev.
  - The manifest carries the signature record in its `signature` field; there is no sidecar.
- **The image push's answer:** at commit the bridge checks the stream's SHA-256, then waits up to 900 s for the write job.
  - Success is `FileState::Committed` with detail "<raw> bytes written; signature verified". The other signature
    texts are "not checked: unsigned", "not checked: signed by an unknown key" and "not reported".
  - Failure is `Rejected` with the job's status or the refusal.
  - It is text today. Atlas asked for the raw byte count and the outcome as fields, landing with the flasher. Until then
    `WriteReport` is not parsed from prose.
  - `verify()` and the reboot are separate calls after the push.
- **Revs:** none yet. They come through Helios when they land: `reboot_to` first, then FLASH-BCM2712.

So `FirstFlash` is a push of the manifest and then the image to the bridge's sink, plus the write job's outcome, and `Flasher` is
a node with `state() == flasher`. Both are written once the revs and Lemnos's destination names are sent.

## The write step as built (2026-11-22, pr/D6 d4df559d)

`crates/board/first-flash` (`atlas-first-flash`) fills `Flasher` and `FirstFlash`, against Lemnos next 4b5be3a5
(FLASH-BCM2712, with `reboot_to` from 4a65e473) and Orion next 3f60576c. The coordinator confirmed these revs for this
work only; the Raze image's pins and build10 are unchanged. The workspace's Orion lock stays at 671d29d6: the client
calls used here are the same at both revs, and moving a lock is its own PR.
- `OrionFlasher` takes the node its `Reach` seam gives once its hello says `state = flasher` and its `serial` is the
  target's (`is_flasher_of`). Another board is refused; a node not yet in the flasher state is waited for.
- `BridgeFlash` runs these steps in order:
  - pushes the manifest (schema 1, `wire::manifest`) to `lemnos/flash/image.img.xz.json` (`image.img.json` for a raw
    image), then streams the file to `lemnos/flash/image.img.xz`;
  - reads the commit's fields (`wire::committed`: `raw_bytes=<n> outcome=<0|1|2|none>`; unknown fields skipped, a
    prose answer refused);
  - runs `verify` through `lemnos.flash.call`;
  - checks both counts against the image's raw size.
  - The restart is `lemnos.reboot.call reboot`. An answer lost after the request went out is taken as the restart.
  - The device ids are the flasher board file's (`flash`, `reboot`).
- `OrionBoard` is the node's session. A push is an `atlas-files` job, cancelled if the flow drops it. A call goes
  through `atlas-actions`. A verify job whose session is lost is followed again, with the capped backoff.
- `atlas-files` now keeps the board's commit answer (`Push::answer`). `ImagePlan` carries `stream` (xz or raw) and
  `signature` (the record as 216 hex digits, or none).

Proof on the PC: 16 tests. The write runs against a fake bridge (order, manifest, phases, every refusal, a lost
verify, the restart). Against the simulated node it runs over a real session: both files land at the bridge's names,
and a commit with no fields is refused. The simulated comm core always says `running`, so the flasher match is proven
by unit test only.

Open, and asked of Orion and Lemnos through Helios:
1. **How the PC reaches the flasher's node.** Orion's client connects over unix, TCP or serial. The flasher's
   gadget carries Orion's link as FunctionFS. Either a host-side comm core takes the USB device (Orion's `bulk`
   handles) and Atlas connects to it, or the gadget also offers NCM and an address, and Atlas uses
   `orion+tcp`. `Reach` is the seam for whichever it is.
2. **verify's count:** the bridge passes a job's result as text when it is UTF-8 and as hex otherwise, so the
   8-byte count arrives as 8 bytes or 16 hex digits. `wire::verified` reads both, by length. A field, as for the
   commit, would remove the guess.
3. **The manifest across a push that resumes:** `atlas-files` begins a broken push again on the same session.
   Lemnos says a streamed image is not resumed. Does the bridge still hold the manifest for the second begin, or
   must the manifest be pushed again first? `FirstFlash::write` re-pushes it on every attempt, but not inside one
   push's own reconnects.

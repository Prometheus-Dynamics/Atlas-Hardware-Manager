# B25: every kernel fragment line takes, checked in the gate

**Group:** B. Board descriptions

**Wave:** 6

**Needs:** B16 (merged, PR 61), B24 (merged, PR 72)

Read `AGENTS.md` and `docs/design.md` first.

## Why

Gaia's kernel fragment check found three lines of the Raze's `raze-trim.config` that did not take in the kernel
it builds: `# CONFIG_KALLSYMS_ALL is not set`, `# CONFIG_KPROBES is not set` and `# CONFIG_QUOTA is not set` each ended
`=y`, because something selects each one. With Gaia's check on, the `raze-base` kernel build failed on `next`. B16's
report gave totals for the Raze and claimed "every requested line in effect" for the RK35xx boards; that claim
was wrong for lines whose symbol is absent from the resolved config, and the Raze was never line-checked. This PR
fixes the causes, makes the sweep complete for every board, and adds a check to our own gate so the next such line
fails here, not in Gaia.

## Creates

- `scripts/check-kernel-fragments.sh`: for each board with a kernel, obtains the pinned kernel tree (a shallow fetch of
  the one pinned commit or tag, cached under `ATLAS_KERNEL_CACHE` by the pin), runs the arm64 defconfig (or the
  family's), `merge_config.sh` with the board's fragments in the order a board applies them, and `olddefconfig`, in a
  scratch `O=` directory. Host tools only (make, git, python3, flex, bison). Every requested line is compared with the
  resolved `.config`; a line that does not take FAILS, naming the board, the fragment file and line, the value requested
  and the value resolved. `--self-test` runs the real check, then a scratch copy of the Raze's trim without the
  `LATENCYTOP` line (the state that failed here) and requires that to FAIL naming `raze-trim.config` and
  `CONFIG_KALLSYMS_ALL`.

## The three causes and their fixes (the Raze, `raze-trim.config`)

Each line was "not set" in the trim, and each was selected by a symbol that is on in the Raze's resolved config
(`bcm2712_defconfig` + the family fragment + `raze.config` + `raze-trim.config`, the pinned tree `53679a5`):

- **`CONFIG_KPROBES`** is selected by `KGDB_HONOUR_BLOCKLIST` (`lib/Kconfig.kgdb`), which is on because
  `CONFIG_KGDB=y` in `bcm2712_defconfig`. **Fix:** `# CONFIG_KGDB is not set`. The Raze has no wired console (pstore is
  its log) and no product runs kgdb; `KGDB_KDB` goes with it. Nothing we need depends on KGDB: its dependents in the tree
  are the PowerPC and AMD display options and the tty serial-kgdb options, none of them on.
- **`CONFIG_KALLSYMS_ALL`** is selected by `LATENCYTOP` (`lib/Kconfig.debug`), on in the defconfig. **Fix:**
  `# CONFIG_LATENCYTOP is not set`, a debug aid. KALLSYMS itself stays on (oopses still name functions).
- **`CONFIG_QUOTA`** is selected by `OCFS2_FS` (`fs/ocfs2/Kconfig`), which is `=m` in the defconfig. **Fix:**
  `# CONFIG_OCFS2_FS is not set`: a shared-disk cluster filesystem no Raze product mounts (its slots are EROFS and its data
  is ext4). `TMPFS_QUOTA` (off) is the only other selector.

Checked after the fix: 126 Raze lines requested, none missing, on the resolved config.

## The patch series at its pin (B19's claim, checked)

B19 wrote that the series "applies cleanly to v7.3.4". That is correct. An earlier test in scratch (this PR's
work) reported every patch failing on a 7.3.4 copy, and that report was wrong: it fed `patch` files from a B19
scratch directory that is a full patched kernel tree, not a directory of patch files, so none of the paths existed.
Checked properly:

- The series repository at `fe0a8ed3` is a directory of `git format-patch` mails (`patches/<group>/<name>.patch`) with
  a `patches/series` file that gives the order. Its own `scripts/build.sh` applies it with `patch -d SRC -p1
  --fuzz=0 --batch --forward` (dry run first), to the kernel.org tarball of `KERNEL_VERSION="7.3.3"`.
- Its `series` file has 379 patch entries (694 lines with comments). 379 is the number of patch files, not commits.
- On a clean copy of `v7.3.3` (`d50d994b`, the series' own base): 379 applied, 0 failed.
- On a clean copy of `v7.3.4` (`7595a62d`, the commit B19 pinned, both commits confirmed by `git rev-parse`): 379
  applied, 0 failed, with the same flags.

So the series applies to 7.3.4 (and to the 7.3.3 base it was written for). Its CHANGELOG says none of its patches is in
7.3.1 to 7.3.3, and the 7.3.4 stable release touched no file the series edits in a way that stops it applying.
The pins go together. Not changed.

The checker prints, for any board it cannot check, the reason (the family names two series, or the series is not a
git source). A board that cannot fetch its series or kernel FAILS in CI as well.

## The release string

The Raze's kernel release was `7.2.9-v8-16k`. The `-16k` came from `bcm2712_defconfig`'s `CONFIG_LOCALVERSION`, a
label from a 16 KiB-page build; this kernel has 4 KiB pages on purpose (`raze.config`'s page-size decision, confirmed on
Raze #2: KernelPageSize 4 kB). A `next` image's release must not state a page size it does not have, so
`raze.config` sets `CONFIG_LOCALVERSION="-v8"` beside the page-size decision, with `# CONFIG_LOCALVERSION_AUTO is not
set` so no scm suffix is added.

With the resolver, `kernelrelease` gives `7.2.9-v8+` in our scratch tree and `7.2.9-v8` with `LOCALVERSION=` passed. The
`+` is the kernel's own source check (`scripts/setlocalversion` appends it when `LOCALVERSION` is not given and the
source is a git checkout that is not at a tag). A Buildroot build from a git source (Gaia's kernel source) gets the same
`+` unless the build passes `LOCALVERSION=`: Buildroot does not set it in `linux/linux.mk` at the pinned rev. That is a
Gaia or Buildroot choice, not a fragment's, and it is recorded for Gaia here. A build from a tarball gives exactly
`7.2.9-v8`.

Where the old string is written: `devices/families/bcm2712/family.toml` (a comment, updated) and `raze.config` (the
explanation). Historical records are not changed: `docs/prs/B14.md` records the module tree dev measured for the
`7.2.9-v8-16k` release on the bench, and it stays as that measurement. No slot manifest in `devices/` writes a
`kernel` field: a slot's manifest `kernel` is the release the build produces (`uname -r`), so it is computed by the
build, and it will read `7.2.9-v8` (or `7.2.9-v8+` from a git source) on a `next` image. The dev image on the bench is
not touched.

## Gate and cold/warm time

The new step is in `scripts/gate.sh` (and the self-test is a second step). Measured here:

- Cold (empty cache, fetches both pinned kernels: `git.kernel.org` v7.3.3 and `raspberrypi/linux` 53679a5): 356 s.
- Warm (cache present): 70 s.

CI caches `~/.cache/atlas/kernel`, keyed by the family and board files, so the cold cost is paid once per kernel pin.
The check FAILS when a source cannot be fetched (a kernel configuration that cannot be resolved is not a pass).
Locally only, `ATLAS_KERNEL_SKIP=1` skips it and prints that it was skipped.

## Build

- A session pins the node key it first saw at its address for its whole life. Every later connect
  is made to the address in Orion's pin form (`orion+tcp://host#<key>`), so Orion refuses a
  different key in the handshake, before any call.
- A node that answers with another key is never sent a call and never becomes `Found`. Its
  presence is `Presence::Replaced { expected, found }`, distinct from `Lost`. The monitor keeps
  looking for the expected node under the failure rule. The expected node answering again makes
  the session `Found` again without anyone acting.
- A person's explicit act makes another key the new expected one: `Monitor::accept` and
  `Sessions::accept_key`. Nothing calls them on its own. The session restarts with the new key and
  calls queued for the old node are refused.
- `Handle::node_key` is the key a session is connected to. A caller that resumes work compares it
  with the key the work started on.
- A caller that knows a node key starts pinned from its first connect: `Monitor::start_pinned`,
  `Sessions::handle_pinned`, `BoardDriver::know_key`. Only an address with no known key is connected
  unpinned (trust on first use), and that first contact is the one unpinned moment.
- A terminal open when its board is replaced ends with `End::Replaced`, not `End::Lost`.

## Lock notes

- At Orion 6dfb990 a pinned connect that meets another key is refused with
  `ClientError::Denied("the node is not the one that was expected")`, which carries no key, so
  `found` is `None`. The `// LOCK:` in `monitor.rs` names `ClientError::OtherKey` for the next lock.
- A pinned connect needs a signed client session at Orion 6dfb990. Every connect is signed with
  the monitor's own client key, generated when the monitor starts and not stored.
- `Orion` can pin only network addresses. A serial address is checked after its hello.

## Proof

Tests (`crates/board/session/tests/pin.rs`, `crates/board/access/tests/rekey.rs`): the same node
back is found again and resumes; a different key under the same address is replaced and receives no
call (counted on the simulated node); a queued call is not delivered to the other node; accepting the
new key starts a fresh session and old work does not match it; a session opened with a known key
refuses a different node on its first connect; the expected node back after an impostor is found
again.

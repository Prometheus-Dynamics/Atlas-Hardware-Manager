6. **The slot root rule reads each product's plan.** `erofs_rule` takes the constant `compression` of each `<image>::erofs` node of `gaia plan --json` and requires the kernel lines for that value in the product's kernel: its family's fragments and its board's. ## The gate's real result: FAILS at the slot root rule (PR B34 is open and not merged)

`devices/families/{bcm2712,rk35xx,sun60i}/assets/linux.fragment` set `CONFIG_EROFS_FS=y` and not `CONFIG_EROFS_FS_ZIP` or `CONFIG_EROFS_FS_ZIP_ZSTD`, so the zstd erofs root of every product that is not the Raze fails. The Raze passes because its board fragment `kernel/raze.config` sets both. The brief said `SLOT_CHAIN` "today requires EROFS_FS_ZIP and EROFS_FS_ZIP_ZSTD for every family". On `origin/next` at 06fdb64a it requires only `EROFS_FS`; those lines are PR B34 (#98, open, `pr/B34`), which adds exactly the two lines to all three family fragments. This PR does not fold B34 in.

The rule fails, verbatim, on the real tree:

```
check-devices: FAIL products/zero-3e-base: image zero-3e-base compresses with zstd, so CONFIG_EROFS_FS_ZIP must be =y; neither families/rk35xx nor the product's board builds it in
check-devices: FAIL products/zero-3e-base: image zero-3e-base compresses with zstd, so CONFIG_EROFS_FS_ZIP_ZSTD must be =y; neither families/rk35xx nor the product's board builds it in
```
(the same for `rock-4d-base`, `rock-4d-bringup`, `rock-5c-base`, `rock-5c-bringup`, `zero-3e-bringup`, and `cubie-a7-bringup` on `sun60i`; the full output is in the gate log below). The Raze's `raze-base` is `NOTE ... compresses its slot with zstd (its plan): the kernel needs EROFS_FS EROFS_FS_ZIP EROFS_FS_ZIP_ZSTD` and passes.

**Verified with B34's lines applied in a scratch copy** (not committed): the same tree plus `CONFIG_EROFS_FS_ZIP=y` and `CONFIG_EROFS_FS_ZIP_ZSTD=y` appended to the three family fragments. `GAIA_BIN=... scripts/check-devices.sh` then ends `check-devices: passed (3 families, 7 boards, 16 components, 8 products)`, every self-test passes, and the self-check passes. Output is in the scratch file noted under "Proof files". So B32 is green once B34 lands, and red until then.

## Differences between INPUTS.md and Gaia at the pin

1. **The "today" slot-chain text.** INPUTS: "`SLOT_CHAIN` today requires `EROFS_FS_ZIP` and `EROFS_FS_ZIP_ZSTD` for every family". Here it requires `EROFS_FS` only; those lines are B34 (open). This is this tree, not Gaia.
2. **#116 refuses nothing in our products.** INPUTS expected refusals to fix. None occurred.
3. **The graph grew for every OS product by new `os.files.N` source inputs.** Checked from the plan JSON: raze-base gains `raze-base.os.files.2`; rock-4d-base gains `rock-4d-base.os.files.2` and `.files.3` (the 2-node growth of the other base products is the same kind of input). Gaia names these by first use (`next_files`, `crates/core/graph/src/os.rs`) and they feed the kernel and host-tools steps. No product's `os`, components or fragments changed; the Raze, which has a `[boot]` table, and rock-4d-base, which has none, both gain the input, so the cause is not the boot fact. Which input each `files.N` carries was not traced; it is probably a kernel contract or config file Gaia now takes from the product's own tree (`require`, `os.rs`). Not confirmed. Its edges also changed (the extlinux layer feeds a `system` layer beside `rootfs`).
4. **`[generate.provides]` exists at 3f6e561** (#113). INPUTS says the L2 branch writes it. Not used in B32; the comment in `raze-lemnos-board` says so.
5. **The gate line for built components** (INPUTS: "every component of a product on the milestone list is BUILT once"). Not added: the brief says not to invent a build-record mechanism, and this repo has none. This is open.
6. **`[boot] firmware`** is read by Gaia for the kernel contract (`[firmware.rpi-tryboot]`, `crates/nodes/os-buildroot/src/contract.rs`). That contract is checked only in a kernel build, which this PR does not run.
7. **The Raze's kernel lines** live in its board fragment (`kernel/raze.config`), not in its family's. The brief said "for that product's family". The rule checks the family's fragments and the product's board's, because that is the kernel the product builds. Otherwise the Raze would fail on a line it sets.

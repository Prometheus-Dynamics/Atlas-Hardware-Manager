## What changed

1. **The pin.** `devices/gaia.lock` and the gadget component's Gaia ref (`devices/components/usb-gadget-network`) name `c6a3d102467f11a86ecc7fb53965cbaca9a09725`. The gadget identity is unchanged (1d6b:0103, bcdDevice 0x0b00). `devices/README.md` names c6a3d10 as current; `docs/prs/*` is history.
2. **The zig tools source** on `orion` and `orion-recovery`: `[sources.tools] download = "https://ziglang.org/download/0.15.2/zig-x86_64-linux-0.15.2.tar.xz"`, digest `sha256:02aa270f183da276e5b5920b1dac44a63f1a49e55050ebde3aecc9eb82f93239` (in the lock; equal to INPUTS). cc and env unchanged. The "NOT YET BUILDABLE" headers are gone. Gaia built both for aarch64 (orion 5,072,904 bytes, orion-recovery 2,595,064 bytes, at Orion 455a956e), x86_64 hosts only. Those sizes are the coordinator's report, not a build this PR ran.
3. **`[boot] firmware = "rpi-tryboot"`** on the Raze (`devices/boards/raze/board.toml`). `firmware_rule` (check-devices.sh) requires the board's Lemnos file to say `record = "tryboot"` for it (`firmware_record`: rpi-tryboot -> tryboot; Lemnos's record default is tryboot). Self-tested: a `uboot` record and an unmapped firmware are both refused by name.
4. **The slot-root rule reads each product's plan** (`erofs_rule`): the constant `compression` of each `<image>::erofs` node of `gaia plan --json` must have its kernel lines `=y` in the product's family fragments or its board's (the Raze's zstd lines are in its board fragment `kernel/raze.config`). A family no product names is held to zstd, and the output says so. Self-tested on a scratch copy: the same kernel passes with `compression = "lz4"` and is refused by name with the zstd default. With B34 merged, **every product passes**: `NOTE products/<p>: image <p> compresses its slot with zstd (its plan): the kernel needs EROFS_FS EROFS_FS_ZIP EROFS_FS_ZIP_ZSTD`.
5. **The note fix.** "NOTE in no product yet" listed three boards that two products each name, because the scan took every `.toml` in a board directory. It now lists description files only (`unnamed_descriptions`). Real output: `boards/radxa-cubie-a7a boards/radxa-cubie-a7s boards/radxa-cubie-a7z`. Self-tested.
6. **The sd-image fixture** (`devices/tests/fixtures/good-sd-image`) failed `--root` at HEAD: its example family had no kernel fragments, so the slot chain failed (9 FAILs with gaia 7177d72). Its family now has `assets/linux.fragment` with the chain and the zstd erofs lines, and `[kernel] fragments` names it. It passes `--root`, and it is in both self-check loops (the default run and `--self-test`). The README's "must pass" line is now true.
7. **The config-only gate step** (new): `scripts/check-config-only.sh`, called from `scripts/gate.sh` after the device step, and CI caches the Gaia store (`gaia-store` restore and save, the save runs even when a later step fails; key on `devices/gaia.lock` and the source pins). For EVERY product under `devices/products`: `gaia build <product.toml> --recipes <recipes> --input bench-key=<throwaway public key> --config-only` (the bench key only for products that name `bench-key`; the private half is deleted at once). A failure prints `FAIL products/<p>` with Gaia's message quoted. It says NOTE when the store is cold (a fetch of each family's kernel source), and needs no excuse for any product: none failed for a reason outside our data.
8. **Plan of every product**: `planned, not built` for each product line; no build record exists in this repo, and none was invented.
9. **Product data fixed by the config-only step**: `devices/products/raze-base/os/raze.fragment` had `BR2_PACKAGE_RPI_FIRMWARE_DTB_OVERLAYS="bcm2712d0 vc4-kms-v3d-pi5 ramoops-pi5"`. Gaia refused it, verbatim: `Buildroot did not take 1 config line as written: image.0.raze.fragment: BR2_PACKAGE_RPI_FIRMWARE_DTB_OVERLAYS="bcm2712d0 vc4-kms-v3d-pi5 ramoops-pi5" was dropped (no such option, or its dependencies are not met)`. Buildroot 2026.08 has no such option (its `package/rpi-firmware/Config.in` has `INSTALL_DTB_OVERLAYS`, `EXTRA_FILES`, and no overlay-list string). The overlays the Raze loads are the `dtoverlay=` lines of `boards/raze/boot/raze-device.txt`, and those are unchanged. The line is removed; `INSTALL_DTB_OVERLAYS=y` stays. Gaia resolves the Raze after the fix.

## Differences between INPUTS.md and Gaia at c6a3d10

1. The config-only step for every product: INPUTS expected the Cubie to be a possible failure (its TF-A chain). It resolves; its TF-A failure is in a build step config-only never reaches.
2. Gaia refused a Buildroot option the Raze's product carried (DTB_OVERLAYS, a dead line in our data). INPUTS did not warn of it. Fixed in the product.
3. #116 refuses nothing in our products at plan time.
4. #119 (erofs held to the kernel at build time) is not exercised by plan or config-only, so the slot-root rule still reads the plan and does not depend on #119.
5. `[generate.provides]` exists at c6a3d10 (#113). Not used by B32; the L2 branch writes it.
6. Every OS product gains new `os.files.N` source inputs at this pin, as at 3f6e561 (raze-base `.files.2`; rock-4d-base `.files.2` and `.files.3`). Which input each is was not traced.
7. The Raze's kernel lines live in its board fragment, so the rule checks the family and the board, not the family alone, as INPUTS's "for that product's family" says.
8. The gate line "every component of a product on the milestone list is BUILT once" (INPUTS) is not added: there is no build-record mechanism, and the brief says not to invent one.
9. `[boot] firmware` drives Gaia's kernel contract only in a kernel build, which this PR does not run.
10. The gaia store: INPUTS says 2.3 GiB per family; measured 6.3 GiB for three families here.

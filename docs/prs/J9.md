# J9: Atlas on Orion's declared lock rev, and its typed client API

Moves Atlas from Orion `fd61df3e` to `c9eb5a25` (Orion `next`, the commit that adds `docs/lock.md`:
wire revision 1, additive level 2, shared-memory crates at Lemnos `bded77a0`).

## The pin, and how it was moved

- `Cargo.toml`: `orion` rev `c9eb5a25ebeff940786901995ad4d9abc91795bc`.
- Three crates pinned Orion's crates directly at `fd61df3e` and were moved with it:
  `crates/board/topics` (`orion-msg-topics`, `orion-wire`), `crates/board/nt` (`orion-nt4`,
  `orion-comm-app`, `orion-config`) and `crates/testing/sim-node` (`orion-stubs`).
- `Cargo.lock`: `cargo update -p orion --precise c9eb5a25ebeff940786901995ad4d9abc91795bc`
  (narrowest form: it moves Orion's own packages and the shm crates that Orion pins), then the three
  crate pins above, then `cargo metadata` to resolve the git sources. No other registry package
  changed.

## `cargo tree` (after the change)

- No Orion package appears at two revs: the lock holds only `c9eb5a25`.
- Lemnos appears only at `bded77a0`, in five crates: `shm-fdpass`, `shm-ring`, `shm-ring-doorbell`,
  `shm-ring-time`, `shm-sample-time`. The old `d1a8939a` entries are gone.
- After merging `origin/next` (L3 landed, `lemnos-slot-store` at `f4a295c6`), Lemnos appears at
  two revs in the lock, in two different crates: the shm crates at `bded77a0` (Orion's) and
  `lemnos-slot-store` at `f4a295c6` (Atlas's `Cargo.toml`). No crate appears at two revs.
  `lemnos-slot-store` depends only on `sha2`, so the two sets share no crate.
- Packages that appear at two versions are registry crates (`syn`, `digest`, ...), as before.

## Changes

1. **`atlas_session::Failure` from the typed refusal.** `ClientError::Refused { error, detail }`:
   the kind and code come from `error` (`Denied` for `denied`, `Refused` with the code otherwise),
   and the text is the node's `detail`, verbatim, never empty. The matches in `atlas-session`,
   `atlas-actions` (`board.rs`, direct and follow) and `atlas-topics` (`describe.rs`) use the
   struct form. Tests: `failure::tests::a_refusal_takes_its_kind_from_its_code_and_its_text_from_the_nodes_words`,
   `failure::tests::the_lease_lost_code_keeps_its_code_and_the_nodes_words_verbatim`,
   `failure::tests::a_lease_held_by_another_is_denied_and_says_who_holds_it`,
   `a_refusal_keeps_the_nodes_words_verbatim` (session tests, a stub refusal with the lease-lost
   words through `with_client`).

2. **The pin flow, and the probe deleted.** `pin`, `repin` and `fingerprint` now take the key the
   transport proves: `link::transport_key` connects with the PC's identity and calls
   `Orion::node_key()` (`Welcomed::node_key` on a signed session, else asked once with a nonce and
   checked). The pin is that key and its fingerprint, not the hello document's. The once-per-run
   security-mode probe (`link::security`, `Security`, `classify`) is deleted, with the mode
   parameters of `board` and `enrol`. Tests: the existing `pin`, `repin`, `fingerprint` and `enrol`
   tests (`crates/tools/next/tests/identity.rs`) now run on the transport key.
   - The security-off first line and the "nothing to enrol" refusal are gone with the probe. A
     tool session always passes an identity, and `Welcomed::signed` says whether the session is signed,
     not whether the node runs with security off. The node's mode is not declared anywhere the tool
     reads. Tests rewritten: `a_security_off_board_pins_fingerprints_and_enrols_like_any_board`,
     `a_board_command_prints_no_security_line`.

3. **BoardState.** Already the three states: `running`, `recovery`, `flasher`. `updating` is
   `UnknownState` and gets no shell (test `an_unknown_state_word_gets_no_shell_guess`, unchanged).
   No code change.

4. **USB-name, lease-free and LeaseLost words, verbatim.** They arrive as `Refused { detail }` and
   reach the caller as `Failure::text()` and the `ActionError` / `SessionError` text. Tests above.
   The sim does not model the words: see "Not done".

5. **Turned on anything gated "until Orion J9".** Nothing is gated. `INFO_IN_PIN` does not exist in
   Atlas or in Orion. The one J9 note in the code (the security probe) is what this PR deletes.

## Install refusals keep a typed value

- `atlas-board-slots`: `classify` keeps an `ActionError`'s `Failure` (`Step::Refused`), the run
  stores it, and `SlotInstalls::failure(job)` returns it. The text is still the stage's `Failed`
  reason. Test: `a_refused_install_keeps_its_typed_failure_and_the_boards_words` (the sim refuses
  an install for room; the typed value carries the board's words and is not `Denied`).
- The sim gained `slot_set_free_bytes` for that test.

## Not done, and why

- **The pending-trial BUSY code cannot be typed yet.** Orion's `Finished` is `{ outcome, output,
  detail }` at `c9eb5a25`: the board's Lemnos status code (for example `-16` BUSY) reaches Atlas only
  inside `detail`. Reading the code out of the words would be the word match this PR removes, so
  `SlotInstalls::failure` gives the kind (`Other`, a board's own refusal) and the words, not the
  code. T4's step 7c needs a code field on the action outcome, from Orion or Lemnos. The sim does not
  model the pending-trial install refusal either. This is a blocker for 7c, not a silent gap.
- **Sim: Busy names the holder, and LeaseLost (22).** The sim's leases (`crates/testing/sim-node/src/lease.rs`)
  drop a silent caller's runs. They do not model contestable leases, Busy, or the lease-lost code.
  Not modelled, so not tested.
- **Orion's `Level` and `Revision` errors** are not matched anywhere in Atlas: no call asks for a
  level-1 feature.
- **Pin on the transport key is a second connect**, made by `transport_key` before the pinned session
  opens. The pinned session still checks the key at the handshake (`handle_pinned`), so a node that
  changes its key is refused as before.

## Doubts

- The security-off line is gone. If the coordinator wants it back, it needs a fact the node
  publishes, not the session's `signed` flag (which is always true for the tool's identity sessions).
- `transport_key` and the hello key agree on the sim, so no test could show that `pin` stores the
  transport key rather than the hello's. The code path is the change; the tests do not discriminate.

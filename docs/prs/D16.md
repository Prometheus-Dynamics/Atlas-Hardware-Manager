## What was built

- `crates/flash/fel/src/thunk_a64.S`: the AArch64 thunk for FEL in native AArch64 (mode b). Same swap, call and return contract as the ARMv7 thunk.
- `crates/flash/fel/src/thunk_rmr.S`: the AArch32 thunk for FEL in AArch32 with an AArch64 payload (mode a). It swaps, writes the SPL's entry to the layout's reset vector register, and requests an AArch64 warm reset through RMR. It never returns to FEL.
- `thunk.rs`: one `Shape` per thunk (the words and the offsets of its table, entry, flag, save area and vector word), one `blob` function that fills it from the layout.
- `layout.rs`: `ThunkIsa` gains `Aarch64` and `Aarch32ToAarch64 { reset_vector }`; `ThunkIsa::return_mode()` gives `ReturnMode::ReturnsToFel` or `NoReturnExpected`. A `Layout` is made only by `Layout::new(LayoutParts, Confirmation)`, `Layout::from_value` or `Layout::from_record(sram, Acknowledgement)`, all of which run the layout's rules. Its fields are crate-private, so a struct literal does not build outside the crate (a `compile_fail` doc test shows it). It carries its `Confirmation`: `Confirmed`, or `Unconfirmed(Acknowledgement::Withheld | Given)`. A withheld acknowledgement lets a caller read a layout but not write or run with it: `load_spl`, `load_image` and `flash` refuse it before their first write. `Fel::write` and `Fel::run` (FEL_DOWNLOAD and FEL_RUN) are crate-private, so they are sent only through those entry points. Reads (`Fel::verify`, `Fel::read`) take no layout and stay open on an unconfirmed device.
- `flash.rs`: `Spl` reports its `return_mode`. The RMR mode runs the thunk, accepts the bus dropping as the expected end, and verifies nothing afterwards. `flash()` (SPL then image) refuses a no-return layout before any device access, with the message to use `load_spl` instead.
- `sim.rs`: the mock device runs each thunk's semantics. For the RMR mode it records the reset vector write (`reset_writes`) and the warm reset (`warm_reset_into`), and the device leaves FEL.
- `records/sun60i-a733.json`: the A733 layout record, `confirmed: false`, mode `aarch32-rmr`.
- Docs: `crates/flash/fel/src/lib.rs` (the spec and the modes), `TODO.md` (one line), `devices/families/sun60i/family.toml` (the A733 board list in plain words, the SCP open item, a pointer to this file), `devices/README.md` (a pointer to that list).

Public API added: `ThunkIsa::{Aarch64, Aarch32ToAarch64}`, `ReturnMode`, `LayoutParts`, `Acknowledgement`, `Confirmation`, `Layout::{new, confirmation, from_record}`, `Spl::return_mode`, `thunk::{shape, Shape}`, the constants of the two new blobs, and `LayoutError::Unconfirmed`. Round 2 changed `Layout`'s fields to crate-private (see above), so `crates/drivers/allwinner/tests/driver.rs` builds its layout through `Layout::new` and `crates/flash/fel/tests/faults.rs` likewise. ## The specification (the ARMv7 thunk, both thunks satisfy it)

Read from `thunk.S`, the words it assembles to, and the crate's design notes.

1. **Entry.** FEL_RUN jumps to the thunk's first byte in the boot ROM's execution state, as a subroutine. lr holds the return address into the ROM's FEL loop.
2. **Save.** The thunk saves r4-r11, sp and lr into its save area, which is inside the blob and outside every swap buffer. It uses only r0-r3 and r12, and never touches the stack, because the ROM's stack may be one of the swapped buffers.
3. **Swap table.** Up to eight `(buf1, buf2, bytes)` triples of 32-bit words, zero-terminated. Each swap exchanges `bytes` at `buf1` with `bytes` at `buf2`. The swap is its own inverse.
4. **Pass 1.** Swap every buffer. The SPL's bytes that would land on a live buffer were written to the backup (`Layout::spl_pieces`), so the SPL now sits at its load address and the live stack sits in the backups. Set the flag. Call the SPL entry word (BLX; no arguments).
5. **Pass 2.** The SPL returned: swap every buffer again. The flag is set, so restore r4-r11, sp and lr and return into the ROM's FEL loop. The next FEL command is served from there.

The thunk's code, table, entry word, flag and save area are data. The host fills the table and the entry from the layout, and the offsets are constants checked against the assembled object. The layout's rules keep the thunk outside every swap and outside the SPL.

For the two new thunks: mode b (`thunk_a64.S`) has the same five steps with AAPCS64 callee-saved registers (x19-x30) and sp, the SPL called with BLR, and RET through the restored x30. Mode a (`thunk_rmr.S`) has step 3 and pass 1 only, then the reset-vector write and the RMR write (see below). It has no save area, no flag and no return.

## The three modes and the return rule

| Mode (`ThunkIsa`) | FEL state | SPL state | Thunk | Return |
|---|---|---|---|---|
| `Armv7` | AArch32 | AArch32 | `thunk.S` | `ReturnsToFel` |
| `Aarch64` | AArch64 (native) | AArch64 | `thunk_a64.S` | `ReturnsToFel` |
| `Aarch32ToAarch64 { reset_vector }` | AArch32 | AArch64, by warm reset | `thunk_rmr.S` | `NoReturnExpected` |

**Mode a, the RMR path, in detail.** The thunk writes the SPL's AArch64 entry (the load address) to `reset_vector`, a word of the SoC's writable RVBAR backing store, and then writes RMR (`MCR p15, 0, Rt, c12, c0, 2`) with `Rt = 3`, which is AA64 (bit 0) = 1 and RR (bit 1) = 1. Per the Arm ARM, RMR is EL3-only, and RR requests a warm reset; after the reset the core starts at the reset vector in the state AA64 selects. The architecture makes RVBAR_EL3 read-only, so software cannot write it: the write goes to the SoC's backing store, which is what makes this mode SoC-specific. The encoding and the RR semantics are checked against the Arm register reference (item 8 below); the exception level the write needs is item 10, and it is UNCONFIRMED for the A733.

**What "no return expected" means for the flow.** After the warm reset the boot ROM's FEL loop is gone, so no command can be sent and no image can follow over FEL. The SPL is entered at its load address and continues on its own. Whether it continues to U-Boot over images that FEL already loaded, or whether a later stage (fastboot, or a second FEL-like path) takes over, is the next stage's job. This crate does not model it. The flow reports `NoReturnExpected` and does not verify afterwards. `flash()` refuses the mode before touching the device, and `load_spl` is the entry point. The SPL's own AArch32-to-AArch64 hook (see below) is consistent with this: it is designed to run when the SPL is entered in AArch32, and it performs the switch with RMR.

## Known, with source

From the pinned Radxa U-Boot tree that B19 names, read for addresses only (its `configs/radxa-cubie-a7s_defconfig`, `arch/arm/mach-sunxi/Kconfig` and `include/configs/sunxi-common.h`, fetched at commit `9da4b3e82d641296f5b19d5e78eaad0d3cf56eec`; no code read):

- SPL SRAM base `0x47000` (`SUNXI_SRAM_ADDRESS` for MACH_SUN60I_A733). `CONFIG_SPL_MAX_SIZE=0x49000`, so the SPL ends at most at `0x90000`.
- `SUNXI_LIBDRAM_BASE` `0x90000`: an SRAM address the early A733 SPL hook copies the AArch32 libdram blob to and enters.
- RVBAR backing store `0x08001004` (`SUNXI_RVBAR_ADDRESS`). The Kconfig help says the RVBAR system register is read-only, and that Allwinner cores provide a writable MMIO backing store "to allow to set the entry point when switching to AArch64".
- BL31 at `0x48000000` (`SUNXI_BL31_BASE`). SCP firmware slot at `0x48100000` (`SUNXI_SCP_BASE`), an address only: nothing in B19's chain loads an SCP image.
- DRAM from `0x40000000` (`CFG_SYS_SDRAM_BASE`), up to 16 GiB (`SUNXI_DRAM_MAX_SIZE`).
- `ARM_BOOT_HOOK_RMR` (`arch/arm`, depends on ARM64): "Insert some ARM32 code at the very beginning of the U-Boot binary which uses an RMR register write to bring the core into AArch64 mode ... This allows both the SPL and the U-Boot proper to be entered in either mode". So the A733 SPL is designed to be entered in AArch32. That is a statement about the SPL. It does not say what state the boot ROM's FEL runs in.
- Gaia's build of B19 compiles the SPL with its aarch64 toolchain (the build log names it). That says nothing about the SPL's entry state.
- The thunk approach itself is the ARMv7 design already in this crate (`thunk.S`), unchanged.

## UNCONFIRMED, and what answers each

1. **The FEL execution state on the A733** (AArch32 or native AArch64). Answered by a FEL `ver` (verify-device) response on the A7S, read-only, and then a register read of the boot ROM's state if the protocol offers one (`FEL_UPLOAD` from the scratchpad region is the existing read path). Until then the record names `aarch32-rmr` as the choice, because the pinned SPL is built to be entered in AArch32; this is a guess the record says it is.
2. **Whether a write to `0x08001004` followed by RMR moves the core into AArch64 at `0x47000`.** The Kconfig states the store exists; the sequence is not run. Answered by one board run: write the entry, RMR, and see whether the SPL's first bytes run (the bring-up's LED or the next FEL-free sign of life, B19 Part 4).
3. **Where the boot ROM keeps its FEL stack and data in SRAM.** The swap table for the A733 record is empty, which is only safe while the SPL's bytes do not overlap live ROM state before the reset. Answered by the verify response's `scratchpad` field and an `FEL_UPLOAD` read of SRAM around it, read-only; until then the record stays unconfirmed and refused.
4. **Whether SRAM survives the warm reset, and whether the reset enters the SPL or the boot ROM's own reset path first.** Answered by the same board run as 2: if the SPL does not start, check the SRAM contents with a read after reset, which needs FEL again (so the first run is the one that matters).
5. **The thunk address `0x90000`** (just above the SPL's largest size, and where the SPL's libdram copy lands). It is safe for the no-return mode, because the thunk is not used after the reset. The returning modes need a place the SPL never writes, and no such place is known for the A733.
6. **The DRAM address the flasher image is written to** (`0x41000000` in the record: below BL31 at `0x48000000` and the SPL's FIT address `0x47a00000` from the defconfig). Not checked against the DRAM map of the board. It matters only when an image follows over FEL (the returning modes).
7. **Whether the device disconnects or times out when RMR resets it.** The flow accepts `Disconnected` and treats it as expected. A timeout is an error. Answered by the board run in 2.
8. **The `RMR` encoding (checked, with one inference left).** Arm's A-profile register reference (developer.arm.com, ddi0601 and ddi0595, `RMR_EL3`) gives the AArch64 encoding of `RMR_EL3` as op0=0b11, op1=0b110, CRn=0b1100, CRm=0b0000, op2=0b010, accessible only at EL3, and says that AArch32 `RMR` maps onto bits [31:0] of `RMR_EL3`. The thunk emits `MCR p15, 0, Rt, c12, c0, 2` with `Rt = 3`: CRn=c12, CRm=c0, op2=2 is the same coordinates as the AArch64 encoding, which is the inference, because the search summary did not print the AArch32 form. The AA64 bit (bit 0) selects the state the PE boots into after a warm reset. RR (bit 1) requests the warm reset and resets to 0 on it. Remaining: read the AArch32 `RMR` register page to confirm the CP15 coordinates.
9. **The SCP question** is in `devices/families/sun60i/family.toml`.
10. **The exception level the boot ROM's FEL runs at.** `RMR_EL3` (and its AArch32 form) is accessible only at EL3. At EL2 or EL1 the MCR is UNDEFINED, so the thunk would fault instead of resetting. The FEL level on the A733 is not known. The first board check must establish it (step 1 below). If it is below EL3, the RMR mode is not usable as written, and a level change is outside this PR. Not established here: whether `RMR_EL2` or `RMR_EL1` exist (the Arm text for them could not be retrieved).

## The first board check (read-only FEL queries first)

On the Cubie A7S, with no write to any SRAM or DRAM address:

1. Put the board in FEL (the BROM's FEL entry, as the family file and B19 describe). Run `FEL_VERIFY_DEVICE` and record the SoC id, the firmware field, the mode, and the scratchpad address. Expect mode 1. Also record the exception level FEL runs at (item 10): the RMR thunk is valid only at EL3. The record's `confirmed` stays false.
2. Read a small region of SRAM at and around the scratchpad address, and at `0x47000`, with `FEL_UPLOAD`. Record which bytes are live (the boot ROM's data) and which are free. Use this to fix the swap table (item 3).
3. Only after 1 and 2 are read and written down: decide the mode. The verify response's mode field is the FEL mode, not the execution state, so the state comes from the register read in item 1 (if the protocol offers one, otherwise from a documented source for this SoC, which is not yet found). If it is AArch64, the record becomes `thunk_isa: "aarch64"` (no `reset_vector`). If it is AArch32, keep `aarch32-rmr`. Either way, the first write is a flash of the SPL alone, with `load_spl`, and the board is checked for its first sign of life (B19 Part 4) before anything else.
4. Only then set `confirmed: true`, and only with the readings from 1 and 2 pasted into the PR that does it.

Nothing in this PR runs any of it. The board check is a later PR's job, run by the user on the bench.

## Tests (what they prove, and what they do not)

- `thunk.rs`: the committed words of each thunk equal the assembled `.text` of its source when the assembler is installed. The ARMv7 words are checked with `clang --target=armv7a-none-eabi` (as before), the RMR words with the same clang, and the AArch64 words with `aarch64-linux-gnu-as` and `aarch64-linux-gnu-objcopy`. Each label's offset is checked against the object's symbol table with `llvm-nm`. Each test skips with a notice when its tool is missing, so CI without the tools still passes. The shape lengths and table/entry/vector positions are checked for each mode.
- `layout.rs`: each `thunk_isa` reads; an unknown one is refused; `aarch32-rmr` needs a non-zero reset vector register; an unconfirmed record reads with the acknowledgement withheld, and `load_spl`, `load_image` and `flash` refuse it before any write, through every public constructor (`Layout::new`, `from_value`, `from_record`); an acknowledged one runs on the mock device. Reads take no layout. The return mode of each mode is right; the A733 record reads (its addresses, and that it is unconfirmed). The overlap refusals still hold. A `compile_fail` doc test shows that a struct literal no longer builds outside the crate.
- `flash.rs` on the simulated device: the AArch64 flow runs the SPL, leaves the stack back in place, and verifies FEL afterwards. The RMR flow writes the SPL, sends the entry to the layout's reset vector register, requests the warm reset, reports `NoReturnExpected`, and verifies nothing afterwards. `flash()` refuses the RMR layout before any device access.
- The existing ARMv7 flow tests and the USB fault tests are unchanged and pass.

What the tests do not prove: the thunks' machine behaviour. The simulated device models what each thunk does (swap, call, reset); it does not run the code. Nothing was run under qemu: `qemu-system-aarch64` is installed, but a bare-metal harness for the AArch64 thunk was not written in this PR (optional in the brief). The assembled words prove the committed bytes are what the source assembles to, not that the source is right on the A733.

## Known limits

- **The gate is a field, not a check at ingestion (round 2).** An UNCONFIRMED layout made without acknowledgement cannot be written or run: `load_spl`, `load_image` and `flash` refuse it before the first byte is sent, and `Fel::write`/`Fel::run` are crate-private. Still open: the `UsbIo` trait is public, so a caller outside the crate can send raw transfers. That is a boundary of the USB layer, not of this crate.
- **`flash_error` in the driver is exhaustive over `FlashError`.** This PR adds no `FlashError` variant: the no-return refusal is `FlashError::Layout(LayoutError::Unsupported)`, and the unconfirmed refusal is `LayoutError::Unconfirmed` (inside `Layout`).
- The record's swap table is empty for the A733 and the SRAM plan is unconfirmed (item 3).
- The reset vector write and the RMR request are one sequence in a thunk, and the thunk runs only after the SPL bytes are written. A failure between the two leaves the SPL in SRAM and the device still in FEL.

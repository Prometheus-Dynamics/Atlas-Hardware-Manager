# T4: `atlas-next cycle`, the milestone-2 slot cycle as one run with a scorecard

Milestone 2 is the first `next` image booting on a Raze and the slot cycle run on it. The steps exist as separate
commands (T1-T3). This PR runs them in a fixed order against one board and writes ONE scorecard, so the run on the
bench is one command and its result is one file that says, step by step, what happened, in the board's own words.

## Command

    atlas-next cycle <address> --good <bundle> --bad <bundle> --scorecard <file> [--identity <file>] [--state <dir>]

`--good` is a bundle that boots; `--bad` is a bundle whose slot does NOT come up (its trial must fall back by
itself). The tool never makes bundles; the caller brings both.

## Steps, in order (each step's result: PASS, FAIL or SKIPPED, the exact words the tool or board printed, and the
## elapsed time; a FAIL stops the run unless the step says otherwise; SKIPPED only where stated)

1. `identity`: the PC's client fingerprint.
2. `fingerprint`: the board's key fingerprint; whether the address is pinned already; security on/off (the T3 probe).
3. `pin` if not pinned (first contact). If pinned and the key differs: FAIL with both fingerprints (no re-pin here,
   ever: the re-pin after a reflash is the separate `repin --reflashed` command, run by a person).
4. `list` (before).
5. `install --good`; record the slot id it reports.
6. `trial <good id>` and follow it to the end: PASS only if the board came back in the trial slot.
7. `install --bad` WHILE the good slot's trial is still pending is not possible after step 6 (the trial ended), so
   the trial-pending refusal is its own step: `install --bad`, then `trial <bad id>` WITHOUT following
   (`--no-follow` or equivalent; add the option to `trial` if it does not exist), then `install --good` again: it
   must be REFUSED by the board because a trial is pending: PASS if refused, with the board's words recorded; then
   follow the bad trial to its end: PASS only if the board came back in the PREVIOUS slot by itself (the automatic
   return), with no command sent in between.
8. `confirm <good id>`; then `list` (after): PASS if the good slot is the default and the bad slot is shown as
   failed (or as the board names it).
9. The scorecard ends with: the board's fingerprint, the PC's fingerprint, security on/off, Atlas's commit
   (`git describe` is not available at run time: use the build's version string), the start time and end time
   in the PC's clock (never the board's), and one line per step.

Exit status: 0 when every step passed; 1 when any failed; 2 usage; 3 the pin rule refused the board.

The scorecard is plain text, one step per block, readable by a person who did not run it (UI for students: plain
words, no codes, no abbreviations). `--json` writes the same as JSON beside it (same path with `.json`).

## Proof (mandatory)

Against the simulated board (see how T1's tests stand up a sim and its bundles, and how a failed trial is simulated):
1. A full run on a fresh sim with a good and a bad bundle: exit 0, every step PASS, the scorecard holds each step's
   words; the trial-pending refusal's words are the sim's.
2. A run where the "bad" bundle in fact boots: step 7's fallback fails, exit 1, the scorecard says why in words.
3. A run against an address pinned to another key: stops at step 3, exit 3, both fingerprints in the scorecard.
4. The scorecard of run 1 is pasted into the PR text.

## Not in this PR

Signed bundles and the security-on steps (enrol, switch on, unsigned refusal, signed OFF): they join at the L2
move. Running against a real board: the coordinator runs it.

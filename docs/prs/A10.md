## Build

- `DeviceKey` says which kind it is: a board key (`family:serial`, from the hardware facts) or a node key (the Orion key fingerprint, for a node that publishes no hardware facts). Jobs that need a board identity (flashing, version installs, matching a board description) refuse a node key with a clear error; everything Orion itself provides works with either.
- `Identity` carries the board's Lemnos state as a field: absent (normal), answering, expected but not answering (faulted and restarting), built from a different revision (the app or the board needs updating). The board driver fills it; nothing carries it as a string attribute.
- The connection to a node (seeds, the monitor thread, reconnect with the failure rule, the handle later calls run on) moves out of `crates/drivers/board` into `crates/board/session` (`atlas-session`), so readings, actions, files and shell can each be their own crate under `crates/board/` without one driver depending on another. `crates/drivers/board` keeps discovery, identity and capabilities, and uses the session.
- The scan asks the registry which driver owns a device, so a device claimed by a family driver and by the any-family driver is reported once.

## Proof

Tests: a node key is refused for an install and accepted for a file read; each Lemnos state reaches an `Identity`; the board driver's tests pass on the moved session; a device two drivers claim is reported once.

# B29: the Raze kernel back to lean

**Group:** B. Board descriptions

**Needs:** B16, B25, B14 (merged); Lemnos I5i6 (kernel contract version 2, `contracts/slot-kernel.toml`, `[firmware.rpi-tryboot]`)

Read `AGENTS.md` and `docs/design.md` first.

## Why

The user's standing rule is lean and stripped on every board. The Raze's kernel on `next` was 23,796,224 bytes
`Image` (25,430,528 in Gaia's own build) against the dev image's 15,022,592. The table below is the measurement.

## Method

Every number here is from a kernel built out of tree in scratch with `CROSS_COMPILE=aarch64-linux-gnu-` (GCC
16.2.1, `make -j13`, niced, CPUs 6-31). The three configurations were resolved with the same cross toolchain:

- **before**: origin/next's fragments (`bcm2712` family `linux.fragment`, `raze.config`, `raze-trim.config`).
- **after**: this PR's fragments, read from `devices/`.
- **dev**: dev's `.config` (`linux-custom/.config` of the dev image's buildroot tree, read-only), resolved with
  `olddefconfig` and built with the same toolchain. Its `Image` is **15,022,592 bytes, the published dev figure
  exactly**, so the comparison is like for like.

Dev's trimmed set is the size floor. Every option that is `=y` or `=m` on next and absent from dev is turned off,
unless the slot contract, `lemnos.ko`, a driver Lemnos owns on this board, the gadget, pstore, or a deliberate
line (B14, B16, `raze.config`) needs it. A line is written only for a symbol that is on in the resolved next
configuration; a line whose symbol came out absent (its parent is off) or selected by something kept is dropped, so
every remaining line takes.

The checker's resolve was also corrected (see "The checker"): with the host compiler the same next configuration
resolved to 1,858 `=y`. With the cross compiler it resolves to 1,874 `=y`, with `ARM64_MTE=y` and the toolchain-probed
symbols as the build sees them. This PR reports the cross resolve only.

## Before and after (measured)

| | before (origin/next) | after (this PR) | dev (rebuilt, same toolchain) |
|---|---|---|---|
| resolved `=y` / `=m` (cross) | 1,874 / 1,657 | 1,342 / 123 | 1,354 / 259 |
| `Image` raw bytes | 23,796,224 | **15,159,808** | 15,022,592 (published 15,022,592) |
| `Image` `gzip -9` bytes | 9,451,478 | **6,779,760** | 6,701,888 (published 6,706,733) |
| modules built (`.ko`) | 1,645 | **114** | 250 (259 `=m` symbols) |
| installed module tree | 1,645 files, 21,816,661 B (`.ko.xz`) | 114 files, 7,723,788 B | not measured |
| release string | 7.2.9-v8 | 7.2.9-v8 | 7.2.9-v8-16k (its `LOCALVERSION`) |
| page size | 4K | 4K | 4K |

- Modules were installed with `make modules_install INSTALL_MOD_STRIP=1 INSTALL_MOD_PATH=<scratch>`, the same
  stripping Buildroot's `BR2_STRIP` applies. The before tree is xz-compressed (`MODULE_COMPRESS_XZ=y` in next);
  the after tree is not (that option is off here).
- After: 123 `=m` symbols produce 114 `.ko` files. Nine `=m` symbols build no separate `.ko` (combined objects or
  options without a module of their own). Not traced one by one.
- Dev: 259 `=m` symbols build 250 `.ko` files, the same effect.
- The `gzip -9` of dev differs from the published 6,706,733: a different gzip implementation or level on the
  publishing side. The raw figure is exact.
- Compared with the published dev image: after is **+137,216 bytes raw** (+0.9%) and about **+77,872 bytes**
  gzip against our own dev rebuild (+73,027 against the published figure). See "The gap to dev".

**The target was not reached.** The brief asks the after figure to be at or below dev's. It is 137,216 bytes over.
The gap is explained below, and the largest part of it is three things the Raze needs built in (the slot chain and
the USB gadget among them), not an unexamined leftover.

The four built-in groups above (about 185 KB) and the dev-only groups (about 109 KB) account for about 76 KB of the
+118 KB net symbol growth. The remaining ~42 KB is spread over smaller symbols and was not attributed one by one.
The largest known cause is the slot chain and the gadget built in (what the contract and the flasher need). Nothing
here is an option next was given on purpose that this PR removed without saying so.

**To reach dev's figure** (a further 137,216 bytes raw), the only sizable candidates are the gadget's built-in
functions and the dm stack, which the slot contract and the flasher require built in. Dropping them is a
contract change, not a trim. So the honest statement is: the Raze's kernel is 137 KB above dev because the slot
and gadget requirements are built in, where dev had dm and the gadget as modules.

## Dev-only options (dev has it, after does not): each decided

Counted from `analysis/sets-after3`: 39 dev `=y` and 137 dev `=m` are not on in the after config. Each is in one of the
groups below. Nothing Lemnos or the Raze needs is among them: every symbol of the Lemnos kernel requirement list is
checked `=y` in the after config (`CONFIG_MODULES`, the stock routes, the gadget, the RP1 chain, the slot chain and
the contract).

- **ECM, RNDIS, configfs serial** (`USB_CONFIGFS_ECM`, `USB_CONFIGFS_RNDIS`, `USB_CONFIGFS_SERIAL`, and the `USB_F_ECM`,
  `USB_F_RNDIS`, `USB_F_SERIAL` modules): off. The link is NCM; there is no RNDIS or ECM anywhere (the brief).
- **Overlayfs** (`OVERLAY_FS`, `OVERLAY_FS_REDIRECT_ALWAYS_FOLLOW`): off. `raze.config` keeps it off on purpose: Lemnos
  refuses layered slots.
- **Netpoll and netconsole** (`NETPOLL`, `NET_POLL_CONTROLLER`, `NETCONSOLE`): off. Nothing uses them; `raze.config`
  already turns netconsole off.
- **EFI** (`EFIVAR_FS`, `DMI_SYSFS`): off. The Raze boots through the Pi firmware, not EFI.
- **Squashfs** (`SQUASHFS` and its decompressors): off. No product mounts one (B16).
- **Media TV and test options** (`MEDIA_SUPPORT_FILTER`, `VIDEO_OV9282`, `VIDEO_RP1_CFE` and the other stock CSI and
  ISP modules): off. Lemnos owns the Raze camera (`raze.config`).
- **Toolchain-derived** (`CC_CAN_LINK`, `FS_STACK`, `XOR_BLOCKS_ARCH`, `CRYPTO_LIB_*_ARCH`, `CRYPTO_USER_API_ENABLE_OBSOLETE`,
  `BTREE`, `SKB_EXTENSIONS`, `GRO_CELLS`, `DST_CACHE`, `IPVLAN_L3S`, `SPI_DW_DMA`, `REALTEK_PHY_HWMON`, `MFD_WM5102`,
  `MULTIPLEXER`, `IIO_*`, `IKCONFIG_PROC`): follow from the options off above or from the toolchain. No line.

The full dev-only lists are `analysis/sets-after3/b_y_not_a_y.txt` and `b_m_not_a_m.txt` (scratch, not committed).

## The trim (`devices/boards/raze/kernel/raze-trim.config`)

The existing B16/B25 text is unchanged. A B29 header states the method and the kept-above-floor list; the new
section holds 882 `not set` lines, grouped under headers that name each group and its reason. Groups, with the
number of lines in each: crypto ciphers, modes and user API (25); input, Type-C, CEC, backlight and LED classes (14);
the legacy VideoCore camera and codec stack (10); tunnels, virtual networks and diagnostics (8); I2C controllers
other than the RP1 pair (4); filesystems and helpers no product mounts (4); SPI controllers (3); sensors and IIO (3);
Ethernet PHYs and MDIO (3); USB gadget functions the link does not use (2); the Cirrus codec (2); EFI (1); and 746
lines under the header "Everything else next has and dev does not, and that no kept line needs", grouped by the
symbol's first word. Each line was checked with `scripts/check-kernel-fragments.sh`: every requested line takes.

**Sound is not turned off** (the group was removed from the off list, see the Raze's GPU above).

## The family fragment (`devices/families/bcm2712/assets/linux.fragment`)

- `CONFIG_SPI_SPIDEV=y` removed. The SoC map has no SPI controller for the Raze (`lemnos-board.toml` names none), so
  `/dev/spidevB.C` has nothing behind it. The SPI core stays: `lemnos.ko` needs it.
- Five lines added with the contract's reason: `BRCM_CHAR_DRIVERS`, `MAILBOX`, `BCM2835_MBOX`, `BCM_VCIO`,
  `RASPBERRYPI_FIRMWARE`, all `=y`.

## The checker (`scripts/check-kernel-fragments.sh`) and the CI

- The checker now resolves every kernel with the arm64 cross compiler, `ATLAS_KERNEL_CROSS` (default
  `aarch64-linux-gnu-`), and exports `ARCH=arm64 CROSS_COMPILE=…`. It prints which toolchain it used. With no
  compiler on the machine it **fails by name** (it does not fall back to the host compiler). The header comment says so.
- A bare comment marker is refused, by file and line, before any kernel is fetched: a fragment line that is only
  `#` fails with `FAIL <board>: <file>:<line>: a bare comment marker`, and the self-test (`--self-test`) appends one to a
  scratch copy and requires that failure. The two fragments this PR edits had nine such lines (the family's comment
  blocks and the Raze trim's two); each is now an empty line. `devices/products/zero-3e-bringup/os.fragment` also has
  one: that is another product's file, not edited here, and the kernel checker does not read it.
- `.github/workflows/next.yml`: `gcc-aarch64-linux-gnu` is added to the apt line that installs flex and bison (one
  package; it pulls `binutils-aarch64-linux-gnu`).
- `scripts/check-devices.sh`: `SLOT_CHAIN` gains the five firmware symbols for `bcm2712`, in the existing style, so the
  gate holds them.

## Not proven

- **Nothing was booted.** A trimmed kernel is unbooted. The most likely thing to be missing is a driver the
  dev image had built in and this kernel drops in the groups above, and a person would see it as a missing device, not a
  panic: a USB device that does not appear (only a hot-plug module is gone, and the USB Ethernet, UVC and storage
  drivers are kept), or a missing console. The Raze has no VT (`VT` is off in both), so there is no HDMI console in
  either image.
- The after `Image` is 137,216 bytes over dev's raw figure (above).
- `lemnos.ko` (the out-of-tree module) was not built against this kernel. The module route needs the kernel's
  `Module.symvers`; that is Gaia's build, not this PR.
- The 9 `=m` symbols that build no `.ko` are not traced.
- Dev's 78-modules-loaded-at-idle figure is a boot measurement; this PR cannot reproduce it without a board.
- `ARM64_ERRATUM_834220` was listed as kept in an early draft; it is absent from both configurations, so no line exists for it.

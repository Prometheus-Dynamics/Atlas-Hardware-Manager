## What the lease is, and what Atlas does

The bridge keeps one lease per Orion caller identity, 60 s by default. A caller that makes no request to
that board's bridge for that long has its daemon connection dropped, which releases its claimed devices,
running action runs and transfers. Any request renews it. So a client that takes a hold and then stays
silent loses it. This PR is Atlas's side of that.

- `atlas_session::Hold` is the guard. Holding it means a hold exists; dropping it ends the hold. It is cheap
  to clone (each clone is one hold) and several holders may hold at once. A hold sends nothing by itself.
- While at least one hold exists on a session, the session's keep-alive makes sure a request reached the
  board's bridge at least every `LEASE_RENEW`. A request of the holder's own counts: a run, or a cancel,
  sent through `Handle::with_bridge`. Reads through `Handle::with_client` (topics, the node's hello) do not
  reach the bridge and do not count. When no hold exists the keep-alive sends nothing. A node that lists no
  Lemnos device has no bridge, so nothing is renewed on it (see "Deviation" below).
- The keep-alive runs in the session's own turn, before the turn's calls and steps, so a renewal is never
  queued behind a turn's work. It is one short call, bounded by `RENEW_WAIT`.
- A lost session stops the keep-alive with it. When the same node (same key) is back, renewals resume if
  holds still exist. A replaced board gets nothing: the keep-alive runs only on a Found session.
- Holds are per session, and a session is per board. A hold on one board sends nothing to another.

### The renewal call

- Today (the lock, `d6b9361d`): `lemnos.<device>.call` with no arguments. The bridge's `serve()` lists the
  devices (a read), then refuses a `.call` with no method, `call needs a method`, before it writes anything
  (`service/orion/src/calls.rs`, `serve`, the `words.split_first()` branch). The refusal is an answer, so the
  bridge has the request. `<device>` is the first `lemnos.device` resource the node lists
  (`orion.resources("lemnos.")`), cached for the session.
- At Lemnos I6h: `describe` as the argument (`lemnos.<device>.call describe`). Marked `// LOCK: Lemnos I6h
  describe` in `lease.rs`: the constant `RENEW_ARGS` inside `renew()`.

### The constants and their reasons

- `LEASE` = 60 s, the bridge's default (`LEMNOS_ORION_LEASE`). `// LOCK: Lemnos I6g lease period`. The
  period is not reported to a client (no hello fact, topic or description carries it), so it cannot be read
  from the node yet.
- `LEASE_RENEW` = 20 s = `LEASE / 3`. Two renewals may fail (a refused or slow one) before the lease runs
  out. The keep-alive turns every 100 ms, so a renewal is never more than 100 ms late.
- `RENEW_WAIT` = 2 s. A refusal answers at once (the normal case); a silent bridge is cut here, so one
  renewal never holds the session. A cut run is cancelled, and the cancel is itself a request.

## Who holds what on the board, and from when to when

| Holder | What it holds on the board | Guard taken | Guard dropped |
| --- | --- | --- | --- |
| Long action (`atlas-actions`, `jobs.rs`) | its run on the bridge: the lemnosd job the run drives, its claims | the step's first run, before the start is sent (`Tracked.hold`) | when the outcome is read (`forget`): Done, Failed, Cancelled. It is kept through a lost session, so a job waiting for the node still holds |
| Push (`atlas-files`, `push.rs`) | the transfer and its streamer on the board | at the start of the push's `run` | when `run` returns: committed, rejected, cancelled or failed |
| Slot install (`atlas-board-slots`, `install.rs`) | the install's accept, push and install steps | at the install's first step (`Run.hold`) | when the install settles (`finish`): Done or Settled. Kept across its steps and a lost session |
| Terminal (`atlas-access`, `terminal.rs`) | the open shell | at `open` (`Finish.hold`) | at any end of the terminal (`Finish::finish`), so also on close and drop |
| Topic subscriptions | nothing | not a hold | |

A topic subscription is not a hold: the answers' table of hold kinds (A3) has no subscriber, and a
subscriber is only a count on the board (`Publisher::subscribers()`). A subscription keeps no lease alive
by itself.

## How a dropped hold reaches each holder

Atlas cannot see the board's drop itself. What it can see is that its session was silent for longer than
the lease period while a hold existed: a lapse, recorded by the session (`Hold::lapsed()`,
`Handle::lapses()`). That covers a silent client, a machine that slept past the lease, and a session that
was down. A lapse means the board may have dropped the hold. It is an outcome of its own, with its own words:

- Job: `ActionError::HoldLapsed { call, reason }` ("the board may have dropped the hold on run N: no request
  reached its bridge within the lease (the board said: ...)"). The step ends as a retry, the lapse is
  acknowledged, and the run is followed again by its number. If the run had already ended with the board's
  error, that error is in the message. Tested: `a_board_that_drops_the_hold_on_a_long_action_is_reported_as_a_lapse_then_as_the_drop`
  (the job reports the lapse, then the board drops the run and the job fails with the board's
  "the lease ran out" words).
- Slot install: the install ends with `Stage::Failed` and the message "the board may have dropped the
  hold ..." (`HoldLapsed` through `classify`), or at a step boundary with `LAPSED`. Tested:
  `an_install_whose_session_lapses_while_the_board_runs_it_ends_as_a_lapse`.
- Terminal: `End::HoldLapsed` ("the board may have dropped this shell ..."). Nothing reopens it. Tested:
  `a_shell_whose_session_lapses_while_it_is_open_ends_as_a_lapse_not_as_a_loss`.
- Push: the push notes "the board may have dropped the transfer ... sending the file again from its start"
  and sends the file from its start, as after a lost session. Not tested (see Not covered).

## The simulated node

- `crates/testing/sim-node/src/lease.rs`: the lease per caller identity on a simulated clock. A request from
  a caller (a run, or a cancel of one of its runs) renews its lease at once. `SimNode::lease_advance(secs)`
  moves the clock: a caller silent for longer than the period loses its lease, and the node ends all of its
  running action runs with the lease's words. The bridge sees no detached flag at the locked Orion revision,
  so detached and attached runs both end; this is the worst case. A stalled run (`Behaviour::Stall`) ends
  when stalled for longer than the stall time. Transfers (files) are not modelled here.
- Defaults `PERIOD` 60 s and `STALL` 600 s (both `// LOCK: Lemnos I6g`); `SimNode::lease_set(period, stall)`
  shortens them. Nothing sleeps: drops are applied on the node's thread at its next tick and counted
  (`SimNode::lease_drops`).
- A device `.call` action is registered per device (`lemnos.<device>.call`), as the bridge names it. A
  `.call` with no arguments is refused with `call needs a method`, as the bridge refuses it.
  `SimNode::bridge_calls_started()` counts them, so a test counts renewals.

## Part 2: absent `hello.offers` is NOT REPORTED

- `hello.offers` is capped at 256 bytes at the lock (`service/orion/src/hello.rs`) and is silently dropped
  when it does not fit, which is about 19 contracts or more. An absent offers fact on a board that publishes
  other Lemnos hello facts therefore does not mean "offers nothing".
- `crates/drivers/board/src/identity.rs`: when the node publishes a Lemnos fact (`family`, `serial`, a
  `version.*`, `model`) and its offers are absent or refused, the identity records `offers.reported = no`.
  A node with no Lemnos facts is a plain Orion node and reports that it offers nothing, as before. Marked
  `// LOCK: Lemnos M8c (offers cap 1024)`.
- `crates/core/types/src/capability.rs`: `CapabilitySet` has a third state, `Offers::NotReported`, and
  `CapabilitySet::reading(kind)` returns `Reading::Granted`, `Reading::NotGranted` or `Reading::NotReported`.
  Orion's own kinds are granted for every node, as before. `grants()` is unchanged (false when not
  reported); a caller that gates must use `reading()`.
- `crates/drivers/board-slots`: `BoardSlots::for_capabilities(handle, board, &capabilities)` builds the gate
  from the set. A board whose offers are not reported gets `SlotError::NotReported` ("this board did not report
  what it offers") for every slot call, and nothing is sent. `BoardSlots::new` is unchanged.
- Actions and topics do not gate on `hello.offers` at this lock: no code path in either crate reads it, so
  nothing there hides or assumes a feature. They are unchanged, and the Hardware tab's gate is not in this
  repo yet.
- Tests: identity unit tests (a Lemnos node without offers, a plain node, read offers, twenty contracts with
  the offers dropped, refused offers); the simulated board with its offers missing
  (`a_board_whose_offers_are_missing_reports_them_not_reported_and_no_slots_is_not_claimed`); the slots gate
  (`a_board_that_did_not_report_its_offers_is_not_told_it_has_no_slots`). The twenty-contract board is
  modelled as the dropped fact, since the simulated node has no cap.

## Deviation: the device listing

To know whether a node has a bridge, the session lists the node's `lemnos.device` resources (a read of the
node, not a request to the bridge), once per renewal period while a hold exists, and caches the device. A
node that lists none is therefore asked again once per period while a hold exists. The earlier design read
the node's hello facts; that failed when a freshly started node had not published its facts yet at connect,
and the session then never kept a lease. The listing is current, so it is used instead.

## Not covered (the answers file, and this lock)

- A detached run from a dead caller is never cancelled until Orion R2: the bridge cannot see the detached
  flag at 455a956e (A3). The lease ends the bridge's connection, so the bridge ends the runs on it; a detached
  run's own owner is not told.
- Sessions of one user share one bridge connection (one caller identity). A live sibling session keeps a dead
  sibling's holds, because the lease is renewed for the identity. Per-session isolation is not possible at this
  revision.
- A push is one blocking step at the lock (A14, `Blocking`). No renewal can be sent while it runs, so a push
  longer than the lease can lose the other holds of the same board. The stepped push (Orion R2) fixes this.
- The answers do not say that a file transfer's chunks renew the lease. The session does not count them as
  traffic, so it renews on its own during a push. A stalled transfer is dropped by the board after 600 s.
- The lease period is not reported to a client. It is `LEASE` = 60 s (`// LOCK: Lemnos I6g`).
- The push's lapse path is implemented but has no test: at the lock a push is one blocking step, so a lapse
  is seen only between attempts, and the push then completes or fails on its own words.
- Real boards: none run. Every proof is against the simulated node. `untested on board`.

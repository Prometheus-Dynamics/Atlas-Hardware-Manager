## Watchdog timing windows (merge condition; read from source, pins below)

Pins read: U-Boot v2026.10 (research/u-boot, commit 55084065, tag v2026.10 = family.toml `[sources.u-boot]`);
kernel bare repo gaia/git/8231e0889387506d4ce07e38.git at commit 7595a62d (the commit the checker applies the
kernel series to; family.toml names v7.3.3, whose tag is not in that repo: NOT VERIFIED that 7595a62d == v7.3.3);

### 1. U-Boot arms and feeds
- Driver: `rockchip,rk3568-wdt`, `snps,dw-wdt` (dts/upstream/src/arm64/rockchip/rk356x-base.dtsi:1376-1382),
  driver drivers/watchdog/designware_wdt.c. Clock TCLK_WDT_NS = OSC_HZ = 24 MHz (drivers/clk/rockchip/clk_rk3568.c:2453-2454,
  arch/arm/include/asm/arch-rockchip/cru_rk3036.h:8 gives the macro form; rk3568 header not read: NOT VERIFIED for rk3568 OSC_HZ).
- Arm timeout: wdt-uclass.c:233 `timeout = WATCHDOG_TIMEOUT_SECS`, where drivers/watchdog/wdt-uclass.c:21 is
  `CONFIG_WATCHDOG_TIMEOUT_MSECS / 1000`. Kconfig default 60000 (drivers/watchdog/Kconfig:30-39, generic default). Our fragment
  does not set WATCHDOG_TIMEOUT_MSECS, and the DT has no `timeout-sec` (checked rk356x-base.dtsi; the radxa board DT not
  checked: NOT VERIFIED). Arm request = 60 s (wdt-uclass.c:88 passes `timeout*1000` ms).
- Hardware timeout actually set: designware_wdt.c:37 `i = fls(timeout*clk_khz - 1) - 16`, clamped to 0..15 (:38). For 60 s at
  24 MHz: fls(1 439 999) = 21, i = 5, TOP = 2^21 cycles = **87.38 s** (the device rounds UP to the next power of two).
  Hardware maximum: i = 15, TOP = 2^31 cycles = **89.48 s** (designware_wdt.c:37-40; kernel dw_wdt.c:53 DW_WDT_FIX_TOP).
- Feeding while U-Boot runs: `schedule()` (common/cyclic.c:121-131) runs the watchdog's cyclic reset every `reset_period`
  (wdt-uclass.c:242-245, default hw_margin_ms 1000 -> reset every 1 s). Callers of schedule() in the boot path: boot/image-board.c:178
  (image copy), boot/bootretry.c:68 (wait for input), common/cli_readline.c, common/console.c, common/menu.c, board_f/board_r init.
  The filesystem read path (fs/ and cmd/bootflow.c, drivers/mmc/mmc.c, cmd/booti.c, arch/arm/lib/bootm.c) has NO schedule():
  so an extlinux load (`load`/`booti`) does NOT feed. Measured: NOT MEASURED (the load time on this board is not known).
  Window: last U-Boot feed -> kernel probe must be < 87.38 s. Expected from the load of kernel+dtb+initramfs over SD: NOT VERIFIED.

### 2. Kernel keeps or re-arms it
- dw_wdt probe (7595a62d drivers/watchdog/dw_wdt.c:641-646): if the watchdog is already enabled, the timeout is read back from
  TOR (wdd->timeout = dw_wdt_get_timeout) and WDOG_HW_RUNNING is set; otherwise DW_WDT_DEFAULT_SECONDS = 30 (line 55).
  So a U-Boot-armed device reports ~87 s to the kernel.
- Feed by the kernel: watchdog_dev.c:60-61 `handle_boot_enabled = IS_ENABLED(CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED)`;
  watchdog_need_worker (:76-95) is true when `!watchdog_active && t && watchdog_hw_running`, so the kernel pings a boot-enabled
  watchdog from its worker until userspace opens /dev/watchdog. Kconfig default y (drivers/watchdog/Kconfig:50-52: "default y").
  arch/arm64/configs/defconfig does not set it (grep: only CONFIG_WATCHDOG=y, CONFIG_DW_WATCHDOG=y at :807-814). Our
  linux.fragment does not set it either (devices/families/rk35xx/assets/linux.fragment:74 sets DW_WATCHDOG only).
- open_timeout: Kconfig default 0 (watchdog Kconfig :61-68) = infinite: the kernel keeps feeding until userspace takes over.
- CONSEQUENCE: between kernel probe and the first userspace open, the kernel feeds the device; the device does NOT reset
  for lack of an owner in that interval. A product with no owner is therefore not a reset loop on this kernel; it is an
  armed device the kernel keeps fed forever (the one-owner XOR is still broken, and the rock-5c-base finding is about
  ownership, not a reset). This corrects the coordinator's premise, which is stated here with its source.
  NOT VERIFIED on a board: the boot-enabled ping path on v7.3.3 itself (only 7595a62d was read).

### 3. First feed by the owner
- BRINGUP image (systemd, devices/components/bringup-alive/files/10-watchdog.conf:24 `RuntimeWatchdogSec=16s`): systemd
  opens /dev/watchdog at PID 1 start and pings every half of the timeout (8 s), per the file's own comment (:1-2). The
  takeover moment within boot: NOT VERIFIED (systemd 258.7 source is not on disk). Before the takeover, the kernel feeds.
- BENCH image (lemnosd): the hw-watchdog driver opens the node at bind (drivers/hw-watchdog/src/lib.rs:150-158, write-only
  open arms it with the inherited timeout; the driver then sets 15 s, board file `config = { timeout_s = 15 }`,
  devices/boards/radxa-zero-3e/lemnos-board.toml:87-92). Feeds are gated by the daemon's liveness (lib.rs:50-56; host.rs:428-432):
  healthy = main loop turned within TURN_BOUND = **10 s** AND control socket answered within ANSWER_BOUND = **5 s**, probed every
  PROBE_EVERY = **1 s** (service/lemnosd/src/liveness.rs:12-18). Failed feed: retried 250 ms, doubling, capped 8 s (lib.rs:68).
  Unit (packaging/systemd/lemnosd.service, Lemnos 50907f37): `Type=notify` (READY=1 after drivers start and socket listens),
  `Restart=always`, `RestartSec=1s`, `StartLimitIntervalSec=0` (:43-44), `WantedBy=multi-user.target`, NO `After=` other than the
  implicit local-fs/sysinit ones, `ConditionPathExists=/etc/lemnos/board.toml`.
  Window to the first healthy tick after bind: NOT MEASURED. Must be < 15 s from the bind (the device resets 15 s after its
  last good feed/timeout set).

### 5. Conclusion per image (numbers)
- **U-Boot -> kernel window: margin = 87.38 s - (last U-Boot feed -> kernel probe). The probe time is NOT MEASURED; a plausible
  value (seconds) gives a large margin, but it is NOT SHOWN here.**
- **Bringup (systemd 16 s): margin = 16 s - 8 s ping interval = 8 s between pings, once systemd holds the device. Before
  that, the kernel feeds. SHOWN from the file (10-watchdog.conf); the takeover time is NOT VERIFIED.**
- **Bench (lemnosd 15 s): margin = 15 s - (bind -> first healthy tick). NOT SHOWN: the first healthy tick needs a loop turn and a
  socket answer, and their time is not measured.** A window that is too short is a reset loop (Restart=always, 1 s; each boot
  that starts slowly resets). Options, none implemented (the coordinator decides):
  (a) raise the board's `timeout_s` from 15 to e.g. 60 (lemnos-board.toml:92 `config = { timeout_s = 15 }`; the hardware max is
      89.48 s, so 60 is inside the range). Reason: the first healthy tick after bind can exceed 15 s on a slow first boot.
      Cost: a hung daemon is caught 45 s later. This is ours to write, with the reason stated in the board file.
  (b) lemnosd starts earlier / bind later (Lemnos ordering; not ours to change here).
  (c) the kernel-fed window (HANDLE_BOOT_ENABLED) does not help: once userspace opens the device, the kernel stops feeding.
  The one-owner rule forbids systemd RuntimeWatchdogSec on the bench image, so systemd is not an option here.
- **Recommended, NOT implemented: (a), with the timeout_s change and its reason written in the board file, after the
  first-boot measurement shows the bind-to-first-tick time.** Until measured, the bench margin is NOT SHOWN.

### 7. Coordinator's rulings applied (this draft)
- Wording: an armed product with no owner under HANDLE_BOOT_ENABLED=y and no open timeout is **kernel-fed forever: never
  resets** (silent, not a loop). Sources: watchdog_dev.c:60-61 (handle_boot_enabled), :76-95 (need_worker), watchdog Kconfig
  :61-68 (open_timeout default 0 = infinite), watchdog_dev.c:65-74 (past deadline; set_open_deadline with 0 = KTIME_MAX),
  :204-215 (worker pings while hw_running and not past the deadline).
- CONFIG_WATCHDOG_OPEN_TIMEOUT: the kernel sets `open_deadline = now + open_timeout` at registration (watchdog_dev.c:1088,
  watchdog_set_open_deadline), and stops the kernel's pings once that deadline passes without a userspace open (:204-215).
  The hardware then resets when its own timeout runs out after the last ping. So the value is a deadline from boot on the
  kernel's clock: a boot where nothing opens /dev/watchdog resets about open_timeout seconds after registration plus the
  hardware timeout (the last ping sets the clock). NOT VERIFIED: the exact reset instant on hardware.
- open_timeout longer than the hardware maximum (89.48 s): the core's own pinging is not limited by the hardware maximum:
  the worker pings every max_hw_heartbeat_ms / 2 (watchdog_dev.c:129-141 update_worker; :82-95 need_worker) until the
  deadline. So a deadline beyond 89.48 s is served by the core's pings, not by a single hardware timeout. NOT VERIFIED on the
  board that the pings keep the device fed for the whole window.
- lemnosd opening: the hw-watchdog driver opens /dev/watchdog0 at its bind (drivers/hw-watchdog/src/lib.rs:150-158, a
  write-only open); the bind is the host's device start (engine/host/src/host.rs:506 "waiting for its first bind"), retried on
  NOT_FOUND (lib.rs:44-46). The kernel-fed window therefore ends at that bind, not at the first healthy tick. The exact
  position of the bind relative to the unit's READY=1 (packaging/systemd/lemnosd.service:22): NOT VERIFIED.
  M41b stamps (bind -> running-ok): NOT FOUND in the Lemnos checkout read (50907f37; no M41 text in the repo).
- lemnosd timeout_s stays 15 (not proposed for change here).

### 10. Open-timeout value (provisional; Lemnos decides)
- Provisional: `CONFIG_WATCHDOG_OPEN_TIMEOUT=180` in devices/families/rk35xx/assets/linux.fragment, marked PROVISIONAL.
  Reason: must exceed the slowest legitimate first boot before lemnosd binds (the bind ends the kernel-fed window). The

  must not be the Raze's 30 if first boot is slower than that.

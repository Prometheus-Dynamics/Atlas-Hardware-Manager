# Atlas 2026.1.0 release notes (draft for review)

Since 2026.0.0. Atlas was rebuilt from the ground up as a manager for every
device on a robot: it finds them over USB, through another device, or on
the network, and flashes, updates and checks them. This draft is from the
development history (over 440 commits); the Raze device package's own changes
are in `devices/raze/CHANGELOG.md`.

## Highlights

- **One app for the robot.** The Overview shows the robot's readiness and a
  map of how each device is reached. Every device has a live page with
  readings, cameras, logs, history and its actions. Devices reached through
  another one, such as a SystemCore's boards, are listed under it.
- **Flash a board from scratch.** Atlas flashes a Raze in USB boot in two
  ways. It can serve the eMMC over the board's USB, or let Atlas's own
  flasher on the board write the image itself. It can also flash a board
  plugged into a SystemCore's USB, through Atlas's USB agent on the
  SystemCore. It reads every write back. When a flash is cut short, Atlas
  carries on from where it stopped.
- **Update without a flash.** A/B updates, and slot installs on boards that
  keep several OS images, go through Orion first and SSH second. A board
  on USB can also be updated through its own console, with no SSH key
  needed. A failed trial boot rolls back by itself, and Atlas says why.
- **The robot network.** Atlas finds and reads the roboRIO (including CTRE
  Phoenix's CAN devices), the radio and the SystemCore. It installs `.ipk`
  packages on a SystemCore and checks its USB link. It also has a
  NetworkTables viewer with a local NT4 server.
- **Live data.** Readings stream from boards over Orion, with polling as
  the fallback. Atlas keeps board clocks in sync, merges a board's event
  log into its history, and shows the board's last boots (reset causes,
  rollbacks, kept kernel logs).

## Flashing and recovery

- Raspberry Pi boards in USB boot, written by Atlas's own Rust `rpiboot`,
  so no vendor tool is needed. This works on Linux, Windows and macOS.
- Atlas checks the host before writing and refuses system and internal
  disks. It writes xz, zstd or gzip images directly, reads them back to
  verify, and restarts the board into its new image.
- After a flash, Atlas puts this computer's SSH key on the board, forgets
  the board's old host key, and runs the board's self-test.
- `atlas flash` does the same from a terminal, for scripts and CI.
- **Through a SystemCore:** Atlas installs and updates its USB agent on the
  SystemCore with one click (an `.ipk`, a memory-capped service). Boards in
  USB boot on the SystemCore's USB show as its children and flash through
  the agent. A flash goes on if Atlas's link drops, and an Atlas started
  again follows it to its end.
- **New boards, written and not yet tested on a board** (the boards are on
  order): Rockchip maskrom flashing for the Radxa ROCK 5C (RK3588S2), the
  ROCK 4D (RK3576) and the Luckfox Pico Pro (RV1106G2), and K230 USB
  burning for the CanMV K230D Zero. Atlas also writes UBI images to raw
  SPI-NAND the way `ubiformat` does. Each board's record says it is
  untested, and Atlas says so before it flashes
  (`docs/soc-flashing.md`).
- **NAND slots on a running board** (written, untested): `atlas-ubi
  nand-slot` installs, trial-boots and commits Gaia's A/B slots on SPI-NAND,
  checking every write so a power cut always leaves a slot that boots. The
  Luckfox Pico Pro's image carries it. Atlas doesn't drive it yet: how Atlas
  sends commands to such a board is still open.

## Updates, slots and images

- One Software tab per device. It offers an update in place or a fresh
  install from one list of images, and says which image will be written.
- **Slots:** boards that keep several OS images (dynamic slots, including
  layered slots and a live layer push for fast testing). You can install,
  boot once, confirm, pin and remove slots. `atlas slots` does the same
  from a terminal.
- Atlas runs an image server that boards download from. Slot installs work
  without SSH keys while board security is off, and through a robot
  controller's HeliOS for boards behind it.
- **Releases:** local images and remote manifests. Signatures and checksums
  are used when present and never required. An unsigned image gets a
  warning; a mismatch offers "Download again" or "Flash anyway". Downloads
  ride out server errors and dropped connections.

## Devices and the robot

- Device packages (`devices/`) describe each board's hardware, recovery
  steps, EEPROM files and identity. New boards and controllers are added as
  data:
  - the Raze has a full package;
  - the roboRIO and the SystemCore are recognised from data;
  - the four new boards have flash records, and a small read-only identity
    service (`board-lite`) in their images, so Atlas lists them when they
    run.
- **Hardware tab:** a Raze's sensors, fan, LED ring and USB port power,
  live, with the IMU shown in a 3D model of the case.
- **Self-test:** Atlas runs a board's hardware checks after a flash or
  update, and you can run them again from the device page.
- Discovery is event-driven: USB hotplug and mDNS trigger a scan. A sweep of
  the robot networks finds boards that mDNS misses, including boards behind
  a camera's USB route onto the robot network.
- A ROBOT/PIT switch in the device header. ROBOT locks network, team and
  security settings and holds back the self-test and IMU calibration (they
  drive the board's hardware); PIT opens them.
- **Support bundles:** a board's own diagnostics as one `.tar.gz`, from
  the device page or `atlas support`.
- **Boards behind a SystemCore** are listed under it and reached through
  its HeliOS, including their camera views. They get Restart and their
  slots (install, boot once, set as default, remove, pin) the same way,
  with no SSH key. An install that restarts the board is followed until
  the board is back on its new slot, even when the restart cuts off
  HeliOS's answer. A board the SystemCore sees on its USB but can't route
  to is shown as unreachable, with the reason.
- **Camera views:** each camera's live preview on the device page, with a
  picker when a board has several, and the SystemCore's own cameras. A view
  that loses its stream keeps the last frame and reconnects by itself.
- **Health** reads a robot's power cuts as normal; it warns only when a
  board keeps crashing (three of its last ten boots).
- Atlas speaks Orion protocol 1, and says which side to update when a
  board's Orion is newer or older.

## Atlas itself

- **It updates itself** from its GitHub releases. It picks the installer
  for how it's installed here, checks its SHA-256, and verifies the
  release's signed manifest when signing keys are configured. Releases are
  unsigned for now (the signing key is pinned for later), so Atlas says the
  update isn't signed.
- **Installers:** deb and rpm (with USB access set up), AppImage, Windows
  (with the WinUSB driver) and macOS. The CLI is in the same binary.
  Installed size went from 88.9 MB to 55.9 MB on Linux.
- The interface was redesigned: dense, sharp-cornered, every page fitting
  the window, and lighter on older laptops (no blur, no looping animation).
- Idle boards are asked for less: pushes replace polling where a board
  streams. An idle board takes about 2 requests a minute instead of 11.
- **It logs its own trouble:** a command that fails or hangs goes to
  `atlas.log` with an error id and your last few clicks, and the error's
  toast shows the same id. A failed request says what the device answered.
- Reversible actions (restarting a port or a board) run on click, without
  a confirmation step.

## Known limits

- **Not yet proven on hardware:**
  - a fresh USB-boot flash with this release;
  - how soon a stalled USB link is noticed (a rebind itself brings the
    link back in about 10 s; no stall has happened on the bench to time
    the noticing);
  - an A/B update in place;
  - a keyless slot install over robot Ethernet;
  - PIT/ROBOT on a whole robot;
  - Atlas following a flash through a SystemCore's USB agent after Atlas
    itself restarts (a real flash through the agent worked on 2026-11-03);
  - the four new boards.
- Windows and macOS installers haven't been tried on real machines yet.
- Releases and installers are unsigned.
